# NotebookLM_PDF_2_PPT

<img src="pdf2ppt/assets/icon-256.png" alt="" width="104" align="right">

把 **NotebookLM 產出的 PDF 簡報** OCR 後轉換成**可編輯的 PowerPoint**。完全在本地執行、資料零上傳。

每頁投影片的輸出結構：

- 以全解析度的頁面渲染圖作為背景，版面 100% 保留
- 每行文字疊上一個「取樣自原圖底色」的實心色塊，蓋住圖中的點陣文字
- 色塊上承載**真正可編輯的文字方塊**，字級、粗體、文字顏色、對齊都從影像自動估計

## 特色

- **本地離線**：OCR 使用 [RapidOCR](https://github.com/RapidAI/RapidOCR)（PP-OCRv5 server 模型），只有首次執行需要網路下載模型
- **GPU 加速**：支援 DirectML（Windows 上任何 DX12 GPU，含 Intel 內顯）與 CUDA，自動偵測選用，實測快約 4×（見[安裝](#gpu-加速選用)）
- **繁體中文最佳化**：PP-OCRv5 server 模型對繁中準確度遠勝預設模型；自動修正辨識混入的簡體字形（恶→惡，採台灣標準 s2tw 字典；只改 Big5 寫不出來的字，「划得來」「拉升」「注定」「他那台」這類兩種寫法都合法的字不會被改掉，除非同一頁確實出現了簡體殘留），整行滑成簡體的短標籤以同頁詞彙佐證後修正，刻意呈現的純簡體內容仍保留
- **樣式擬真**：字級以字墨高度實證校準、文字色取筆畫核心避免反鋸齒偏色、底色支援緞帶/膠囊/多層背景的判別
- **帶投影的文字**：簡報常給白字加一層柔和暗色投影。底色取樣會往外走到顏色穩定為止，不會把投影誤當成籌片色；蓋板也依量到的投影半徑外擴、上下相鄰的同色蓋板在接縫處會合，原稿投影不會沿著色塊邊緣露出暗框
- **偵測框切到字形也蓋得住**：偵測器偶爾把大字的框切小（步驟徽章的數字只框到一半），系統會沿著字墨走出框外找到真正的字形邊界，蓋板與可編輯文字都跟著對齊；表格格線、公式橫線等「畫出來的線」不會被誤認成字形
- **表格儲存格不會被併成一行**：同列相鄰的兩個儲存格看起來就像被打散的標題碎片，系統會檢查兩者之間有沒有欄線，有就不合併
- **並排卡片字級一致**：同一列的多張卡片，若只有其中一張的文字短到不受卡框寬度夾制而放大一階，會跟著同列多數縮回同一級（原稿本來就同級）
- **傾斜與弧形文字**：偵測器給出旋轉框時直接輸出旋轉文字方塊；弧形緞帶（圓弧排列的橫幅文字）自動偵測曲率，以分段切線文字方塊沿弧線排列、色塊條帶沿弧線覆蓋
- **文字品質**：自動還原英文單字間的空格（含物理墨水驗證防誤插）、中英交界補空格（盤古之白）、復原被裁掉的行尾標點、同一行多種顏色會拆成多個 run、行首 ⚠ 警告圖示不會誤認成字母 A
- **浮水印清除**：右下角的匯出浮水印（Logo + 字樣）自動以同底色色塊遮蓋，新舊品名皆支援（**Gemini Notebook** 與舊版 **NotebookLM**）；遮蓋範圍在渲染圖上逐列／逐欄量測，緊貼浮水印本體，不會連旁邊的頁框線或卡片一起塗掉（`--keep-watermark` 可保留）
- **圖表內文不亂轉**：插圖裡太小、太模糊的文字（流程圖小框、K線圖刻度、終端機截圖等，OCR 結果多為亂碼）自動偵測並**保留原圖不處理**，不會疊上錯字色塊；清晰可辨的小字（時間戳、圖例籌片）仍正常轉換（`--keep-tiny-text` 可關閉）
- **無法忠實還原的視覺內容保留原圖**：線稿圖示被誤讀成單字母（交叉箭頭 → 大「X」）、markup 示範的刪除線疊字（`==螢光==` 上的紅 ✗）、上下標化學/數學式（H₂O、X²）等轉成可編輯文字必然失真者，自動偵測並保留原圖點陣
- **雙色橫幅**：一句橫跨深/淺兩塊背景的橫幅（前半深底白字、後半白底黑字）會偵測背景的銳利分界、拆成兩塊蓋板加分色文字，忠實重現反白效果

## 安裝

需求：Windows、[uv](https://docs.astral.sh/uv/)（Python 由 uv 自己準備，目前鎖在 3.14）

**雙擊「安裝.bat」**即可，它做的就是一句 `uv sync`。手動的話：

```bash
uv sync
```

第一次會下載約 300MB（`onnxruntime-directml` 佔大宗），之後由 `uv.lock` 鎖住版本，換電腦重跑一樣的組合。OCR 模型（約 100MB）另外在**第一次轉檔**時自動下載，需要一次網路。

裝好之後只有兩個入口（2026-08-25 起：交付面刻意留得單純，資料夾裡不該有一堆長得都像入口的檔案）：

| 檔案 | 做什麼 |
|---|---|
| **啟動.vbs** | 開圖形介面，**不會有黑視窗**（平常用這個） |
| **安裝.bat** | 建環境／更新相依套件，**順便在桌面與「開始」功能表放上圖示** |

要看訊息、或要用命令列批次轉檔的話，在資料夾裡開終端機（按住 Shift 點右鍵 →「在終端機中開啟」）執行 `uv run python pdf2ppt_gui_2.py` 或下面的命令列用法即可。

> **桌面與「開始」功能表的圖示**：跑過「安裝.bat」之後，桌面與「開始」功能表會出現一顆**NotebookLM PDF → PPT 轉檔工具**，雙擊就開圖形介面（和雙擊「啟動.vbs」完全一樣，一樣不會有黑視窗）。圖示本身是 `pdf2ppt/assets/icon.ico` —— 藍磚上四個取景角框住一個「文」字，就是 OCR 的定義。
>
> ⚠️ **把整個資料夾搬到別的地方之後，要再跑一次「安裝.bat」**：捷徑記的是絕對路徑，不重建的話桌面上會留一顆指向舊位置的死圖示。只想重建捷徑、不想重跑安裝的話，在資料夾裡執行 `uv run python tools/make_shortcut.py` 就好。
>
> 捷徑建不出來（桌面被公司政策鎖住、OneDrive 沒登入、資安軟體擋寫入）**不影響使用**，安裝.bat 會改口告訴你雙擊資料夾裡的「啟動.vbs」一樣能開。

> **程式已經開著時再點圖示，不會開第二個**：它會把已經開著的那個視窗叫到前面。同時跑兩份沒有好處——兩邊會搶同一顆顯示卡、各自載一份辨識模型，結果只是兩邊都變慢，而畫面上看不出來。要一次轉多份 PDF 的話，在同一個視窗裡連續轉即可。
>
> **黑視窗與錯誤訊息**：`啟動.vbs` 把主控台隱藏起來，所以原本會印在那裡的東西改由兩個地方接住。
>
> - **資料夾複製不完整時**（少了 `pyproject.toml`、`pdf2ppt_gui_2.py`，或是隔壁那個 `winkit` 共用資料夾）：`.vbs` 會**在啟動程式之前就擋下來**，用中文列出少了哪幾個檔，請你把整個專案資料夾完整複製過來、再跑一次「安裝.bat」。⚠️ 這個工具用到一個放在**隔壁**的共用資料夾 `winkit`（兩支桌面小工具共用的顏色與視窗零件），所以搬家時要把**它們的上一層整個**複製走，只複製這一個資料夾是不夠的。少了這道守門的話，看到的會是 uv 或 Python 的英文訊息——少了 `pyproject.toml` 那種甚至**什麼訊息都沒有**，視窗照常開，要等按下轉檔才失敗。
> - **程式起不來時**（`uv` 沒裝、環境沒建好、Python 在載入期就炸）：`.vbs` 會**當場把錯誤內容跳訊息框顯示出來**，不必自己去翻檔案。
> - **程式跑起來之後**：每次啟動都會在專案底下的 **`logs`** 資料夾寫一份執行紀錄（檔名就是啟動時間，例如 `logs\2026-08-24_143020.log`），介面下方日誌區看得到的東西那裡都有，轉檔失敗的完整訊息也在裡面。**保留 30 天**，過期的自動清掉。要回報問題時，附上最新的那一個檔即可。
>
> 紀錄檔萬一寫不出來（磁碟唯讀、防毒攔截），從終端機執行 `uv run python pdf2ppt_gui_2.py`：訊息會直接印在那個視窗裡。
>
> **另外一個會被寫到的地方**：介面的圓角底板有五種顯示縮放的現成圖（100%／125%／150%／175%／200%）。如果你的螢幕是別的縮放（4K 面板常見的 225%／250%／300%，或自訂值），程式會**第一次啟動時當場畫一份**（多花零點一秒左右）並存進 `%LOCALAPPDATA%\NotebookLM_Pdf2Ppt\skin`，之後就直接讀它。那個資料夾**刪掉完全沒關係**，下次啟動會再畫一次；寫不進去（家目錄唯讀）也只是每次啟動各畫一次，畫面一模一樣。

中文輸出字型預設為 Microsoft YaHei（Windows 內建），可用 `--font` 改成其他字型；英文（拉丁字元）一律輸出為 Arial、**大標題（≥28pt）改用 Arial Narrow**（來源簡報的拉丁字較窄，長標題用 Arial 會明顯過長）— 中英混排的行會同時呈現兩種字型（PowerPoint 的字元級字型機制，單一 run 即可承載）。

### GPU 加速

**不需要任何額外安裝或設定**：相依套件裡直接綁的就是 `onnxruntime-directml`（Windows 上任何支援 DirectX 12 的 GPU：Intel Arc/Iris、AMD、NVIDIA 皆可），實測 **快約 4×**（Intel Arc 140V：整份 15 頁簡報 50 秒，CPU 為 210 秒）。

`--device` 預設為 `auto`，依可用性自動選用 DirectML > CUDA > CPU，實際用到哪一個會印在啟動時的 `OCR: …` 那一行供確認；也可用 `--device dml/cuda/cpu` 強制指定。NVIDIA 的 CUDA 路徑要另外 `uv pip install onnxruntime-gpu`。

> ⚠️ **不要改裝成 CPU 版的 `onnxruntime`**：DirectML 版是「取代」CPU 版的完整 build（同時提供 CPUExecutionProvider），裝了 CPU 版就沒有 GPU，而且**首次**執行需要一次性的驅動 shader 編譯、那次速度看起來與 CPU 差不多——所以裝錯了不會當場發現，只會一直慢 4 倍。編譯結果會由顯示驅動快取到磁碟，**第二次起**才看得到完整的加速效果。

## 使用方式

### 圖形介面

```bash
uv run python pdf2ppt_gui_2.py
```

在專案根目錄執行即可（它會自己找到同目錄的 `pdf2ppt` 套件）。挑一份 PDF——**或直接把 PDF 拖進視窗**——然後按「開始轉檔」。它做的事就是把選項組成命令列，然後在背景執行緒呼叫同一支 `pdf2ppt.cli.main()`。

介面採 **Sun Valley** 佈景（模仿 Windows 11 Fluent／WinUI 的外觀），版面是由上而下的**三張圓角卡片**（轉檔／轉檔選項／詳細訊息，後兩張預設收起來），按鈕、輸入框、核取方塊與進度條也都是圓角的實色底板、配 Apple 的色票（主要動作是 Apple 藍、停止是紅），字型 Microsoft JhengHei UI，**亮／暗自動跟隨 Windows 的「應用程式模式」**（要固定的話設環境變數 `NOTEBOOKLM_PDF2PPT_THEME=light` 或 `dark`），並已開啟 DPI 感知，在 125%／150% 顯示縮放下不會糊。

**主畫面只留一件事**：選一份輸入 PDF。輸出檔名自動帶成同名的 `.pptx`（顯示在下面一行，要改按「變更…」）。

**介面上只有五個選項**，收在**開始轉檔底下**那顆「▸ 轉檔選項」按鈕裡，按一下才展開：

| 介面上的選項 | 對應旗標 |
| --- | --- |
| 頁碼（例 1-5,8，留空＝全部） | `--pages` |
| 保留浮水印（NotebookLM／Gemini Notebook） | `--keep-watermark` |
| 關閉簡體混入修正 | `--no-s2t` |
| 色塊獨立畫成矩形 | `--cover` |
| 保留圖表內小字 | `--keep-tiny-text` |

下面選項表裡的其餘旗標（`--dpi`、`--font`、`--min-score`、`--device`、`--lang`、`--fast`、`--no-bold`／`--force-bold`、`--merge-lines`、`--debug`）**介面上沒有**，一律使用預設值：它們不是改了會讓結果差很多（DPI／字型／信心分數是校準值，粗體模式與快速模型會整份換掉判別依據），就是日常根本用不到（`--device` 有 auto、`--lang` 預設就是中英、`--merge-lines` 與 `--debug` 是開發用的）。真的要動就用命令列。

**轉檔時看得到什麼**：「開始轉檔」旁邊就是進度條與「3/15 頁」（首次執行要先下載 OCR 模型，那段沒有頁數可報，進度條會先跑不定長度的動畫）。同一顆按鈕在轉檔中變成「■ 停止轉檔」，按下去會在**目前這一頁跑完之後**收工，而且**不會產生檔案**（半份簡報比沒有更糟）。⚠️ **轉檔中所有選項與檔案欄都會變灰**：命令列在按下去的那一刻就組好送出了，這時候改頁碼、改核取方塊或換一份 PDF 對這一趟都沒有作用，所以乾脆不讓你按（拖放與 Ctrl+V 同樣會被擋下並說明原因）。要換就先按「停止轉檔」。跑完的結果寫成一列顯示在畫面上——降級的頁碼直接寫在那一列，旁邊是「開啟簡報」與「開啟資料夾」。每頁的詳細訊息收在「▸ 詳細訊息」裡（轉檔一開始會自己展開），右邊的「開啟紀錄」開的是這一趟的執行紀錄檔。

**切到別的視窗也看得到進度**：轉檔中，工作列上那顆圖示本身就是進度條；轉完會閃一下提醒你，而且**有頁面降級會留一條黃的、失敗留一條紅的**——不必切回來就知道這趟不是乾淨完成。⚠️ **它不會把視窗搶到你面前**：你這時多半正在別的地方打字，被搶走焦點比沒收到通知更糟。按「停止轉檔」是你自己做的動作，所以不閃、也不留顏色。

> 視窗高度會自己配合內容，並鉗在螢幕的工作區以內；展開「轉檔選項」時會把「詳細訊息」收起來（兩區同時攤開會超出小螢幕）。自己拉過視窗大小之後就只長不縮。

介面上**沒有「程式在哪」這種選項**：它載入的一律是 `pdf2ppt_gui_2.py` 自己所在資料夾裡的 `pdf2ppt` 套件。同一層找不到那個套件（複製時漏了東西、只把這支 .py 拉出來放），會跳一個說明資料夾路徑的錯誤訊息，**視窗不會開起來** —— 請把整個專案資料夾完整複製過來，再執行一次「安裝.bat」。

> **注意**：命令列的 `--dpi` 與 `--font` 會影響排版估算的準確度 — 字級／粗體／色塊的所有判別門檻都是以 200 DPI 搭配 Microsoft YaHei 字寬校準的（`style.py` 量寬度時固定使用 `msyh.ttc`，不隨 `--font` 改變）。非必要不要更動，這也正是圖形介面不再露出這兩項的理由。

### 命令列

```bash
uv run python pdf2ppt.py input.pdf                    # 輸出 input.pptx
uv run python pdf2ppt.py input.pdf -o output.pptx     # 指定輸出檔名
uv run python pdf2ppt.py input.pdf --pages 1-5,8      # 只轉指定頁
uv run python pdf2ppt.py input.pdf --keep-watermark   # 保留右下角的匯出浮水印
```

執行時每頁印一行：頁碼、轉成文字的行數、形狀數、丟回原圖的行數、浮水印，以及**這一頁花了多久**（只有總時間的話看不出是哪一頁慢——一行進入旋轉救援就要跑七次 OCR）。

```
Loading OCR engine... (first run downloads ~90MB of OCR models)
OCR: PP-OCRv5 rec=server, device=dml, dpi=200
page 1 (1/15): 11 lines, 11 shapes, 4 tiny/blurry left as image, 1 watermark wiped, 5.5s
page 2 (2/15): 12 lines, 12 shapes, 1 watermark wiped, 1.6s
Saved input.pptx (15 slides, 41.7s)
```

離開碼有三種：**`0`** 全部正常、**`3`** 有頁面降級（檔案可用，降級的頁碼列在最後一行 `WARNING:`）、**`1`** 每一頁都失敗。圖形介面會把這三種結果分別顯示出來（另有 **`4`**＝使用者按了停止，只有圖形介面才會出現）。

### 選項

| 選項 | 說明 |
|---|---|
| `-o, --output` | 輸出檔路徑（預設：輸入檔名改副檔名 `.pptx`）|
| `--dpi N` | 渲染解析度（預設 200）|
| `--pages 1-5,8` | 頁碼選擇 |
| `--min-score 0.5` | 過濾低於此信心分數的 OCR 行 |
| `--cover` / `--no-cover` | 色塊放哪裡。**預設 `--no-cover`**：讓文字方塊自己帶底色，**在 PowerPoint 裡移動文字時底色跟著走**，形狀數少四成五。`--cover` 改成每行畫一個獨立色塊矩形、上面疊透明文字方塊。兩個例外：雙色橫幅行一律保留獨立色塊（一個形狀無法承載兩種填色），底色估不出來的行（漸層／照片／插畫區）兩種模式都維持透明。兩者的視覺輸出幾乎相同，取捨見下方「編輯輸出的 PPTX」 |
| `--keep-watermark` | 保留右下角的匯出浮水印（Gemini Notebook／舊版 NotebookLM）|
| `--keep-tiny-text` | 連太小/模糊的圖表內文也轉成文字（預設保留原圖不處理）|
| `--merge-lines` | 相鄰同樣式行合併為一個文字方塊（多段落）|
| `--no-bold` / `--force-bold` | 全域強制細體 / 粗體 |
| `--no-s2t` | 關閉簡體混入修正 |
| `--font "Microsoft YaHei"` | 中文（東亞字元）輸出字型；英文固定為 Arial（大標題 Arial Narrow） |
| `--fast` | 改用 mobile 辨識模型（較快，繁中準確度較低）|
| `--device auto/cpu/dml/cuda` | 推論裝置（預設 auto：依可用性 DirectML > CUDA > CPU）。GPU 約快 4×；首次執行需一次性 shader 編譯（較慢，之後由驅動快取）|
| `--lang` | 指定 RapidOCR 辨識語言（預設中英混合）|
| `--debug` | 輸出每頁 OCR 框疊圖 PNG 與樣式 JSON，供調參；每頁另外印一行 `fixes:`，列出這一頁做過的文字修正（`pangu` 中英之間補空格、`s2tw` 簡體還原、`trailing` 行尾標點復原、`bullet` 行首圓點、`tilt_rescue` 旋轉救援…）。這些修正在輸出的簡報裡看不見（文字就是對的），所以「某一頁怪怪的」的第一步就是看那一頁動過什麼 |

### 編輯輸出的 PPTX

每頁的底圖是整頁的點陣渲染圖，可編輯文字疊在上面、由色塊把底下的點陣字蓋住。這代表**你看到的每一行字，在背景圖裡都還有一份**，只是被蓋住了。日常編輯（改錯字、調字級、換顏色）不受影響，但有一個動作要注意：

> ⚠️ **要拿掉一行文字時，把文字內容清空，不要按 Delete 刪掉整個文字方塊。** 預設的 `--no-cover` 讓底色長在文字方塊上，刪掉方塊等於連色塊一起刪掉，背景圖裡的點陣原字就露出來了 —— 而那是圖片的一部分，之後只能自己補畫一塊色塊去蓋。清空文字則保留形狀與底色，得到乾淨的空白。

其餘差異都對你有利：`--no-cover` 的形狀數比 `--cover` 少約 45%（15 頁的範例簡報：255 vs 463），而且每一行的操作方式一致 —— 在 `--cover` 下有一部分行（雙色橫幅、行內 highlight、弧形）仍然自帶填色，改底色時有的點一下就到、有的要點到下面那層，而外觀看不出是哪一種。兩種模式的視覺輸出幾乎相同（逐像素比對：差異最大的一頁只有 0.22% 的像素差異超過 8 個灰階，全部落在色塊上緣的背景線條）。

## 運作原理

```
PDF 頁面 ──PyMuPDF 渲染(200dpi)──▶ 頁面影像 ─┬─▶ 投影片背景圖
                                             │
                                             ▼
                                   RapidOCR (PP-OCRv5 server)
                                   逐行文字 + 座標框 + 逐字框
                                             │
                                             ▼
                              樣式估計（全部來自影像分析）
                              字級 ← 緊貼字墨高度 / 0.91
                              　　　（中英混合行取逐字 CJK 共識，
                              　　　  拉丁降部不會灌高字級；
                              　　　  同段折行字級自動調和、
                              　　　  同款標題粗體隊列投票；
                              　　　  寬度按 Arial/YaHei 分段量測，
                              　　　  投影片右緣為硬性夾制）
                              粗體 ← YaHei Regular/Bold 模板比對
                              　　　（同字墨高 + 模擬升頻模糊 +
                              　　　  對比度相對切割，≥16pt 適用）
                              底色 ← 框外環帶 + 光暈/膠囊/緞帶判別
                              　　　（光暈往外走到顏色穩定才採信，
                              　　　  文字投影不會被當成表面色）
                              文字色 ← 筆畫核心（離底色最遠的 30% 像素）
                              多色行 ← 逐字取色分段
                                             │
                                             ▼
                              python-pptx 輸出
                              背景圖 + 實心色塊 + 可編輯文字方塊
```

## 驗證

倉庫附有比對工具，可把轉換結果與參考 PPTX 做文字召回率比對：

```bash
uv run python tools/compare_pptx.py generated.pptx reference.pptx
```

在 15 頁的範例簡報上，文字召回率 100%。

## 已知限制

- 粗體判定：≥24pt 一律視為粗體；16–20pt 以「該行文字的 YaHei Regular/Bold 渲染模板」比對筆畫寬決定（吸收字級、字元內容、白字深底對比的系統差）；14pt 以下來源模糊已抹掉字重訊號，僅在筆畫極端時判粗
- 模板比對需要本機有 `msyh.ttc` 與 `msyhbd.ttc`（Windows 內建）；缺檔時自動退回筆畫門檻規則
- 某一頁處理失敗時，**只有那一頁降級，其餘照常轉完**：底圖已經渲染出來的話那一頁仍會進簡報，只是沒有可編輯文字（連渲染都失敗的頁才會整頁不進去，因為空白頁會讓後面的頁碼位移）。降級的頁碼會列在最後一行 `WARNING:`，完整的例外堆疊在同一份紀錄裡
- 同一行中英混排只使用單一字級
- 弧形文字以 3–6 段切線文字方塊近似（各段可分別編輯，段間可能有微小空隙）
- 色塊預設由文字方塊自帶（`--no-cover`），移動文字時底色跟著走；`--cover` 改成畫獨立矩形、上面疊透明文字方塊。兩種模式下**同列／堆疊裁切都照常執行**（那是幾何修正，不是色塊機制），雙色橫幅也一律保留獨立色塊。漸層或照片背景上估不出單一底色的行，兩種模式都維持透明疊圖 — 這類頁面（如電路球上的深字白暈）仍可能出現點陣原字與可編輯文字的重影，換模式幫不上忙
- 插圖內過小/模糊的文字預設不轉換（保留在背景圖中、不可編輯）；用 `tools/compare_pptx.py` 與未過濾的參考檔比對時，這些行會列為 MISS，屬預期行為
- 插圖上交疊的斜排裝飾字（書封、告示牌）整組保留原圖、不轉文字
- 來源字型的拉丁字較 Arial 窄約 14%：大標題以 Arial Narrow 吸收差距，內文極端緊湊時可能以少量超寬換取正確字級（懸崖防護）
