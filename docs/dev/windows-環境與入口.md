# Windows 環境、相依鎖定與四個入口（實作細節）

> ⚠️ **動到相依版本、`.bat`／`.vbs`、字型檔路徑，或 GUI 的選項清單之前請先讀這一份。**
>
> 決策層級的那幾句在 `docs/spec/09-執行環境與效能.md`（為什麼要有 GPU build、為什麼要留一個有主控台的入口、字型為什麼是這一套）；這一份放**綁死 Windows／Python／這幾個函式庫**的細節。啟動與錯誤留底的實作在 `docs/dev/gui-啟動與錯誤留底.md`。

## 1. 相依鎖定：兩個會靜默壞掉的地方

環境由 `uv` 管，`pyproject.toml` 宣告、`uv.lock` 鎖版本。兩條**不可以放寬**的約束，理由都寫在 `pyproject.toml` 的註解裡。

### `onnxruntime-directml`，不是 `onnxruntime`

DirectML 版是「**取代**」CPU 版的完整 build（它同時提供 `CPUExecutionProvider`），裝了 CPU 版就**沒有 GPU**。兩個套件同時存在時匯入哪一個是未定義的，所以是取代不是並存。

⚠️ 這件事**不會當場發現**：DirectML **首次**執行要付一次性的驅動 shader 編譯（實測該次約 213s，看起來與 CPU 同速），編譯結果由 Intel 驅動存碟快取，第二次起才看得到加速。所以裝錯的症狀是「一直慢 4 倍」而不是「壞掉」。我們自己差點因為首跑數據下錯「GPU 沒用」的結論。

實測 Intel Arc 140V：**DirectML 全份 50s vs CPU 210s（快 4.2×）**。

### `rapidocr>=3.8,<3.9`

3.9.2 改掉了模型設定的 API，本專案的參數在它上面直接 `ValueError: Invalid OCR configuration.`（2026-08-23 用 `uv` 建環境時實際撞到）。

3.8.2 → 3.8.4 是安全的，而且更準：`Transformer_演進地圖` 全跑 288 行只差 1 行——`Caping` 被修正成 `Capping`。

### 效能雜項

`_dominant_color` 是全 pipeline 最熱的 helper，每行呼叫 6–10 次；改用 `bincount` 後快 9.3×（900 個真實裁切驗證輸出相同）。樣式估計 56 頁 1249 行由 59.5s 降到 39.2s（2026-08-23 的 `/simplify`，−34%）。

**量過而否決**：`rec_batch_num` 加大反而變慢（16: 0.98s vs 6: 0.80s/頁），維持預設。

## 2. 字型檔與量測

| 用途 | 檔案 |
| --- | --- |
| 寬度量測（預設） | `C:\Windows\Fonts\msyh.ttc` |
| 純拉丁且 ≥3 字的行 | `arial.ttf` |
| 出生估字級 ≥28 的行，其拉丁段 | `ARIALN.TTF`（與輸出的 Arial Narrow 一致） |
| 備援中文字型 | `%LOCALAPPDATA%\Microsoft\Windows\Fonts\` 下的 Noto Sans TC |

每個 run 同時設 `<a:latin>` 與 `<a:ea>`，PowerPoint 按字元類別自動選用，**中英混排同一行雙字型、不需拆 run**。

⚠️ 兩個不可改的細節：**2 字短串**的寬度夾制騎在 snap 平手點上（曾把 p8「98」籌片從 20pt 推成 24pt 粗體），所以短串維持原規則；`_cjk_band_height` 的單字映射**一律維持 YaHei 度量**。

## 3. 主控台與 shell

- Windows 11、Python 3.14；主控台是 **cp950**。印中文的腳本需要 `python -X utf8`（`cli.py` 自己會重設 stdout）。
- PowerShell 會吃掉 `python -c` 單行指令中的雙引號；這類情況改用 Bash 工具或腳本檔。**git commit 訊息中的雙引號也會被截斷**——訊息避免使用雙引號。
- `.bat` 與 `.vbs` 是唯二不用 UTF-8 的檔案：**cp950（Big5）、CRLF、無 BOM**，`.bat` 開頭（任何中文之前）還必須 `chcp 950 >nul`。
- ⚠️ 自己跑完 `.bat` 之後，同一次呼叫的最後一行必須還原 `chcp 65001`——**`chcp` 改的是主控台不是行程**，不還原會讓使用者畫面整片亂碼。
- `.vbs` 沒有 `chcp` 這回事：`wscript` 用系統 ANSI codepage 讀檔，所以編碼要對，但**不需要也不能**下 `chcp`。
- ⚠️ **cp950 編不出 `U+26A0`（⚠）**：`.bat`／`.vbs` 的註解不能用這個 repo 慣用的警告符號，改寫「【注意】」。中文、破折號、全形括號、`→` 都編得出來，只有這一個字會在寫檔當下丟 `UnicodeEncodeError`。

| 檔案 | 做什麼 |

| `啟動.vbs` | 開圖形介面，**不開黑視窗**（使用者 2026-08-24 要求；平常用這個） |

⚠️ **圖形介面每次啟動會在 `logs` 底下寫一份執行紀錄**（檔名是啟動時間＋pid，保留 30 天）；`啟動.vbs` 在程式沒能正常結束時**當場把攔到的訊息跳訊息框**、不落檔（專案資料夾裡沒有 `啟動.log` 這個東西了）。細節見 `docs/dev/gui-啟動與錯誤留底.md`。

⚠️ **`安裝.bat` 在 `uv sync` 之後會真的 import 一次**（`import pdf2ppt.cli`，0.3s，會拉到 numpy／pymupdf／python-pptx／Pillow）：`uv sync` 成功不等於跑得起來——Python 被防毒隔離、uv 的 trampoline 生不出子行程，都是「安裝看似成功、雙擊啟動卻沒反應」。那種事要在安裝當下就講，不要等使用者雙擊「啟動.vbs」才發現，那時他已經不知道該回頭做什麼了。⚠️ **不可改成 `import pdf2ppt`**（那是空的 `__init__.py`，什麼都驗不到），也**不要**扯進 rapidocr（它的模型是第一次轉檔才下載的）。

## 5. GUI 只露出五個選項（其餘吃 cli.py 的預設值）

⚠️ **`pdf2ppt_gui_2.py` 的選項清單是手抄 `cli.py` 的 argparse 定義**，已經漂移過一次（`--lang` 在 CLI 與 README 都有、GUI 完全沒有，2026-08-16 補上）。現在由 `tests/test_docs.py` 釘著。

⚠️ **2026-08-25 使用者指示把選項砍到五個**：頁碼（`--pages`）、保留浮水印（`--keep-watermark`）、關閉簡體混入修正（`--no-s2t`）、色塊獨立畫成矩形（`--cover`）、保留圖表內小字（`--keep-tiny-text`）。理由是原話——**其餘那些「如果改變，會讓結果影響很大，或根本就用不到」**：`--dpi`／`--font`／`--min-score` 是校準值（200 DPI ＋ YaHei 是整條管線唯一校準過的作業點）、`--no-bold`／`--force-bold`／`--fast` 會整份換掉粗體與辨識的判別依據、`--device` 有 auto、`--lang` 預設就是中英、`--merge-lines` 與 `--debug` 是開發用的。

⚠️ 沒露出來的旗標**連變數都不留、也不再傳**，直接吃 argparse 的預設值。舊版是在 `_build_vars()` 手抄一份預設值（`dpi=200`、`min_score=0.5`、`device="auto"`、`font=FONT_CHOICES[0]`）再在 `_build_argv()` 原封不動傳回去——值沒變，但 `cli.py` 改預設時 GUI 會安靜地把舊值釘住。**一起刪掉的殘骸**：`FONT_CHOICES`、`self.lang`／`font`／`device`／`dpi`／`min_score`／`bold_mode`／`fast`／`merge_lines`／`debug` 九個變數，以及「進階開關」那個 `LabelFrame`（`adv_frame`，剩五項還分兩區只是讓一件小事看起來像兩件事）。

⚠️ **測試的述詞跟著換，但守備範圍不可以縮**：`test_every_cli_flag_has_a_gui_control` 從「每個旗標都要有控制項」改成**雙向釘**——露出來的五個必須真的在 GUI 裡，而**沒露出來的每一個都要在 `hidden` 名單上**。`cli.py` 新增旗標時它就會紅一次，逼人回答「這個要不要給使用者看」；少了後半，這支測試會退化成「那五個還在嗎」，新旗標可以整個被忘掉。

⚠️ 版面上刻意偏離的只有一件事（使用者 2026-08-23／08-24 指示）：**主畫面一個選項都不露出來**，只留輸入／輸出檔，那五個全部收進預設收合的「轉檔選項」區（`_toggle_advanced`）——日常轉檔一項都不必動，攤在主畫面上只是擋住主線。

**2026-08-25 使用者又指示了三件事**（都在 `_build_ui`／`_toggle_advanced` 一帶）：

1. **「開始轉檔」排到收合按鈕之上**、緊接檔案區底下。主線是「選檔 → 按下去」，把終點排在一個日常不必碰的東西後面等於把主線切斷；展開進階區時它還會被推到很下面。連帶：展開的兩區改插進收合按鈕正下方的空槽 `adv_slot`（2026-08-25 傍晚以前是 `before=self.progress`，那條進度條後來併進了動作列、`before` 的目標也就沒了）。
2. **主要動作按鈕要明顯**：藍底白字的實心鈕。⚠️ 這一項當天做了兩版——先用 `tk.Button` 自己塗色（因為 Windows 的 vista 佈景把 `ttk.Button` 的底交給原生主題畫，`style.configure(background=…)` 完全沒有效果），換上 Sun Valley 佈景之後改成佈景自己的 **`Accent.TButton`**（`Run.Accent.TButton` 只加大字級與內距）。⚠️ 樣式名**必須以 `.Accent.TButton` 結尾**才繼承得到那組圖片元件；鎖／解鎖也因此瘦成一行 `state()`（`_refresh_run_button`），hover／pressed／disabled 全部由佈景畫。
3. **收合要把高度還回去**。原本是「只長不縮」；2026-08-25 先改成「記下展開前實際量到的高度再還原」（`_restore_height_after_collapse`），當天傍晚整批重整版面時再併成 `_fit_window()`——**每次都重新量 `reqheight`**，算式裡沒有減法，也就沒有「視窗管理員夾掉幾像素、按幾次愈長愈高」那個坑要躲。⚠️ 那個判斷仍然留著：使用者自己拉過視窗（與 `_auto_h` 差 >8px）就只長不縮。

**2026-08-25 傍晚整批重整（§5.4）**：拖放、進度條、結果列、手風琴、停止鈕。

### 沒有「選擇專案資料夾…」這件事了（2026-08-25）

使用者當天指示「UI 上有專案位置的選擇，這個請拿掉，預設目錄下應該就有，如果預設目錄讀不到，就出現錯誤訊息，程式不啟動」。決策層的理由寫在 `docs/spec/09-執行環境與效能.md` §9.7，這裡記形狀與**一起清掉的殘骸**：

- `PROJECT_DIR = Path(__file__).resolve().parent`，模組層級一個常數，**沒有第二個候選**。`APP_ICON`、`log_dir()`、`_git_sha()`、版號讀的 `pyproject.toml` 全部改成從它出發（本來各自寫一次 `Path(__file__).resolve().parent`）。
- 驗證放在 `main()`、**在 `App()` 之前**：`is_project_dir(PROJECT_DIR)` 不過就呼叫 `fail_no_project()` 然後 `return 2`，視窗完全不建。
- `fail_no_project()` 的訊息有兩個落點：`messagebox.showerror`（自己起一個 withdraw 掉的 `tk.Tk()`，因為此刻還沒有主視窗）＋ `sys.stderr`。對話框是給雙擊「啟動.vbs」的人看的（那條路沒有主控台）；stderr 是給從終端機跑的人、**以及對話框跳不出來時**看的。⚠️ `tk.Tk()` 起不來也要吞掉例外，否則錯誤訊息本身變成 traceback。
- ⚠️ **只讓使用者看到一個框**（使用者 2026-08-25 追加指示）：`.vbs` 本來在結束碼非 0 時會把攔到的 stderr 再跳一次，於是同一件事說兩遍。改法是一個雙方講好的暗號——`fail_no_project()` **回傳訊息框有沒有真的跳出來**，`main()` 據此回 `SELF_REPORTED_RC`(78) 或 1；`.vbs` 收到 78 就 `Cleanup` 後 `WScript.Quit rc`，安靜收工但結束碼照傳。⚠️ **暗號不可以是 1 或 2**：`1` 是未攔到的例外，**`2` 是直譯器連 `.py` 都打不開**（只複製了 `.vbs`、GUI 檔不在的情況）——撞上去就會把那次最需要跳框的失敗靜靜吞掉。78 是 sysexits 的 `EX_CONFIG`，uv 與 Python 都不會回。⚠️ **也不可以無條件回 78**：Tk 起不來的機器上那等於什麼都沒說，所以「跳不出來就回 1」那一半是這條規則的另一半。兩個常數由 `tests/test_docs.py::test_the_self_reported_exit_code_matches_the_launcher` 釘著。
- **跟著刪掉的殘骸**（位置固定之後它們在定義上不會再被用到）：`~/.notebooklm_pdf2ppt_gui.json` 這個設定檔與 `load_config()`／`save_config()`（它只存過 `project_dir` 一個鍵，連同 `import json` 一起沒了）、`find_project_dir()` 的三段 fallback、`App.project_dir`／`App.loaded_from`、`_refresh_project_label()`／`_pick_project()`、`_run_conversion()` 裡「換過資料夾就把 `sys.modules` 裡的 `pdf2ppt` 清掉」那一段，以及 `_start()` 開頭的位置檢查。⚠️ **`_run_conversion()` 的 `ModuleNotFoundError` 分流要留著**：`pdf2ppt` 自己不見了（啟動後才被搬走）與缺相依套件（沒跑 `uv sync`）的處方不同。
- 版面連帶：主畫面第一個區塊從「專案位置」變成「檔案」，多出來的高度落給日誌區（`geometry` 的 760×640 沒有跟著改）。

## 5.1 外觀：DPI、字型、佈景（2026-08-25）

使用者當天回報「UI 字體有鋸齒狀」、要求介面全部改用 **Microsoft JhengHei UI**，並問「有沒有其他 Theme 可以選」、能不能改成 [WinUI 3](https://learn.microsoft.com/zh-tw/windows/apps/winui/winui3/)。三件事分開處理：

**① 鋸齒的成因不是字型，是 DPI。** 本機顯示縮放 150%，而 Tk 行程預設**不是 DPI-aware**：Windows 讓它以 96dpi 畫完整個視窗，再**點陣放大** 1.5 倍貼上去，所有筆畫因此糊掉。修法是 `enable_dpi_awareness()`（`SetProcessDpiAwareness(1)`，⚠️ **必須在建 Tk 之前**，Tk 只在啟動時問一次 DPI）。實測 `winfo fpixels 1i` 95.9 → 143.9、螢幕 1707×960 → 2560×1440。⚠️ **連帶代價**：點數指定的字型會自己換算，**寫死的像素不會**——`geometry`、`padx`、`wraplength` 全部要過 `App.px()`，漏一個就在 150% 下縮成 2/3。另外本機的 `TkDefaultFont` 本來就已經是 Microsoft JhengHei UI，所以「換字型」本身治不了鋸齒。

**② 字型走 Tk 的具名字型**（`TkDefaultFont`／`TkTextFont`／…）：ttk 控制項預設就吃這幾個，改一次全部跟著換。⚠️ 連 `TkFixedFont` 與日誌區的 `Consolas` 都換掉了（使用者說「全部的字體」）——代價是日誌區不再等寬，`tqdm` 之類的欄位對齊會鬆掉；要換回等寬只需改 `_build_ui` 裡日誌 `tk.Text` 的 `font=`。⚠️ 佈景自帶的 `SunValley*Font` 是 **Segoe UI Variable + 像素單位**（`-14`），既不是使用者要的字型、在 DPI-aware 的 150% 下也小一號，所以一併改成我們的家族名 + 點數。

⚠️ **介面字型與輸出字型是兩回事、不可互相「順手統一」**：`UI_FONT`（Microsoft JhengHei UI）只管介面自己的字，`--font`（預設 Microsoft YaHei）是**寫進 PPTX 的東亞字型**——`style.py` 的 `_measure_em()` 固定載入 `msyh.ttc` 量寬度，整套寬度夾制、snap 與標題足跡門檻都照 YaHei 校準，換掉它不會跟著換度量衡。兩個名字長得像、住在同一支檔案裡，是這個專案最容易被「統一」掉的一對。

**③ 佈景：`sv-ttk`（Sun Valley）**，一套模仿 Windows 11 Fluent／WinUI 的 ttk 佈景（圓角、細框線、Fluent 輸入框、亮／暗兩套，MIT，純 Tcl+PNG 約 100KB）。內建可選的只有 `winnative / clam / alt / default / classic / vista / xpnative`——其中只有 `clam` 吃得下自訂配色（vista/winnative 的控制項是原生主題畫的），而手工調 clam 只能做到「乾淨」，做不出圓角（圓角要圖片元件）。亮／暗跟隨 Windows 的「應用程式模式」（`preferred_theme_mode()` 直接讀 registry 的 `AppsUseLightTheme`，不為了一個值加 `darkdetect` 依賴），`NOTEBOOKLM_PDF2PPT_THEME=light|dark` 可覆寫；深色時連標題列也用 DWM 屬性 20 一起變深。

⚠️ **切完佈景要自己補一發 `<<ThemeChanged>>`，而且要先 `update_idletasks()`**：sv-ttk 的顏色不寫在佈景定義裡，而是掛在該事件上的 `configure_colors` 設的，Tk 8.6.15 在 `ttk::style theme use` 時**不會**把事件送到根視窗。實測 `ttk::style configure .` 在 `set_theme()` 之後仍是空字串；只補 `event_generate`（`tail` 或 `now` 都一樣）也沒用，**視窗還沒實體化前那個 class binding 根本不會觸發**——補上 `update_idletasks()` 兩者才成立。症狀非常好認：深色模式下一堆**白底黑字的標籤**散在深色視窗上（那是母佈景 clam 的預設灰）。

⚠️ **沒有 `sv_ttk` 也必須開得起來**：`apply_ui_style` 的 `except` 會留在系統原生佈景、只換字型。GUI 是使用者的主要入口，為了外觀讓它開不了完全不划算（測法：`sys.modules["sv_ttk"] = None` 再開一次）。

### 為什麼不是真的 WinUI 3

使用者問了兩次（[microsoft-ui-xaml](https://github.com/microsoft/microsoft-ui-xaml)、[sotanakamura/winui-python](https://github.com/sotanakamura/winui-python)）。WinUI 3 是 C++/C#/XAML 的原生框架（WinAppSDK），**Tk 的視窗裡放不進 XAML 控制項**，所以「改成 WinUI 3」等於換掉整個前端，三條路的代價：

| 路 | 代價 | 換到什麼 |
| --- | --- | --- |
| 現況：Tk + Sun Valley | 一個 100KB 的 MIT 依賴，程式碼零改寫 | 很像 Win11 的外觀（圓角、Fluent 控制項、亮暗自動） |
| `winui-python`（`win32more`） | 使用者機器要另外裝 **Windows App Runtime**；UI 全部改寫成 XAML；背景執行緒要改走 `DispatcherQueue`；那個 repo 是 **16 個 commit 的範例集**，不是框架 | 真的 WinUI 3 控制項、Mica 背景 |
| PySide6 + Fluent widgets | 約 150MB 依賴 + 前端全改寫 | 很接近 WinUI 的外觀，但仍不是 WinUI |

⚠️ 第二條的**風險落點是啟動**：這支 GUI 的價值有一半在「雙擊就開、出事有 log」（`啟動.vbs`、`logs\<時間>-<pid>.log`、訊息框留底），而多一個必須預先安裝的執行階段正好打在那裡。要走這條路的話，先做一個**只有一個視窗、一顆按鈕**的 PoC 確認 Runtime 在使用者機器上裝得起來，再談移植。

**預設值現在三方一致**（2026-08-24 起）。曾經不一致的只有色塊那一項：2026-08-23 到 08-24 之間它是主畫面上唯一的核取方塊、且刻意與 `cli.py` 相反（使用者要拿它做 A/B，看「只有文字方塊帶底色」在 PowerPoint 裡的可編輯性）；量完之後 `cli.py` 的預設改成 `--no-cover`（理由與完整量測見 `docs/spec/06-流程-顏色、蓋板與裁切.md` §6.4），GUI 那一項也收進進階區。

⚠️ **GUI 存的是反向旗標**：進階區那一格叫「色塊獨立畫成矩形」、對應 `self.cover`、預設不勾，勾了才送 `--cover`。所以 `tests/test_docs.py` 的三方一致例外清單是 `{"--no-cover", "--output"}`——`--no-cover` 是預設值、GUI 不需要它的字面。測試只檢查旗標有沒有對應控制項，**預設值本身沒有機器守得住**，改 `cli.py` 的預設時要自己回頭看這一段。

## 5.2 應用程式圖示（2026-08-25）

`assets/` 底下那一組（`icon.svg`／`icon-small.svg`／`icon-mark.svg`／`icon.ico`／兩張 PNG）**全部是 `tools/make_icon.py` 的產物**，幾何與色票的唯一真值在那支腳本裡。改顏色或比例的作法是改腳本、重跑 `uv run python tools/make_icon.py`，然後把 `assets/` 一起提交——不要單獨手改 SVG，下一次重跑就被蓋掉了。

**立意是 OCR 的定義本身：把光學影像認成字元。** 藍色圓角磚，四個白色取景角框住一個白色的「文」。取景角是辨識的通用符號、在 16px 也認得出來；框住的東西刻意是**一個繁體字**而不是拉丁字母，因為這個專案整套是為繁中調的（PP-OCRv5 server 辨識模型、s2tw、頁面詞彙校正）。

### 「文」是量出來的，不是畫出來的

⚠️ **憑感覺畫會變成「女」**——第一版就是，使用者當場指出。文與女的差別**不在撇捺的形狀**（兩個都是交叉的兩筆），而在三件事：

| | 文 | 女 |
| --- | --- | --- |
| 點 | 有 | 沒有 |
| 橫 | 在撇捺**之上**，不穿過它們 | **穿過**撇捺 |
| 交叉點 | 在橫**之下**，字身約 59% | 在橫**之上** |

第一版把橫畫在 y=210、交叉點落在 y=313（77%），三條全踩，於是整個字讀成「女」。

現在的骨架是**從 `msyhbd.ttc` 的「文」量出來的**：把真字形縮進字身框 (160,138)-(352,362)、逐列取墨水游程中心當骨架，撇捺做三次貝茲最小平方擬合（殘差 3px）。量到的數字寫在 `WEN_SKELETON`：橫在 y 173..203（厚 31、近滿寬），撇捺從橫的正下方 y=204 出發，**交叉點 y≈291**。⚠️ 要重畫的話，做法是**重跑那個量測**（把真字形與手畫的疊圖比對），不是改座標試到看起來順眼——「看起來順眼」正是第一版失敗的方式。

⚠️ **點與橫之間要留得開**：點的圓端加上橫的半筆寬很容易吃掉那道縫，黏起來就少掉判別特徵①。

⚠️ **16–32 px 另有一版簡化圖形**（`icon-small.svg`：取景角臂變短、筆畫加粗到 44–46）。滿版那版的筆畫是 30/512，換算下來 16 px 只剩 0.9 px，整個字會斷掉。`.ico` 裡 ≤`SMALL_MAX`(32) 的四個尺寸一律取簡化版。

### 上一版的殘骸與教訓

2026-08-25 稍早有過一版**「NotebookLM 的弧 + 一張投影片」**（取自使用者提供的 `notebook-logo.svg`），同一天被這個 OCR 立意取代。留一條可重用的教訓：⚠️ **一道弧的兩隻腳只要露在方塊兩側，整張圖就會讀成一把掛鎖**（當時排 10 個變體目視，露腳的 5 個全中）。⚠️ 另外，**不可直接沿用 NotebookLM 的商標圖形**——那一版是刻意改成對稱同心、換掉色票才用的；現在這版已經完全不含那個語彙。

### 工作列那顆圖示走的是另一條路（AppUserModelID）

⚠️ **標題列的圖示對了，不代表工作列那顆也對**。使用者 2026-08-25 回報「工作列上的 ICON 不是我設計的」，實際看到的是 **wscript 的圖示**。兩顆的來源不同：

| | 來源 |
| --- | --- |
| 標題列 / Alt-Tab | 視窗的 `WM_SETICON` —— `iconbitmap` 設的就是它 |
| **工作列按鈕** | 先把視窗歸到某個 **AppUserModelID**，再用**那個身分**的圖示 |

行程沒有自己宣告身分時，Windows 會沿用啟動鏈上游的執行檔，而這條鏈是「捷徑 → `wscript.exe` → `cmd` → `uv` → `pythonw`」，於是拿到 wscript 的圖示。

修法有**兩半，缺一半就只修好一半**：

1. **行程端**：`pdf2ppt_gui_2.py` 的 `set_app_user_model_id()` 呼叫 `SetCurrentProcessExplicitAppUserModelID(APP_ID)`。⚠️ **必須在建立第一個視窗之前**（和 `enable_dpi_awareness()` 一樣）——視窗一建出來就已經被工作列歸隊了。
2. **捷徑端**：`.lnk` 也要寫上同一個 `PKEY_AppUserModel_ID`（`tools/make_shortcut.py` 的 `IPropertyStore` 那一段）。少了這一半，使用者把捷徑**釘到工作列**之後，釘的那顆（身分從 `wscript.exe` 推出來）與執行中的視窗（身分是我們宣告的）會變成**兩個各自獨立的按鈕**。

⚠️ **那個字串只有一份**：寫在 GUI 的 `APP_ID`，`make_shortcut.py` 用正規表示式讀走（作法同 `app_name()`）。兩邊不一致就是上面那個「兩顆按鈕」的症狀，而且不會有任何錯誤訊息。

⚠️ **不要找 `InitPropVariantFromString`**：那是 `propvarutil.h` 的 **inline** 函式，`propsys.dll` 沒有匯出這個符號（2026-08-25 實測 `not found`）。`_PROPVARIANT` 是自己排的，⚠️ **尾巴那個 `pad` 欄位不可省**——真正的 PROPVARIANT 是 24 bytes（x64），而 `PropVariantClear` 會把整個結構清成零，宣告短了就是寫出界。字串要用 `CoTaskMemAlloc` 配置（`PropVariantClear` 負責收），⚠️ 而 `CoTaskMemAlloc.restype` 一定要設成 `c_void_p`，否則 x64 上回傳值會被截成 32 位元。

驗收方式（不要靠截圖，那會截到使用者的實機桌面而且不可靠）：`GetCurrentProcessExplicitAppUserModelID` 讀回行程那一邊，`IPropertyStore::GetValue` 讀回 `.lnk` 那一邊，兩個字串要相同。

### `.ico` 與 GUI 端

`.ico` 是**自己組容器**寫出來的（`build_ico`）：Pillow 的 `sizes=` 只會把同一張圖縮放，承載不了「小尺寸換一套圖形」這件事。256 用 PNG 承載、其餘用 DIB，⚠️ DIB 的兩段點陣都是**由下往上**存、AND 遮罩每列要補齊到 4 位元組——遮罩全零（＝全部不透明）的話圓角磚在 Windows 上會露出方角。驗收方式是 `PIL.Image.open(...).ico.sizes()` 讀得回八個尺寸，加上 `tk.Tk().iconbitmap()` 真的吃得下去。

GUI 端在 `pdf2ppt_gui_2.py` 的 `App._apply_window_icon()`。⚠️ 兩個點：路徑以 `PROJECT_DIR`（＝`Path(__file__)` 所在資料夾）為基準而不是 cwd（`啟動.vbs`／捷徑進來時工作目錄不一定對）；失敗一律吞掉（圖示是純外觀，`assets` 不在就讓它沒有圖示，不該讓程式開不起來——`啟動.vbs` 藏著主控台，那會變成「雙擊沒反應」）。`iconbitmap(default=…)` 的 `default=` 不能省，少了它 filedialog／messagebox 那些之後才建的 Toplevel 換不到。

## 5.3 桌面與「開始」功能表的捷徑（2026-08-25）

`tools/make_shortcut.py`，由「安裝.bat」在環境驗過之後呼叫；資料夾搬過位置要重建就直接跑 `uv run python tools/make_shortcut.py`。作法整體移植自姊妹專案 `meeting-scribe` 裡同名的那支腳本（在它的 `scripts` 底下，不是本 repo 的路徑），**但有一處關鍵差異**，見下。

⚠️ **捷徑指的是 `wscript.exe`，`啟動.vbs` 當參數 —— 不是直接指 `.vbs`**。這就是與 `meeting-scribe` 的差異：那邊的入口是 `啟動.bat`，直接指就好；`.vbs` 當捷徑目標有兩個坑，都會讓「雙擊桌面圖示」與「雙擊 `啟動.vbs`」表現不一致：

1. **副檔名關聯被改掉**——不少公司把 `.vbs` 關聯到記事本當防毒措施，那時捷徑會打開原始碼而不是執行。
2. **預設主機若是 `cscript` 就會蹦出黑視窗**，而那正是 `啟動.vbs` 存在的唯一理由（`docs/dev/gui-啟動與錯誤留底.md`）。

把主機釘成 `wscript.exe`、`.vbs` 當參數，兩個都繞開了。找不到 `wscript.exe` 才退回直接指 `.vbs`。

⚠️ **三段路徑一段都不可以寫死**（啟動器、工作目錄、圖示）：使用者換電腦的方式是複製整個專案資料夾，寫死的那條在別台機器上就是一顆指向不存在路徑的死圖示，**比沒有更糟**。全部從腳本自己的 `__file__` 往上推。同名一律覆寫——「搬過位置就重跑安裝.bat」那句話要成立，就得真的把舊捷徑改回來。

⚠️ **桌面路徑不可以用 `~/Desktop` 猜**：OneDrive 的「資料夾備份」會把桌面整個重導到 `%USERPROFILE%\OneDrive\Desktop`，而寫死的那條往往還在、只是沒人看——捷徑建立成功，使用者卻永遠看不到。先用 `SHGetKnownFolderPath` 問 Windows，問不到才退回猜。

⚠️ **不叫 PowerShell 的 `WScript.Shell`**：`.lnk` 在 Windows 上只有 COM 一條路，而 PowerShell 正是公司電腦最常被群組原則收走的東西（執行原則、Constrained Language Mode 都擋得掉）。改用 ctypes 直接叫 `IShellLinkW`，不經過任何外部行程、也不必為一顆捷徑多拉一個相依。⚠️ vtable 是照**順序**呼叫的（`_SET_PATH`=20、`_SET_ARGUMENTS`=11…），數錯一格是當場 crash 不是回錯誤碼，所以介面宣告整段抄在原始碼的註解裡對照。

⚠️ **中文不從 .bat 傳進來**：批次檔是 cp950，字串經 cmd 那一層會被重新編碼。捷徑名稱與所有訊息都寫在那支 UTF-8 的 Python 裡，「安裝.bat」只負責呼叫一行**純 ASCII** 的指令。捷徑名字本身是**從 `pdf2ppt_gui_2.py` 的 `APP_TITLE` 讀正規表示式抓出來的**（不是 import，那會拉進 tkinter；也不是寫死，那會漂移成桌面圖示叫舊名字）。

⚠️ **建不出來絕不能擋住安裝**：走到那一步環境已經好了。桌面被群組原則重導到唯讀網路磁碟、OneDrive 沒登入、資安軟體擋寫入都會失敗，那時該講的是「雙擊資料夾裡的啟動.vbs 一樣能用」。離開碼只拿來讓「安裝.bat」挑最後那句話怎麼寫，**0 與 3 都算安裝成功**。

## 5.4 版面與進度回饋的整批重整（2026-08-25 傍晚）

使用者說「UI 擺放的設計不太好，看能否改善 UX」，逐條量過之後一次做完。**量到的兩個事實**是整批改動的起點（在 2560×1440@150% 上以 `PrintWindow` 截圖 + `winfo_reqheight` 量的）：

- **閒置時 51% 的視窗是空的**：762×671 邏輯 px 的視窗裡，檔案區＋開始轉檔只佔 187px（28%），底下那個還沒有內容的日誌框佔 342px。
- **展開進階區就超出螢幕**：展開後 `reqheight` = 953 邏輯 px，本機工作區只有 912；1080p@125% 的筆電工作區約 810，會差 140px 以上——日誌區與進度條被推到工作列底下。

### 手風琴：兩區不同時攤開

`_set_advanced()` / `_set_log_shown()` 互斥：展開進階就收日誌、按下轉檔就收進階並展開日誌。實測三個狀態的 `reqheight`（實體 px @150%）：閒置 462、進階展開 1128、執行中 746，工作區 1368 —— 全部塞得進去（⚠️ 這三個數字在 2026-08-25 晚的間距尺規之後變了，現值見 §5.5；手風琴的結論沒變）。高度一律由 `_fit_window()` 決定（見 §5 第 3 點）。

⚠️ **小螢幕上仍有可能鉗不下**（進階展開需要 752 邏輯 px，1366×768 的筆電工作區只有約 700）。鉗高度時被裁掉的是**最後 pack 的那幾個**，也就是底部的「詳細訊息」那一列；收合進階區就會回來。要根治得把進階區包進可捲動 canvas，那是下一個人的事——**別忘了先量**，不要憑感覺加。

⚠️ **`ttk.Frame` 空掉之後不會自己縮回去**（這一輪踩到、症狀最難認的一個）：容器**最後一個** slave 被 `pack_forget()` 之後，容器自己的 requested size **不會**回到 1x1——geometry manager 只在「還有 slave 可以算」時才更新它。實測收合進階區之後畫面正中央留下一塊 **667px 的空白**，而 `pack_slaves()` 是空的、子控制項 `winfo_ismapped()` 也確實是 0：**每一個「這東西在不在」的檢查都說沒事，版面卻是壞的**。當時的修法是一支 `_collapse_slot()`——沒有 slave 時 `configure(height=1)` 說得算，再 pack 進 slave 就恢復自動計算（實測 1 → 58 → 1 → 58），兩個槽都要（`adv_slot`、`result_slot`）。⚠️ **2026-08-26 那支函式連同兩個空槽一起刪掉了**（見 §5.10）：收合全部改用 `grid_remove()`，而這個坑**只發生在 pack 的容器**——grid 會把整列從高度計算裡拿掉，在定義上就不會發生。⚠️ 記述留著是因為**這是一個下次還會踩到的 Tk 行為**，不是因為那支函式還在。

### 進度：從 cli 的 stdout 解析

動作列現在是**同一列**的〔開始／停止鈕〕〔進度條〕〔狀態字〕。舊版是右上角一個「就緒」、版面中段一條 indeterminate 進度條、最下面一大塊日誌——三個東西講同一件事卻散在 900px 內。

⚠️ **狀態字那一欄的寬度要釘住，但要用量的不要用猜的**（使用者 2026-08-25 截圖圈出進度條右邊那塊空白）。釘住是必要的：不釘的話欄寬會跟著字串長短變，進度條的右端就在「就緒」與「載入 OCR 引擎…」之間左右抽動。但**以字元數寫死（`width=20`）在中英混排的狀態字上一定不準**——Tk 的 `width` 單位是該字型 `0` 的寬度，而表意字約兩倍寬、`…` 又不到一倍，只能往寬的猜。改成拿 `STATUS_SAMPLES` 實際去 `measure()`（`_status_width`）再設 `columnconfigure(minsize=…)`：實測保留 240px → 149px，**進度條多拿 91 實體 px**，而十個狀態字下進度條寬度全部是 677，一格都不抖。⚠️ 新增狀態字時要一併加進那份名單，否則那一個會把欄位撐開、進度條當場縮一截。

`_scan_line()` 認三種行（`_PAGE_RE`／`_WARN_PREFIX`／`_LOADING_PREFIX`，`tests/test_docs.py::test_the_gui_reads_the_words_cli_actually_prints` 釘著兩邊的字面值）：

- `page 7 (3/15)` → 切成 determinate、更新頁數。⚠️ **在此之前一定是 indeterminate**：載入引擎（首次還要下載 90MB 模型）那段沒有頁數可報，畫一條會動的假進度是騙人的。
- ⚠️ **狀態字只報「3/15 頁」，不報剩餘時間**（使用者 2026-08-25 當天指示刪掉）。原本會外推一個「約剩 2 分」——刻意從**第一頁完成之後**的速率算（第一頁含引擎載入），也刻意只報到分或十秒級。⚠️ **但那還是猜的**，而這裡的每頁耗時差異很大（一行進旋轉救援要跑七次 OCR），估計值自己會跳來跳去；頁數是量到的事實，一個抖動的猜測擺在旁邊只會把它稀釋掉。格式化那支函式與只為它存在的「第一頁完成時刻」欄位一起刪乾淨了（想看長相去翻 git 歷史，不要照著這段話重寫一次）。
- `WARNING: page 3 dropped, …` → 存起來寫進結果列，並由 `_fmt_degraded()` 譯成中文、同種下場的頁碼併在一起講。

### 結果列取代「完成」對話框

舊版跑完會 `askyesno("完成", "…要開啟所在資料夾嗎？")`。⚠️ 那個框有一個**當時就寫在程式註解裡**的毛病：它正好蓋住剛印出來的降級 `WARNING`，按完「否」就再也不會有人往下看——於是「哪幾頁沒轉成文字」被一個問句擋掉了。改成日誌區上方一條結果列（`_show_result`）：頁碼直接寫在列上，〔開啟簡報〕〔開啟資料夾〕兩顆鈕常駐（沒有產出時 `grid_remove()`）。

### 停止（`CANCELLED_RC` = 4）

`cli.main(argv, cancel=threading.Event)`，**每頁檢查一次**。⚠️ 停不了「當下這一頁」——OCR 那一下是一次進不去的呼叫，而在寫檔中途砍執行緒正是 `_on_close` 一直在警告的那條路（半截 .pptx）。所以介面上要說**「目前這一頁跑完就會收工」**，不要假裝已經停了；按下去之後鈕變灰、顯示「停止中…」。⚠️ 取消的那一趟**不存檔**：半份簡報比沒有更糟，它看起來像一份完成品。

⚠️ **不跳確認框**：鈕上寫著「停止轉檔」，再問一次「你確定嗎」只是把剛移除的摩擦換個地方裝回來。

### 拖放與貼上

`enable_file_drop()`（`tkinterdnd2`，MIT，附 tkdnd 二進位）。⚠️ **不要為了它把基底類別換成 `TkinterDnD.Tk`**：那個類別的 `__init__` 在載不到 tkdnd 時直接 raise，等於用一個純加分的功能換掉「這支程式一定開得起來」。改成自己呼叫 `TkinterDnD._require()`（同一支函式）再註冊**子控制項**——⚠️ `tkinter.Tk` **不是** `BaseWidget` 的子類，而 tkinterdnd2 是把 `drop_target_register` 掛在 `BaseWidget` 上的，所以根視窗本身沒有那個方法。⚠️ `event.data` 是 **Tcl list 字面值**（含空白的路徑會被 `{}` 包起來），要用 `tk.splitlist()` 拆。

Ctrl+V 貼上路徑綁在整個視窗上。⚠️ **焦點在輸入類控制項上時一律放行**（回 `None` 讓 Tk 走預設貼上），否則在「頁碼」欄貼一段文字會同時把輸入 PDF 換掉。

### 其餘

- **主畫面只剩一個必填欄**：輸出路徑降成一行說明＋〔變更…〕（`out_show`／`_shorten_path`，中間省略、**檔名不可以被砍掉**）。真值仍是 `out_path`。
- **用擋的、不要用告知的**：`_refresh_input_state()` 在路徑不存在時當場把訊息寫在檔案區裡、並把「開始轉檔」鎖起來。⚠️ Enter 那條路要吃同一道閘門（`_on_run_clicked` 檢查 `"disabled" in state()`），否則「鈕是灰的但 Enter 照樣跑得動」。
- **拿掉與標題列一字不差的大標題**（省 60 邏輯 px），閒置視窗高度從寫死的 640 改成量出來的 462 實體 px。
- **收合鈕整條寬、兩個狀態同一句標籤**，只翻 ▸／▾；舊版寬度寫死 34 字、展開後整句換成「進階選項（收合）」，同一顆鈕在兩個狀態講的是兩件事。
- **閒置的進度條不顯示**（2026-08-25 晚改，見 §5.6）。在那之前是一條 determinate + value=0 的空槽——⚠️ 那個「不是停住的 indeterminate」的理由仍然成立（Sun Valley 下停住的 indeterminate 會在最左邊留一小截藍色，看起來像「已經跑了 3%」），所以 `_finish()` 收工時仍要把它歸零成 determinate/0 才藏起來。
- **選項區沒有 LabelFrame 標題**：它貼在收合鈕正下方，而那顆鈕上已經寫著「轉檔選項（頁碼、浮水印、簡體修正、色塊、小字）」，再掛一次標題等於同一句話說兩遍。改用 Sun Valley 的 `Card.TFrame` 純當視覺容器——ttk 樣式名可繼承，載不到 `sv_ttk` 時會自動退回 `TFrame`（實測過，不會炸）。⚠️ 收合鈕括號裡列的是**實際露出來的那五個**，不是「還有什麼藏在裡面」：2026-08-25 之前寫的是「進階選項（頁碼、字型、DPI、除錯…）」，那三樣現在都沒有控制項了。頁碼仍然自己一行排最上（五個裡只有它是「每次可能不一樣」的值，其餘四個是開關）。

## 5.5 間距尺規（2026-08-25 晚，選項砍到五個之後）

選項砍到五個之後使用者說「UI 感覺還是有點擠」。量下去，成因**不是字太小**（基準字級本來就是 10pt，`st.configure(".", font=(fam, 10))`），是**間距的階層反了**：

| 位置 | 改之前 | 改之後 |
| --- | --- | --- |
| 區塊**之間**（檔案／動作列／選項卡／收合鈕） | `pady=5` → 實際間距 **10px** | `SP_LG` = 16px |
| 卡片內距 | 12px | `SP_LG` = 16px |
| 核取方塊行距 | `pady=2` → **4px** | `SP_SM` = 8px |
| 收合鈕 `Adv.TButton` 內距 | `(10, 6)` | `(SP_MD, SP_MD-2)` = `(12, 10)` |
| 視窗預設寬 | 760 | 880（`minsize` 680 → 760）|

⚠️ **關鍵是那一行反轉**：區塊之間 10px、卡片裡面 12px —— **外面的縫比裡面的窄**。人眼靠「外縫大於內縫」分群，反過來就分不出來，五個區塊糊成一片、每一塊都在推擠隔壁。所以規則不是「每個數字都調大」，而是**間距一律走 `SP_*` 這把尺**（`SP_XS, SP_SM, SP_MD, SP_LG, SP_XL = 4, 8, 12, 16, 24`），⚠️ **版面裡不要再出現別的間距數字**——一個手寫的 `p(6)` 混進來，階層就又破一個洞。

⚠️ **「外縫大於內縫」的前提是「沒有別的分群線索」，而 §5.10 之後有了。**卡片化之後每一塊都有自己的底色與邊框，眼睛不必再從間距推論誰跟誰是一群，所以 `CARD_GAP`(20) 小於 `CARD_PAD`(24) 並不會重演這次的災情（MP4-2-SRT 用同一組數字，使用者看過畫面）。⚠️ 但這一條只赦免**有容器邊界**的那幾道縫——卡片**裡面**仍然照舊：欄距 `SP_MD`、行距 `SP_SM`、卡片內要分成兩件事時那一道縫 `SP_XL`。

同一輪一起修的三件事（都在 `_build_ui`）：

- **容器統一成卡片**。原本三種視覺重量同時在場：「檔案」是 `LabelFrame`（蝕刻邊框＋標題）、選項是 `Card.TFrame`、收合鈕是扁平長條。「檔案」改成 `Card.TFrame` 之後，那個標題也不必了——卡片裡第一行就寫著「輸入 PDF」。⚠️ 動作列**不要**也包成卡片：主要動作要浮在版面上，不是再被裝進一個盒子。（⚠️ **這一句 2026-08-26 被 §5.10 推翻**：整個版面卡片化之後，「浮著」的意思變了——畫面上其他每一塊都是白卡，只有它坐在灰底上，讀起來不是「被強調」而是「沒做完」。）
- **輸入欄的標籤移到上面**、輸入框整條寬。舊版「輸入 PDF：」與輸入框左右對擠在同一列，第 0 欄的寬度由那五個字決定，於是**畫面上唯一必填的東西被推掉一截**。
- **同一欄的兩顆鈕都要 `sticky="ew"`**（瀏覽…／變更…）：一顆 `w` 時欄寬由較寬的那顆決定，另一顆的右緣會短一截。

**改完量到的 `reqheight`（邏輯 px）**：閒置 426、選項展開 655、日誌展開 610（⚠️ 卡片化之後是 500／749，見 §5.10）。⚠️ **手風琴仍然成立**：兩區同時攤開是 **839**，而 1080p@125% 的筆電工作區只有約 810——比舊版的 953 好很多，但還是超。這個數字要留著，下一個想拆手風琴的人才有東西可以比。

## 5.6 閒置時不顯示進度條（2026-08-25 晚）

間距修完之後使用者指出最後一處：**閒置時那條 determinate value=0 的空槽橫貫版面中段，讀起來像一條分隔線** —— 一個「什麼都沒在發生」的元件卻在畫面上劃了一刀。改成沒在跑就不顯示（`_build_ui` 建完即 `grid_remove()`、`_start()` 裡 `grid()` 回來、`_finish()` 的 `finally` 再 `grid_remove()`）。

⚠️ **能這樣做的前提是「它和按鈕、狀態字是同一列的三個欄」**，所以要用 `grid_remove()`／`grid()`，不可以 `destroy`、也不要去動欄寬：列高由最高的那個（`Run.Accent.TButton`，46 邏輯 px）決定，藏掉這條 7px 的東西**版面完全不動**。改之前先量過，數字留著：

| | 有進度條 | 藏起來 | 再放回來 |
| --- | --- | --- | --- |
| `actions` reqheight | 46 | 46 | 46 |
| 視窗 reqheight | 426 | 426 | 426 |
| 「開始轉檔」的 x | 0 | 0 | 0 |
| 狀態字的 x | 787 | 787 | 787 |

⚠️ 換成 `pack_forget()` 或整列重排就不成立了 —— 按鈕與狀態字會在按下去的那一瞬間跳位，而那正是使用者最在看畫面的時候。⚠️ 狀態字用的是 `winfo_x`（左緣）；它在「就緒 → 完成 ✓」之間會左右移動是**正常**的，那一欄 `sticky="e"` 釘的是右緣（`STATUS_SAMPLES` 的 `minsize` 只是地板）。

⚠️ **`_finish()` 收工時要先歸零成 `determinate` / `value=0` 再藏**。舊版寫的是「`_determinate` 為假就留在 `indeterminate`」，那正是同一支檔案自己註解裡警告過的狀態（Sun Valley 下停住的 indeterminate 會在最左邊留一小截藍色，看起來像「已經跑了 3%」或「卡住了」）。閒置既然不顯示，那個殘留狀態現在看不到，但下一趟 `_start()` 之前把它留乾淨才不會有人再踩。

**實跑驗過**（`guardV2` 六頁，走 GUI 的 `_start()` 而不是直接呼叫 cli）：閒置不顯示 → 轉檔中顯示（`winfo_ismapped()` 為真、狀態字 `2/2 頁`）→ 收工後不顯示、狀態字「完成 ✓」、結果列出現。

⚠️ **量 Tk 的 `widget["mode"]` 要包 `str()`**（寫驗證腳本時踩到，不是產品問題）：這個 Tk 版本回的是 `Tcl_Obj`，f-string 印出來是 `determinate`，但 `== "determinate"` 是 `False`，於是「等它進 determinate 再截圖」那段永遠不觸發、還看不出哪裡錯。

## 5.7 轉檔中鎖住輸入、說明文字加深（2026-08-25 晚）

### 轉檔中把「按了也沒用」的輸入鎖起來

使用者：「轉檔中 轉檔選項 請 DISABLE 不給輸入，因為轉檔時輸入那些選項已經沒有用了。」argv 在 `_start()` 的第一行就組好交給背景執行緒了，所以轉檔中改頁碼、改核取方塊**對這一趟完全沒有作用**——但控制項照樣有反應、照樣打得進字，看起來像是改得到。這跟「路徑不存在就把開始轉檔鎖起來」是同一條原則：**用擋的、不要用告知的**。

形狀是 `_set_inputs_enabled(bool)` ＋ 一份在 `_build_ui` 裡**明列**的 `self._inputs`（`_start()` 鎖、`_finish()` 的 `finally` 解鎖）。⚠️ **不要走訪 children 一律 disable**：那會把「輸入 PDF」小標與提示文字一起變灰，而那兩行正是轉檔中最該讀得清楚的東西。⚠️ **停止鈕、兩顆收合鈕、開啟紀錄不進清單**：那些是轉檔中真的要按的。

⚠️ **檔案區也要一起鎖**（使用者只點名了轉檔選項，但理由一模一樣）：換輸入 PDF 對這一趟同樣沒有作用，只鎖一半反而讓人以為另一半改得到。

⚠️ **拖放與 Ctrl+V 是繞過控制項的另外兩條路**，各自也要擋——不然欄位是灰的、路徑卻換掉了。⚠️ 拖放**不可以靜靜地什麼都不做**：那看起來就是拖放壞了，使用者會一直重拖。要當場把原因寫在提示行上（紅字），`_finish()` 再把它換回正常提示。

⚠️ **`_finish()` 的 `finally` 裡順序有意義**：`_refresh_input_state()` 必須趁 `self.running` **還是 True** 時呼叫。它結尾會把狀態字寫成「就緒」，而那一步是用 `not self.running` 擋住的——先把旗標放掉再呼叫，剛剛寫上去的「完成 ✓」／「已停止」／「失敗」就會被蓋成「就緒」。這裡要它做的只有一件事：把拖放被擋時寫上去的紅字換回正常提示。

**實跑驗過**（`guardV2` 四頁，走 GUI 的 `_start()`）：閒置 0/8 鎖住 → 轉檔中 8/8 鎖住、停止鈕與兩顆收合鈕與開啟紀錄都還能按、拖放被擋且提示換成紅字、Ctrl+V 沒有換掉輸入檔 → 收工後 0/8、狀態字是「完成 ✓」（沒有被蓋成「就緒」）、提示回復。

⚠️ 寫這種驗證腳本時記得：`_run_conversion()` 期間 `sys.stdout` 被換成 `QueueWriter`，**轉檔中的 `print()` 全部跑進 GUI 的日誌區、不會出現在主控台**（第一版腳本因此看起來像「中間那幾行都沒執行」）。先收進 list、收工後再印。

### 說明文字的顏色加深

使用者：「感覺介面上的字，顏色有點太淺。」量過之後淺的**不是一般標籤**（≈`#1c1c1c`，對 `#fafafa` 是 15:1），是 `Muted.TLabel` 那一組——副標、輸入提示、「輸出：…」，畫面上大半的字。

| | 舊值 | 對比度 | 新值 | 對比度 |
| --- | --- | --- | --- | --- |
| 亮色 `muted`（on `#fafafa`）| `#5d6470` | 5.71:1 | `#41474f` | **8.99:1** |
| 暗色 `muted`（on `#1c1c1c`）| `#a6adb8` | 7.54:1 | `#b9c0cb` | **9.30:1** |

視窗第一句說明（副標）另外改成**粗體**（使用者 2026-08-25 晚指示），走 `Sub.Muted.TLabel`。⚠️ **樣式名必須以 `.Muted.TLabel` 結尾**：ttk 是照**後綴**一層層往上找的（`Sub.Muted.TLabel` → `Muted.TLabel` → `TLabel`），取名成 `Subtitle.TLabel` 就只會繼承到 `TLabel`，字是粗了但顏色會掉回預設的黑——⚠️ 而那看起來只是「有點怪」，不會報錯。加粗不影響高度（`reqheight` 仍是 426）。

⚠️ **色碼本身還不是使用者看到的東西**：中文小字反鋸齒之後會再淡一階。同一句副標在截圖上量到的筆畫核心，改之前是 **(112,118,130)**、改之後是 **(88,93,101)**——比 `#5d6470`／`#41474f` 都淡。所以**判斷要量渲染結果、不要只看色碼**，而 5.71:1 雖然過得了 WCAG AA 的 4.5:1，實際讀起來仍然偏淡。⚠️ 這兩個值有下限，不要再往回調淡。

## 5.8 工作列進度與完成提醒（2026-08-26）

**要解決的是「使用者不會盯著這個視窗看」。** 一份三十頁的簡報要跑好幾分鐘，人會切去做別的事——而那一刻，視窗裡的進度條、狀態字、結果列**全部看不見了**。NN/G 對長等待的建議是讓使用者去做別的事，但前提是他不必切回來才知道進度跑到哪。

Windows 對這件事有兩個原生答案，`pdf2ppt_gui_2.py` 兩個都用：

| 時機 | 做什麼 | 函式 |
| --- | --- | --- |
| 轉檔中 | 工作列按鈕本身畫成進度條 | `taskbar_progress()` |
| 收工時 | 依結果留色，並閃那顆按鈕 | `taskbar_finish()`／`flash_taskbar()` |

### 三個掛載點

- **`_start()`**：`taskbar_progress(self, 0, 0)` → 跑馬燈。⚠️ 要**主動設一次、不要等第一頁**：載入引擎那段可能幾十秒，切走的人在那之前需要看到「它已經開始了」。順便把上一趟留下的黃／紅蓋掉。
- **`_scan_line()`**：收到 `page N (n/total)` 就 `taskbar_progress(self, done, total)`，與視窗裡那條 `ttk.Progressbar` 同步（同一組數字，見 §5.4「進度：從 cli 的 stdout 解析」）。
- **`_finish()`**：`taskbar_finish()` ＋ 條件式 `flash_taskbar()`。⚠️ 兩件事都放在 `finally` 裡——那是整趟轉檔**唯一保證走得到**的收尾點（停止與失敗也走這裡）。

### 四種收場

| rc | 工作列 | 閃 | 為什麼 |
| --- | --- | --- | --- |
| 0 | 清除 | ✔ | |
| `PARTIAL_RC`（3）| 留黃（`TBPF_PAUSED`）| ✔ | 一眼看出這趟不是乾淨完成，不必先切回視窗才發現 |
| `CANCELLED_RC`（4）| 清除 | ✘ | 使用者自己剛按下去的，通知他一件他自己做的事只是噪音 |
| 其他 | 留紅（`TBPF_ERROR`）| ✔ | |

⚠️ `_finish()` 裡 `outcome` 的預設值是 `"error"`、`notify` 是 `True`，**這是刻意的**：底下任何一步炸掉都代表這趟不乾淨，工作列就該留一條紅的。

⚠️ **有降級與失敗要「留在那裡」不清掉**：那條顏色正是給還沒切回來的人看的。下一趟 `_start()` 會蓋掉，關掉視窗也就沒了。

### 五個踩得到的地方

1. ⚠️ **`GetParent` 的 `restype` 一定要設。** `ctypes.windll` 的預設回傳型別是 `c_int`（32 位元），而 64 位元 Windows 的 HWND 是指標寬。值小的時候看起來完全正常，一旦某次配到高位元有值的 handle 就會被**靜默截斷**成另一個視窗的號碼——那種 bug 只會偶爾發生一次，查起來毫無線索。統一走 `window_handle()`（`use_dark_titlebar` 也改成用它）。2026-08-26 實測：同一支程式裡拿到的 COM 指標是 `0x1AB…`（**超過 32 位元**），HWND 只是碰巧小。
2. ⚠️ **`winfo_id()` 不是 HWND。** 那是 Tk 自己那個**子**視窗，DWM 與工作列都不認它，要 `GetParent` 往上取一層才是工作列上那顆按鈕對應的視窗。
3. ⚠️ **`TBPF_ERROR`／`TBPF_PAUSED` 只換色、不動數值。** 前一刻若停在 0%，換色等於畫了一條看不見的紅線——所以 `taskbar_finish()` 先 `SetProgressValue(1, 1)` 推到滿格再換色。
4. ⚠️ **COM 物件只能在主執行緒碰。** `CoInitialize` 給的是 STA，物件綁在建立它的 apartment 上。三個掛載點都在 Tk 主執行緒（`_scan_line`／`_finish` 是 `after_idle` 排進來的），背景 worker 執行緒不可以呼叫。
5. ⚠️ **vtable 的位置是介面定義的一部分**，不會變動：IUnknown 佔 0-2、ITaskbarList 佔 3-7、ITaskbarList2 佔 8、ITaskbarList3 自己的方法從 9 起。所以 `SetProgressValue` 是 9、`SetProgressState` 是 10。

### 不要改成把視窗搶到前景

⚠️ **`focus_force`／`deiconify`／`-topmost` 一個都不要用。** 使用者這時正在別的視窗打字，搶焦點會把他的按鍵吃掉。而且 Windows 本來就有前景鎖擋著，擋下來的結果**還是閃工作列**——差別只在系統選的閃法比我們吵。我們只送 `FLASHW_TRAY | FLASHW_TIMERNOFG`：只閃工作列按鈕（不閃標題列——視窗只被蓋住一半時那樣很吵又沒多給資訊），一直閃到使用者把視窗切到前景為止。

⚠️ `flash_taskbar()` 在**視窗已經是前景時當場返回**：人就坐在這個畫面前面，結果列已經把話講完了，再閃一次只是噪音。

### 失敗一律安靜

全段沿用 `set_app_user_model_id()` 那條原則：**純外觀，任何一步失敗就安靜回到舊行為**，不可以讓轉檔本身跟著倒。`_taskbar_dead` 讓建立失敗只發生一次——沒有這個旗標的話，每更新一頁就會重試一次 `CoCreateInstance`。

### 驗收

底層那一半（HWND 取不取得到、`ITaskbarList3` 建不建得起來、六個狀態會不會丟例外）用一支臨時腳本開個 Tk 視窗跑一遍就知道：`window_handle()` 非 0 且不等於 `winfo_id()`、`_taskbar_dead` 是 False、所有呼叫都不丟。端到端則是真的轉一份 PDF，中途 `iconify()` 把視窗最小化，收工時工作列按鈕會閃。

⚠️ **截圖只能當佐證、不能當判準**（同 §5.2 的理由：會截到使用者的實機桌面），而且閃爍是動態的，連拍才抓得到亮的那一張。

## 5.9 Squircle 皮膚：互動控制項的連續圓角與 Apple 色票（2026-08-26）

**做的是換皮，不是改版面。** 按鈕、輸入框、核取方塊、進度條的背景改成連續圓角（squircle）的實色底板，顏色對齊 `meeting-scribe`；卡片、視窗外框、間距、控制項的排列順序**一個都沒動**。決策層（為什麼只到互動控制項為止、為什麼不做漸層）見 `docs/spec/09-執行環境與效能.md` §9.6.3。

⚠️ **這一節有兩件事在同一天被 §5.10 推翻**（使用者當天稍晚指示「參考 MP4-2-SRT UI 的圓角、卡片、顏色」）：曲線指數從 5.0 換成 **2.0（正圓）**，而「卡片一個都沒動」變成「整個版面卡片化」。**其餘每一條仍然成立**——那六個坑、兩條路的降級、五種縮放、image element 的做法都沒有變。

### 形狀：四分之一超橢圓，直邊保持直的

圓角矩形的角是一段**圓弧**，弧與直邊接得上位置、接不上曲率，交界處看得出一個轉折；squircle 的角是超橢圓 `|x|^n + |y|^n = r^n` 的四分之一，曲率從邊上的 0 連續長到角落的最大值——同樣的 `r` 看起來更飽滿、轉角更長一段。當時取 `SQ_N = 5.0`（4 還看得出方、6 之後跟正圓角分不出來），遮罩用 `SQ_SS = 4` 倍超取樣再縮回來當抗鋸齒。

⚠️ **`SQ_N` 當天稍晚改成 2.0（正圓弧），見 §5.10。** 超取樣、取樣點數、`_sq_points` 那支公式都沒有變——指數是唯一動的那個旋鈕。

### 做法：ttk 的 image element

PNG → base64 → `tk.PhotoImage` → `Style.element_create(..., "image", ...)` → 把 sv_ttk layout 裡的背景元件換成它（`SquircleSkin._swap` 是遞迴複製 layout、只改元件名字，其餘結構原封不動）。sv_ttk 自己整套佈景就是一張 spritesheet 這樣掛上去的，所以這條路一定走得通。

⚠️ **PNG 從哪來，有兩條路，都要通：**

| 來源 | 什麼時候 | 成本 |
| --- | --- | --- |
| `assets/skin/`（打包好的） | 有資產就走這條 | `install()` 約 5ms，**不需要 Pillow** |
| 當場畫（import `tools/make_skin.py`） | 資產不在或壞了 | 首次約 47ms（含 Pillow import），之後約 8ms |

資產是 `tools/make_skin.py` 的產物：十組（深淺 × 五種顯示縮放）sprite sheet 加一份 `sprites.json`，合計約 105KB。⚠️ **形狀、圓角半徑、色票、內距的唯一真值在那支腳本**——改了要重跑再提交，不要手改產物（與 `tools/make_icon.py` 同一條原則）。⚠️ **資產不在就當場畫**（使用者 2026-08-26 指示）：那支工具可以直接 import，`build_variant()` 回傳的東西與資產同構，所以三種情況都活得下去——有資產、只有原始碼、兩者皆無（最後一種才放棄換皮）。實測兩條路畫出來的畫面**逐像素相同**（四個狀態各比一次，差異像素 0）。

⚠️ 兩個小地方：切 sprite 時 **`-compositingrule set` 不可省**（預設是 overlay，會把來源疊上去而不是覆蓋，半透明的角落會被疊成不透明）；讀圖一律走 **base64 而不是 `-file`**，順手避開「專案放在非 ASCII 路徑」那一類麻煩。

### 為什麼要五種縮放

資產是固定像素，顯示縮放不是。五檔（100%／125%／150%／175%／200%）正好對上 Windows 顯示設定裡的那五個值，載入時挑最接近的——實務上永遠是精確匹配，所以圓角與內距不會互相錯開。⚠️ 當場畫那條路用的是**實際**倍率，本來就沒有這個限制。

| 控制項 | 換掉的元件 | 圖片 |
| --- | --- | --- |
| 一般按鈕（瀏覽…／變更…／開啟簡報／兩顆收合鈕） | `Button.button` | 灰底無框，四個狀態 |
| 主要動作鈕 | `AccentButton.button` | Apple 藍／深紅各一組 |
| 輸入框 | `Entry.field` | 淡底描邊，focus 時描邊換 accent 並加粗 |
| 核取方塊 | `Checkbutton.indicator` | 沒勾是空框，勾了才上色 |
| 進度條 | `Horizontal.Progressbar.trough`／`.pbar` | 圓頭軌道與填充條 |

⚠️ **不要用 Pillow 的 ImageTk**：它要再多一個 C 擴充模組才 import 得起來，缺了就是 ImportError，而 Tk 8.6 的 `PhotoImage` 本來就吃 base64 的 PNG（含 alpha）。⚠️ **PhotoImage 的參考要自己留著**（`SquircleSkin._keep`）：Tk 不持有，放掉就整片變空白。

### 六個踩得到的地方

1. ⚠️ **`border` 不可超過圖片邊長的一半。** 切不出九宮格時 ttk 會在幾何計算裡原地打轉，事件迴圈**當場卡死**——`after` 不再觸發、視窗畫不出來，而且**沒有任何例外**。用 19px 的圖配 `border=10` 撞到過一次，症狀是程式一路卡到被 timeout 殺掉，逐個元件二分才找出是 `Entry`。底板一律畫成 `2*(r+1)+1` 見方。
2. ⚠️ **`padding` 一定要明寫。** image element 沒給 padding 時會**拿 border 當內距**，圓角半徑於是加到控制項的內距上——半徑 12 的主要動作鈕就這樣一口氣高了 26px。
3. ⚠️ **sv_ttk 的圖片是自帶內距的，換掉圖片要把那一份補回來**（`SQ_PAD = 4`／`SQ_PAD_FIELD = 5`）。不補的話全畫面的控制項一起矮 8px、視窗 `reqheight` 從 426 掉到 387。核取方塊同理：`SQ_CHK_BOX` 取 20（sv_ttk 的尺寸），17 會讓每個核取方塊矮 3px、選項區展開時整體矮 12px。
4. ⚠️ **九宮格的中段是「重複貼」，不是拉伸——中段留 1px 會讓整個介面慢到像當掉。** 底板原本畫成 `2*(r+1)+1` 見方，中段正好 1px；Tk 填一顆 840px 寬的收合鈕就是幾百次繪製呼叫，於是**重畫整個視窗要 2.5 秒**（`_fit_window` 2584ms、展開選項 2071ms、收合 1044ms），使用者回報的說法是「好像進入死迴圈」。把底板加寬成 `2*(r+1)+SQ_MID`（96）之後 `_fit_window` 回到 71ms——沒有皮膚時是 74ms。⚠️ 加寬的同時 **`width`/`height` 一定要釘成正方形版的尺寸**：image element 的原生尺寸預設等於圖片尺寸，不釘的話每顆按鈕的最小寬度都會變成 96px 以上。進度條的軌道與填充條是另外建的，同一條也要套。
5. ⚠️ **底板要先畫成不透明的 RGB，最後才把遮罩放進 alpha 通道。** 拿遮罩去 `paste` 一張 RGB 到透明畫布上的話，角落抗鋸齒帶的 RGB 會**先跟畫布的黑色混一次**（填色 `(232,232,237)` 被寫成 `(42,42,43)`），而 Tk 合成時又依 alpha 混第二次——四個角各浮出一圈比底色深的邊，使用者回報的是「灰色形狀四個角落都有別的顏色」。驗法是抓一張底板、印出 alpha 介於 1–254 的像素：**它們的 RGB 必須等於填色本身**。
6. ⚠️ **色票不能照抄。** 深色的次要按鈕比 meeting-scribe 亮一階（`#3a3a3c` 對 `#2c2c2e`）：那邊的深色卡片是 `#1d1d1f`，而我們的卡片是 `#2c2c2e`，照抄的話按鈕會整顆融進卡片，畫面上只剩浮著的文字。（換皮當天卡片還是 sv_ttk 畫的，明顯亮一截；§5.10 自己畫卡片之後這個值正好撞在一起，結論不變、理由更直接了。）

### 顏色：抄 meeting-scribe，兩處刻意偏離

色票取自 `meeting-scribe` 那支工具的 UI 樣式模組 src/meeting_scribe/ui_style.py（那份的來源是 apple.com）：主色 `#0071e3`／`#0a84ff`（hover `#0077ed`／`#3395ff`）、次要底 `#e8e8ed`／`#3a3a3c`、輸入框 `#f5f5f7`／`#2c2c2e`、分隔線 `#d2d2d7`。兩處不同：

- **深色的次要按鈕亮一階**（理由見上）。
- **停止鈕兩個模式都用 `#d70015`**。深色的 systemRed（`#ff453a`）拿來當大面積底色時，白字只有 3.4:1；`#d70015` 是 5.4:1。這顆鈕坐在主要動作的位置上、字又是粗體 12pt，讀不清楚不是選項。

⚠️ **形狀不跟著抄**：meeting-scribe 的按鈕是膠囊（`button_*_radius: 999px`），這裡是 squircle。⚠️ 跨 repo 的路徑寫在註解裡會被 `tests/test_docs_index.py` 的斷鏈檢查抓到，那一條要連同理由寫進它的 `_ALLOW`。

### 漸層做過，但拿掉了

第一版是 systemBlue → systemIndigo 的漸層（主鈕、進度條、勾選框），使用者看過參考頁之後指示「我不要漸層效果／全部都是實色」，整批移除。**要加回去之前先知道這兩件事**：

- 漸層**沒辦法走九宮格**——中段一拉伸就成了一片純色（左端一小段藍、中間死板一塊、右端一小段靛），只能跟著控制項的實際寬高重畫整張。
- 而重畫會撞第二個坑：image element 的原生尺寸會撐大 widget 的 requested size，於是「畫大 → widget 變大 → `<Configure>` → 再畫大」一路發散，事件迴圈被灌爆、`after` 永遠排不進去。`element_create` 時把 `width`/`height` 釘成小值可以切斷這個回饋。

實色沒有這兩個問題：**實色配九宮格對任意尺寸都是對的**（拉開的是純色），所以一種控制項一組圖就夠，也不必綁 `<Configure>`。

### 降級與驗收

⚠️ **裝不起來就回 `None`，畫面留在原本的長相**（與 sv_ttk 缺席同一條原則）：沒有 sv_ttk（layout 結構不一樣）、沒有 Pillow、`element_create` 丟例外，三者任一都整個放棄。⚠️ 樣式名照後綴繼承，所以 `STOP_STYLE`（`Stop.Run.Accent.TButton`）在沒有皮膚時會沿用 `Accent.TButton` 的 layout，**不會炸**，只是停止鈕跟開始鈕同色——已實測。

驗收兩件事，缺一不可：

1. **重繪不變慢**：`skin` 開／關各建一次 `App`，量 `App()` 全程、連續 `update()`、展開與收合選項。目標是**每一項都貼著沒有皮膚時的數字**（實測 0.367s／0.070s／0.040s／0.021s，對照組 0.328s／0.062s／0.038s／0.019s）。⚠️ 量的時候不要只看「連續 update 的平均」——慢的是**首次繪製**，暖機之後每次都是 0.01ms，平均值會把兩秒半的卡頓稀釋成看起來還好。
2. **版面零位移**：`skin` 開／關各建一次 `App`，逐個量 `winfo_reqwidth/reqheight`。目標是**每一格都相同**（含視窗的 `reqheight` 426、展開選項後 655）。這一步抓到了上面第 2、3、4 三個坑，截圖只看得出「怪怪的」。
3. **視覺**：閒置／選好檔案／轉檔中／完成加選項展開，淺色與深色各一輪，最後真的轉一頁 PDF（載入引擎那段是 indeterminate，形狀要另外看一眼）。⚠️ 截圖用 `PrintWindow` + `PW_RENDERFULLCONTENT` 抓視窗自己，**不要用 `ImageGrab` 抓螢幕座標**——那會截到使用者的實機桌面（第一次就抓到別人的瀏覽器），也逼得測試腳本去搶前景。

## 5.10 卡片化與正圓角：對齊 MP4-2-SRT（2026-08-26）

同一天稍晚，使用者說「**參考 MP4-2-SRT UI 的圓角，卡片，顏色，修正本專案的 UI**」，接著補「**按鈕都請依照 MP4-2-SRT 樣式**」。那支姊妹專案當天早上才把同一套皮膚移植過去、又在使用者的要求下改成正圓角與卡片版面（它自己的來源是 meeting-scribe 的網頁截圖），所以這一輪是把它已經定案的三件事搬回來：**曲線指數、卡片、三階底色**。決策層見 `docs/spec/09-執行環境與效能.md` §9.6.3。

### 一、曲線指數 5.0 → 2.0（正圓弧）

`SQ_N = 2.0`。⚠️ **光加大半徑沒有用，指數才是那個旋鈕**：n=5 的超橢圓幾乎填滿整個角落方框、只在最角落切掉一點，半徑 21 時**視覺上的圓角只有 7px**（量 sprite 的 alpha 量出來的，MP4-2-SRT 那邊量的）。小按鈕看不出來，卡片那麼大一塊就是「幾乎直角」。

⚠️ **畫面上不要有兩種曲線**：MP4-2-SRT 中間試過一版「容器正圓、按鈕留 squircle」，被使用者那句「所有按鈕圓角弧度也跟它做成相同」推翻。這裡直接照結論走。

半徑逐像素量自那份參考畫面：卡片 30 實體 ÷ 150% = 20（`SQ_R_CARD`），按鈕 12 ÷ 1.5 = 8（我們維持 `SQ_R = 10`，差 3 實體像素，肉眼分不出來）。⚠️ **卡片要比它裡面的框大一號**：圓角一層套一層時內外同半徑會看起來內圈比較胖（外圈的曲率被更長的直邊稀釋掉），轉角對不齊。

### 二、色票抽成一份，底色從兩階變三階

顏色的唯一真值搬到 **`pdf2ppt/palette.py`**（不 import 任何東西），皮膚產生器與 GUI 讀同一份。⚠️ **不要在任何一邊另抄一份**：它原本真的分成兩份（產生器一份「畫進圖片的顏色」、GUI 一份「文字的顏色」），六個鍵是重疊的，而重疊的鍵一旦漂開，症狀是「按鈕的藍跟卡片邊框的灰差一階」——肉眼看得到卻查不出來源。

⚠️ **能住在套件裡的前提**是它沒有相依：`pdf2ppt/__init__.py` 只有一行 docstring，所以 GUI 那行 `from pdf2ppt.palette import PALETTES` **不會**把 numpy／pymupdf／python-pptx 拉進啟動路徑（那些仍然只在按下轉檔時才 import）。

底色從兩階（視窗底 + 日誌白）變**三階**：

| | page（視窗底） | card（卡片，凸起） | field（卡片裡的元件，凹陷） |
| --- | --- | --- | --- |
| 淺色 | `#f5f5f7` | `#ffffff` | `#f0f0f3` |
| 深色 | `#1c1c1e` | `#2c2c2e` | `#161617` |

深色方向相反（卡片比底**亮**、元件比卡片**暗**），但「內容區永遠是凹下去的那一層」兩邊都成立。⚠️ **不要把深色的卡片畫成白的**——那不是「亮一階」，是一堆發光的白塊。

⚠️ **`muted` 兩個模式都要重算**，因為它坐的底色變了，而 CLAUDE.md 釘的是 **≥9:1**：

- 淺色 `#41474f` → **`#3d434b`**：視窗底從 `#fafafa` 換成 `#f5f5f7` 之後舊值只剩 8.61:1。新值對 page 9.17、對 card 9.99。
- 深色 `#b9c0cb` → **`#ccd2dc`**：舊值對視窗底是 9.29，但**卡片比視窗底亮一階**，同一個字坐在卡片上只剩 **7.61**。新值對 card 9.17、對 page 11.20。

⚠️ 副標坐在 page 上、卡片裡的提示坐在 card 上，**兩個底都要過**——所以淺色以 page（較暗的底）為準、深色以 card（較亮的底）為準。

### 三、圓角外側要畫進圖裡（`plate` 的 `on`）

**這是卡片化帶進來的新坑，換皮那一輪不會遇到。** ttk 先用樣式的 `background` 把整塊填滿、**再**把九宮格圖畫上去，所以圓角外側那圈透明區露出來的是那個 background，不是父容器的顏色。沒有卡片時看不出來（樣式的預設背景正好就是視窗底），有了卡片就是**按鈕的圓角外露出一圈視窗底的灰、方方正正貼在白卡上**。

作法：每張底板都指定 `on=`（它坐在什麼顏色上），把外側直接畫成那個色、整張圖不透明。⚠️ **不要改走「把樣式的 `background` 設成外側色」那條捷徑**：那對 `TFrame` 有效，但對有自己 `background` 語意的控制項（`TEntry` 的欄位底、`Treeview` 的列底色）就是把別的東西一起改掉。代價只是「同一張底板不能重複用在兩種背景上」——本專案的每個控制項都只坐在一種底色上。

⚠️ 順帶一提：`shade()` 因此也要**對顏色做、不要對圖片做**。整張 blend 會把圓角外側那圈一起壓暗，按下按鈕時卡片上會浮出一圈比周圍暗的方框。

`tests/test_gui_helpers.py::test_every_skin_plate_declares_what_it_sits_on` 釘著「新增底板時忘了指定 `on`」，因為那個漏法只有截圖看得出來。

### 四、九宮格中段的**垂直**版（`block()`）

§5.9 第 4 點的水平版說的是「中段留 1px 會慢到像當掉」。卡片與日誌槽會被撐到好幾百 px **高**，於是同一條規則在垂直方向再來一次。會被撐得又寬又高的東西改用 `block()`（兩個方向都留 `SQ_MID`），只被水平拉開的（按鈕、輸入框、進度條）維持 `wide()`。

⚠️ 元件的 `width`／`height` **不可以跟著改成圖片邊長**——那兩個是「最小尺寸」，給了整張圖的邊長之後每一張卡片都會被硬撐成一百多 px 高。資產從 105KB 長到 234KB，那是實色圓角、PNG 壓得掉。

### 五、`layout()` 要**先全部抄下來再統一寫回去**

低調按鈕（`Adv.TButton`／`Subtle.TButton`）是從 `TButton` 抄 layout 的，而 `TButton` 自己也在同一批裡被換掉。邊抄邊寫的話，抄到的是**已經換過**的版本：`Button.button` 早就被改名成 `Sq.button`，替換表對不上任何一個元件名——兩顆收合鈕安靜地留在一般按鈕的灰底皮上，沒有例外、也沒有錯誤訊息（2026-08-26 截圖才看出來）。

### 六、版面：四張卡片，收合鈕在卡片之外

由上而下：副標 → **卡片一「檔案」** → **卡片二「進度與動作」**（含結果列）→ **卡片三「轉檔選項」** → **卡片四「詳細訊息」**，後兩張可收合。尺規三個：`PAGE_PAD = 20`（視窗邊 → 卡片）、`CARD_PAD = SP_XL`（卡片邊 → 內容）、`CARD_GAP = 20`（卡片之間）。⚠️ `CARD_PAD` **第一版寫 16，MP4-2-SRT 的使用者當場說太窄**；他在截圖上圈的那圈白量出來約 27 邏輯 px。

⚠️ **可收合的兩張：收合鈕就是卡片自己的標題列，展開的內容長在同一張卡片裡。** 第一版做成「卡片外一顆整條寬的鈕 ＋ 底下另外長出一張卡片」，使用者當天指出並附了 meeting-scribe 的網頁截圖：**那讀起來是兩塊東西，而它們講的是同一件事**（兩者之間還隔著一道 SP_SM 的縫）。

三個跟著改的細節：

- **低調皮的 `on` 從 `page` 換成 `card`**（靜止色同理）。收合鈕搬進卡片之後，留在 `page` 的話白卡上會浮出一條視窗底色的灰橫槓——這是「每張底板都要知道自己坐在什麼顏色上」那條規則的第二次現形。
- **卡片內距左右是 `CARD_PAD`、上下是 `SP_MD`。** ⚠️ 這兩個數字各有各的理由，不要「統一」：

  - **左右 24**：卡片裡**每一個直接子元件的左緣都落在同一條線上**——輸入框、開始轉檔鈕、收合鈕的底板、內框、日誌槽，量出來全是 24。⚠️ 對齊的是**元件邊緣，不是文字**：卡片一裡「輸入 PDF」那行字（24）與輸入框裡的字（約 31）本來就不同，因為後者還隔著底板自己的內距。第一版把可收合卡片給了 `SP_MD`(12)，理由是「這樣標題**文字**才對齊 24」——使用者當晚圈了三張卡片的左邊那圈白說寬度不一致，要以 MP4-2-SRT 為準。**他圈的是元件邊緣**。連帶 `ADV_STYLE` 的左右內距要收成 0：那顆鈕的底板左緣就是卡片內距的邊界，左右再給內距等於把它推進去一截。
  - **上下 12**：標題列自己已經有 10 的內距，兩份疊起來上緣就有 34px。給 12 之後標題文字距卡片頂是 12+10 = 22，與另外兩張卡片的 24 幾乎同一條線。⚠️ 上下也給 24 的話兩張可收合卡片各長高 24px，**選項展開時 `reqheight` 會來到 841，而 1080p@125% 的工作區只有約 810**（§5.5 那個數字現在還在守門）。

  ⚠️ **驗法是量、不是看**：逐個 `winfo_rootx()` 減卡片自己的 `winfo_rootx()`，六個直接子元件要全部相同（腳本量到的就是「24 24 24 24 24 24」，日誌槽要先展開才量得到——`grid_remove` 狀態下 `rootx` 不可靠）。
- **展開內容的內框（`Inner.TFrame`）與卡片同色、只有一圈邊框。** ⚠️ 不可以讓它換一階明度：坐在它上面的輸入框與核取方塊，底板都是照 `card` 畫外側色的，內框一換色，那些控制項的圓角外就會露出一圈白方角。真正要凹下去的是日誌槽（`Sunken.TFrame`），那一層裡沒有 ttk 控制項。
- **日誌卡片常駐，`expand` 是動態切的**（`_set_log_shown` 裡 `pack_configure`）：日誌是版面上唯一撐得開的東西，但收起來時若還 `expand=True`，剩下的高度會全灌進一張只有標題列的空卡片。

三件與 §5.4–§5.7 有關的變動：

- **動作列從「浮在版面上的裸列」變成卡片**。舊註解寫的是「主要動作要看起來浮在版面上，而不是又被裝進一個盒子裡」——卡片化之後「浮著」的意思變了：畫面上其他每一塊都是白卡，只有它坐在灰底上，讀起來不是「被強調」而是「沒做完」。主要動作靠那顆藍鈕自己就夠亮了。
- **結果列搬進動作卡片**，改用 `grid_remove()` 藏。⚠️ 因此 `result_slot` 那個空槽連同 `_collapse_slot()` 的呼叫一起刪掉了：那個坑（空掉的容器把高度永久留在版面上，見 §5.4）**只發生在 pack 的容器**，grid 會把整列從高度計算裡拿掉。（⚠️ 當天稍晚選項區與日誌區也改成 grid，那支函式於是整個刪掉——見下面的「同一張卡片」。）
- **兩顆收合鈕與「開啟紀錄」走低調皮**（`Sq.subtle`：靜止態就是卡片底色本身，滑過才浮出灰底——Fluent 的 Subtle button）。⚠️ 做成實底的話，畫面上最重的三個元素會是三條灰橫槓，而它們講的是最不重要的三件事。

⚠️ **卡片上的每一種文字都要繼承得到 `Card.*` 那一層的 `background`**：`ttk.Label`／`ttk.Checkbutton` 是**實色底**的，不是透明——不指定就吃佈景的視窗底色，坐在白卡上就是一塊塊淺灰矩形浮在白色裡。樣式名的後綴一定要留 `.Card.TLabel`（ttk 是逐段剝前綴往上找的）。⚠️ 卡片**裡面**的 Frame 要用 `CardBody.TFrame` 而不是 `Card.TFrame`：後者的 layout 被換成了一張底板圖，每用一次就多畫一張帶邊框的小卡片。

### 七、「瀏覽…／變更…」改成線框鈕（2026-08-27）

使用者要這兩顆做成 apple.com 上那種效果，指的是 Mac mini 那一頁**「查看價格」**那顆（不是旁邊藍底白字的「進一步了解」）：**靜止是白底＋藍色細線框＋藍字，滑鼠經過才整顆翻成藍底白字。**

⚠️ **只有這兩顆**（`Sq.cta`／`CTA_STYLE`）：它們是「選檔」這條主線上的兩顆，值得在滑鼠經過時明確地說「按這裡」；「開啟簡報／開啟資料夾」是跑完之後的分岔，維持一般按鈕的灰。同一種強調用在每一顆上，就等於沒有強調。

⚠️ **三個藍各有各的用途，不可以合併成一個鍵**：

| 鍵 | 用在哪 | 淺色 | 深色 | 為什麼是這個值 |
| --- | --- | --- | --- | --- |
| `cta_fg` | 靜止的線框與字 | `#0071e3` | `#3395ff` | 它坐的不是白卡而是 `#2c2c2e`：`#0071e3` 在上面只有 **2.97:1**、`accent`(`#0a84ff`) 也只有 **3.82:1**，都過不了 4.5；`#3395ff` 是 **4.59:1** |
| `cta_hi` | 翻過去的底 | `#0071e3` | `#0071e3` | **兩模式同值**，與 `stop` 同一條理由：深色的 `accent` 當大面積底色時白字只有 **3.65:1**，`#0071e3` 是 **4.70:1** |
| `accent` | 主要動作鈕、進度條、輸入框 focus | `#0071e3` | `#0a84ff` | 主色，不動 |

⚠️ 深色的 `cta_fg` 與 `accent_hi` 恰好同碼（`#3395ff`）**是巧合**，不要因此合併——後者管的是主要動作鈕滑過去的底色。

三個實作細節：

- **前景色要自己設兩層**：`st.configure(CTA_STYLE, foreground=cta_fg)` 給靜止態，`st.map(...)` 給 `disabled`／`pressed`／`active`。⚠️ `map` 不會與 `TButton` 的合併、是**整個取代**，所以 `disabled` 也要自己列——漏掉的話轉檔中被鎖起來的那兩顆會是一般的黑字，看起來還能按。⚠️ `pressed` 要排在 `active` 前面：按住不放時兩個狀態同時成立，而 ttk 取的是第一個對上的。
- **停用態是「淡框淡字」而不是灰底實心**：底色維持卡片本身、線換成 `line_off`、字換成 `run_off_fg`。灰底實心會讓它看起來像一顆**還能按**的一般按鈕。
- **線寬跟著顯示縮放走**（`max(1, px(1, scale))`，輸入框那圈是固定 1px）：這一圈是**強調**，200% 下留 1 實體像素會細到看不出它是個按鈕。

⚠️ 兩份樣式名（`Cta.TButton`／`Small.Cta.TButton`）是因為兩顆的**內距不同**。ttk 照後綴一層層往上找，所以 `Small.Cta.TButton` → `Cta.TButton`，layout 與前景色的 map 設在後者一份就夠；⚠️ 但它**繼承不到** `Small.TButton`（那要剝掉的是後綴不是前綴），內距得自己再設一次。

### 驗收（與 §5.9 同一套，數字換新的）

1. **重繪不變慢**：皮膚開／關各建一次 `App`，量 `App()` 全程、連續 `update()`、展開與收合選項。實測 0.289s／0.039s／0.021s／0.013s，對照組 0.171s／0.085s／0.032s／0.020s——建構慢的那 0.15s 是載 sprite sheet 加切 20 幾張 sub-image，其餘三項皮膚開的反而更快。⚠️ 慢的是**首次繪製**，不要只看「連續 update 的平均」。
2. **版面零位移**：皮膚開／關各建一次 `App`，逐個量 `winfo_reqwidth/reqheight`，**每一格都要相同**（實測 14 個控制項加視窗全部相同；視窗 `reqheight` 551、展開選項後 769——卡片化之前是 426／655）。
3. **資產與當場畫逐像素相同**：`tests/test_gui_helpers.py::test_the_shipped_skin_matches_what_the_generator_draws_today`（十組全比，0.2 秒）。⚠️ 故障注入驗過：把 `SQ_R` 改成 11 之後十組全紅。另外把 `SKIN_DIR` 指到不存在的路徑、逼 GUI 走 `_drawn()` 那條後路各截一張圖，客戶區逐像素相同、`reqheight` 也相同。⚠️ 比圖時**標題列會有差異**，那是視窗焦點狀態不是皮膚——比對範圍要扣掉它，否則看到的是「差兩萬七千個像素」這種假警報。
4. **視覺**：閒置／轉檔中／完成／選項展開，淺色與深色各一輪。⚠️ 截圖用 `PrintWindow` + `PW_RENDERFULLCONTENT` 抓視窗自己，**不要用 `ImageGrab` 抓螢幕座標**。
