# 文件怎麼寫(三個 repo 共用的規範)

> **要新增一份文件、要決定某一段話該寫在哪一層,或要在新專案建 `docs/` 之前先讀這一份。**
>
> 2026-08-24 定案。`meeting-scribe`、`MP4-2-SRT`、`NotebookLM_OCR` 三個 repo **各存一份、措辭刻意一致**——規範分岔了就等於沒有規範,而三份長得不一樣的時候,沒有人分得出哪一份才是對的。改了任何一份,另外兩份要一起改。

## 為什麼要分層:`CLAUDE.md` 是有預算的

`CLAUDE.md` 每開一次新對話就**整份載入**,而它八成的內容只有動到特定領域時才用得到。meeting-scribe 2026-08-06 那次瘦身把它從 **75,689 字元砍到 18,414**,細節搬進 `docs/dev/`,原地只留摘要與指路。

抽離的收益不在「文件比較整齊」,在**成長曲線**:那次之前,`CLAUDE.md` 從開專案的 16k bytes 一路漲到 145k(26 天);抽離之後的三週,它只從 19k 長到 32k。**每開一次對話都要付的那筆固定成本,從五萬字降回一萬字。**

⚠️ **上限不是技術限制**(跟 context window、API 都無關),**是注意力預算**:太長的 `CLAUDE.md` 會開始被略讀,而它每一條都是踩過坑才寫下來的——守不住注意力,寫再多也等於沒寫。

## 三層,以及各自放什麼

| 層 | 何時載入 | 放什麼 | 紀律 |
| --- | --- | --- | --- |
| `CLAUDE.md` | **每次自動** | 硬護欄、已結案的裁決、指路句 | **字元硬上限**,測試守著 |
| `docs/spec/` | 按需 | **問題與決策**——換一種語言重寫仍然成立的那些 | 實作名詞集中在「附錄-現行實作對照」一章,其餘章不得出現 |
| `docs/dev/` | 按需 | **這一份實作**——綁著語言、函式庫、平台 | 一個領域一支檔,檔頭寫明「什麼時候該讀」 |

**`CLAUDE.md` 只留「用到時才知道就來不及」的那幾條。** 判斷方式:如果沒讀 `docs/dev/` 也不會做錯,那它就不必佔用每次對話的預算。

⚠️ **上限的數字是各 repo 各自校準的,不是普世常數**:meeting-scribe 與 MP4-2-SRT 是 **18,000**(第一輪瘦身的落點,判斷過是讀得完的量級),NotebookLM_OCR 是 **35,000**(2026-08-26 從 28,000 放寬到 30,000,2026-08-27 再到 32,000,2026-08-28 再到 35,000)——它的主體是 80 幾條視覺判準的**不變量索引**,平均 208 字元/條已經是「規則+門檻+⚠️陷阱」的最小形,而**不變量的性質是改任何一處都不得違反**,不像領域文件可以「動到才讀」。⚠️ **該放寬的訊號是「上限開始咬掉規則本身的內容、而不是贅字」**:硬守只會把新規則寫成看不懂的暗號,那比長一點更傷注意力。⚠️ **放寬不等於不守**:數字放寬之後,新增的每一條一樣要先問「這條沒有每次載入,會不會做錯」——會做錯才留在 `CLAUDE.md`,否則進 `docs/spec/` 或 `docs/dev/`。調整上限時把理由寫進那條測試的 docstring,不要只改數字。

## 一句判準:這段話該進 spec 還是 dev

> **「換一種語言重寫,這句話還成立嗎?」成立 → `spec`;不成立 → `dev`。**

同一個領域(講者分離)的兩種寫法:

| | `docs/spec/` 的寫法 | `docs/dev/` 的寫法 |
| --- | --- | --- |
| 講模型 | 「輕量模型(約 28MB)」「主模型(約 71MB,192 維)」 | `models.internal_embedding_model()`、CAM++、eres2netv2 |
| 講門檻 | 「2 秒以下的聲紋近乎雜訊」 | `_BLOCK_MIN_SIM` 掃過 0.60/0.65/0.68 的消融表 |
| 講限制 | 「切分工具的內部聚類在長錄音上會塌縮,只取它的區段邊界」 | 「sherpa 1.13.4 沒有 segmentation-only API,pip wheel 是靜態連 CPU 版 onnxruntime 的單顆 `.pyd`」 |

**量化的自我檢查**:數「反引號包住的識別字」(函式名、常數名)每 10 萬字出現幾次——那是「綁死這一份實作」最直接的指標,而且一行指令就量得出來。meeting-scribe 主線 17 章是 **42.8**、`docs/dev/` 是 **389.1**,差 **9.1 倍**;spec 剩下的那點實作綁定,絕大多數集中在「附錄-現行實作對照」那一章,那一章的存在目的就是當隔離區。

⚠️ **密度倒掛就是警訊**:如果某個 repo 的 `spec/` 不低於自己的 `dev/`,那它的 spec 裝的其實是 dev 內容。最常見的成因是**從 `CLAUDE.md` 逐字搬過去**——目錄換了、內容沒換。2026-08-24 實測三個 repo:meeting-scribe **42.8 / 389.1**(正常),MP4-2-SRT **393.2 / 184.6**、NotebookLM_OCR **495.0 / 224.1**(兩個都倒掛,後者的 `spec/00` 自己寫著「從 CLAUDE.md 的架構章逐字搬過來、一個字都沒改」)。

⚠️ **倒掛不必立刻重寫**:spec 層只在**會兌現**時才回本(換語言、換平台、交給別人重寫)。沒有兌現需求之前,同一個人在同一個 repo 裡讀,內容放哪個目錄不影響用處——真正要緊的是**新增的內容知道該往哪放**,而那由這份規範與那五條測試管住。等真的要換平台時再重寫,那時候也才知道該抽出什麼。

## spec 與 dev 不能合併

它們**過時的原因不同**:`dev` 被**程式碼的改動**弄過時,`spec` 只被**產品決策的改動**弄過時。合併之後,每次改碼都要在一份混著兩種生命週期的文件裡判斷「這段該不該跟著改」,而判斷錯的方向是**沉默的**——文件會靜靜地錯下去,沒有任何測試抓得到。

**驗證過一次**:2026-08-22「從既有規格抽出一份 iOS App 用的領域規格」,`spec` 的六章直接變成 iOS 版的骨架(01、02 連章名都沒改),而 `dev` 的 38 萬字**一個字都帶不走**。分開的話那次是整章拿走;合併的話,那是逐段判斷「這句是問題還是實作」。

## 目錄結構

```
CLAUDE.md            每次載入:硬護欄 + 指路
docs/
  spec/              問題與決策(語言中立、平台中立)
    00-總覽與閱讀指南.md
    NN-....md
    mac/             平台差異(spec 的 delta,只寫「跟主線不一樣的地方」)
    ios/
  dev/               這一份實作(綁語言/函式庫/平台)
    documentation.md ← 本檔
    <領域>.md
tests/
  test_docs_index.py 守著上面每一條紀律
```

⚠️ **平台變體是 `spec` 的 delta,不是第三種東西**——它們住在 `docs/spec/<平台>/` 底下,不在頂層另開目錄。頂層永遠只有 `spec` 與 `dev` 兩個,新平台長在該長的地方。

## 守規範的五條測試(`tests/test_docs_index.py`)

分層唯一的風險是**指路斷掉**:檔案被改名或刪掉時,`CLAUDE.md` 那一行變成指向不存在的檔,而症狀是**知識安靜地消失**——以後的人不會知道那裡本來有東西,只會重蹈一次已經記載過的覆轍。所以用測試釘住:

| 測試 | 守什麼 |
| --- | --- |
| `test_every_pointer_in_claude_md_resolves` | `CLAUDE.md` 提到的每一份 docs 都要真的存在 |
| `test_every_dev_doc_is_reachable_from_claude_md` | 反向:`docs/dev/` 每一份都要有人指得到——**沒有入口的文件等於不存在** |
| `test_dev_doc_says_when_to_read_it` | 每一份 dev 檔的檔頭要寫「什麼時候該讀」,否則它只是一份不知道何時該打開的長文 |
| `test_no_comment_points_at_a_file_that_does_not_exist` | 全 repo 的註解與 `.md` 都不得指向不存在的檔 |
| `test_claude_md_stays_small` | `CLAUDE.md` 的字元上限(各 repo 校準,見上) |

⚠️ **要在文件裡提到一個不存在的檔案時,別寫成完整路徑**:第四條分不出「指路」與「講述某個檔不存在」,寫全了就是拿自己的敘述再餵它一條假斷鏈。

## 退化形式:小專案不必三層都有

**這不是例外,是規範的一部分。** 抽離是治療不是保健——等它痛:

| 層 | 什麼時候才建 |
| --- | --- |
| `CLAUDE.md` | **一律要有** |
| `docs/dev/` | 撞到任一個訊號:① `CLAUDE.md` 逼近它的字元上限;② 出現**互不相干**的領域(改 A 的人不需要知道 B);③ 某段實測論述長到寫不進程式碼註解 |
| `docs/spec/` | 只在**會兌現**時建:換語言/換平台、交給別人重寫、或需要一份「不看原始碼也能重建」的全貌 |

⚠️ **`dev` 層的知識一律要留下來,但載體可以是程式碼註解**——它防的是「同一個坑踩兩次」,而這個成本跟專案規模無關。小專案把實測數據寫在常數上方的註解裡,那也是做了;只有當註解塞不下長論述、或知識跨了好幾支模組時,才需要 `docs/dev/`。

⚠️ **反過來說,沒有互不相干的領域就不要硬拆**:全都在同一條主線上的專案(例如「來源 → 辨識 → 翻譯 → 輸出」這種一條鏈到底的),拆開只會逼人一直跨檔跳,每一次跳都是一次分心。

## 新增或搬動文件時的檢查表

1. **這段話換個語言還成立嗎** → 決定進 `spec` 還是 `dev`
2. **新的 `docs/dev/*.md` 檔頭要寫「動到 X 之前請先讀這一份」** —— 測試會擋
3. **`CLAUDE.md` 要留一句可 grep 的指路**,用反引號包住完整路徑 —— 測試會擋(沒有入口的文件等於不存在)
4. **`CLAUDE.md` 只留摘要**:留下來的那幾行要能讓人「沒讀 dev 也不會做錯」,其餘全搬走
5. **搬檔一律 `git mv`**,搬完 `grep -rn` 全 repo 修指路(範圍含 `.md` 與 `.py` 的註解)
6. **跑 `uv run pytest tests/test_docs_index.py`**
7. **改了本檔就三個 repo 一起改** —— 措辭一致是這份規範的前提

## 寫作慣例(三個 repo 共用)

- **全部繁體中文**(台灣用語),重在**為什麼**——實測數據、上游 API 行為、踩過的地雷;「做了什麼」看程式碼就好。
- **`.md` 一律不硬折行**:一個段落就是一行,靠編輯器 soft wrap。表格、程式碼圍欄、標題、清單的項目起點不受此限。
- **否決過的路要寫下來,連同數字**:「試過 X,因為 Y 所以不行」比「現在用 Z」值錢得多——前者擋得住第二次嘗試,後者擋不住。
- **⚠️ 開頭的那幾條是給未來的自己看的警告**,不是強調語氣的裝飾;沒有實際代價的事情不要標。
