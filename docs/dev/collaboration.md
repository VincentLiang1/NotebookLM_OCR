## 1. 「記住 / 記憶下來」= 寫進 repo，不是寫進 Claude Code 的記憶功能

2026-08-17 移植自 `C:\SOURCE5\Python\meeting-scribe`（該規則 2026-08-06 在 meeting-scribe 與 `MP4-2-SRT` 定案，2026-08-10 推及 `C:\SOURCE5\WIKI` 與 `C:\SOURCE5\FWIKI`，措辭一致；本專案是第五個）。

**Why**：記憶功能的目錄在 `%USERPROFILE%\.claude\projects\<由專案路徑編出來的名字>\`，**在 repo 之外、git 不追蹤**，而使用者換電腦的方式是**複製專案資料夾**——寫在那裡的東西一份都帶不走。更麻煩的是那個目錄名是從絕對路徑編出來的：光是把專案搬到別的資料夾，名字就對不上，記憶等於憑空消失。同理，`C:\Users\vli\.claude\CLAUDE.md`（全域規則）也帶不走，所以跨專案規則若對本專案是關鍵的，要在這裡再寫一份。

**How to apply**：聽到「記住 / 記憶下來 / 以後都要…」時——

1. **必須當場生效**的規則 → 寫進 repo 根目錄的 `CLAUDE.md`（只有它每次自動載入）。
2. **領域細節、沿革、災情紀錄** → 寫進 `docs/dev/`，並在 `CLAUDE.md` 留一句指路。**只寫在 `docs/dev/` 等於沒寫**——那要有人想到去讀才載得進來。
3. 然後**一併提交推送**（本專案本來就是自動 commit + push，見 §3）。
4. **在回覆裡說清楚寫進哪個檔**，讓使用者知道換機器之後還在。

## 6. 收尾清掃：用一條完整的掃描指令，不要憑記憶手打

**這條失守過兩次**（2026-06-12、2026-06-14，使用者兩次都不高興）。兩次的成因**一模一樣**：我手打一條片段的 `rm`，漏掉 `--debug` 的疊圖 PNG（`*.debug.p*.png`）與臨時腳本。

⚠️ **根因不是文件缺漏**（`CLAUDE.md` 的驗證章節早就列了這些檔），而是兩件事疊在一起：手打指令會漏，而 `.gitignore` 已經涵蓋這些檔案，所以 `git status` 看起來是乾淨的、**把殘留藏起來了**。**乾淨的 git status 不等於乾淨的工作目錄。**

**How to apply**：每一輪修正的**最後一個動作**跑一次完整掃描，不要用眼睛掃：

```bash
rm -rf verify/ *.debug.json *.debug.p*.png dbg*.pptx dbg.* _dbg_*.py nul.* *.tmp.png
ls -1   # 目視確認只剩原始碼、設定檔、.bat 與產出的 .pptx
```

`ls -1` 那步是**強制**的——它才是抓得到「漏了一個 glob」的那一步。

⚠️ 永遠不要刪要交給使用者驗收的產出 `.pptx`。臨時檔一律寫到 scratchpad 目錄，不要落在專案裡。

## 7. 規則搬進 `docs/spec/`（2026-08-23）

使用者指示「CLAUDE.md 裡面可以搬移的內容，移到 `docs/dev` 去」，同一輪還要求「比照 `MP4-2-SRT` 的 `docs` 產出架構導讀與 spec 目錄」。兩件事其實是同一件：**那 78 條不變量本來就是規格書的內容，只是住錯地方。**

**搬之前的問題**：`CLAUDE.md` 113KB、每次對話整份載入，而其中絕大多數規則在任何一次對話裡都用不到。壓縮它的誘惑一直在，但那些句子的價值**全在細節**——門檻是多少、誤殺過什麼、前一版結論是什麼、哪三條替代路線量過而失敗。改寫成摘要等於毀掉它們，下一個人放寬門檻時就再也讀不到「這個值是這樣來的」。

**做法**：81 條頂層條目**逐字**搬進 `docs/spec/03`–`08`（規則 80 條）與 `11`（結構性風險那一條）（一個字都沒改，機器驗過每一條在且只在一個章節裡），`CLAUDE.md` 改留「規則本身 + 關鍵門檻 + 程式指路 + 詳見連結」的索引。CLAUDE.md 因此從 113KB 降到 49KB（−57%），而理由一句都沒有消失。

**為什麼索引仍要帶門檻數字**：只寫「見 spec 04」的索引擋不住任何事——agent 讀到規則名稱不會去翻章節，只會照直覺改。門檻留在自動載入的那一份，才擋得住「順手把 0.72 放寬成 0.6」這種改動；理由留在 spec，是給真的要動它的人讀的。

## 9. 自己下 Bash 指令的形狀：別寫成權限閘門攔得下的樣子

（自 `MP4-2-SRT` 移植 2026-08-23；原始查證 2026-08-15 讀 `claude.exe`。2026-08-25 從 `CLAUDE.md` 搬進來，那邊只留三條規則本身。）

Auto Mode 的自動核准是把指令交給分類器判斷，但**分類器只吃能被靜態解析的指令**。指令一旦被判為 `too-complex`，程式會設 `classifierApprovable: false`，**跳過分類器直接中斷去問使用者**——而且在 `settings.local.json` 加 `allow` 白名單**救不了**，因為對 `too-complex` 的指令，規則比對一律回傳 `unverifiable`。

三條規則：

1. **不在指令裡 `cd`** —— Bash 工具的工作目錄本來就在專案根目錄，需要別的路徑就寫絕對路徑。
2. **重導向目標寫死絕對路徑**，不可用 `$VAR` 或 `$(...)` 組出來（會被判 `Redirect target contains $(cmd) output — path is runtime-determined`）。
3. **`cd` 與輸出重導向不可出現在同一條複合指令**（`cd-compound-redirect`；程式碼註解寫的是「防止靠 cd 繞過路徑檢查」）。

能不重導向就不重導向，讓輸出直接回到對話裡。

⚠️ **連帶效應：工作區未被信任時，`.claude/settings*.json` 裡的權限規則會被整批忽略**（Claude Code 2.1.232 起，信任不再從上層資料夾繼承進 git repo，每個 repo 要各自確認一次）。症狀就是「每個工具都重新問一次」。

## 11. 第二次瘦身：`CLAUDE.md` 觸到上限時搬哪一段（2026-08-25）

`tests/test_docs_index.py::test_claude_md_stays_small` 的上限**當時**是 28,000 字元（⚠️ 2026-08-26 起是 **30,000**、2026-08-27 起是 **32,000**、2026-08-28 起是 **35,000**，三次放寬的理由都見那支測試自己的 docstring；下面這一段講的是 08-25 那天的事，數字照當時記），當天連續兩筆改動之後它到了 **27,765——只剩 235 個字元**，使用者指示「幫我搬一段到 docs，騰出空間」。搬完是 **26,768（剩 1,232）**。⚠️ **數字要照測試的數法量**：`Path.read_text()` 走 universal newlines，CRLF 併成一個字元，所以用位元組或 `newline=""` 量會多出「行數」那麼多（本檔約 200），憑那個數字判斷離上限多遠會嚇到自己。

## 12. 跨 repo 改東西：先跑三步判定，判定沒過才給 PROMPT（2026-08-27 立、2026-08-29 改判準）

**2026-08-27 的原規則**是使用者這句：「**以後如果 MP4-2-SRT 需要修正，不要直接去改，請給 PROMPT 我貼過去處理，否則會錯亂。**」

**2026-08-29 他把判準整個換掉**：「**可以跨 REPO 修改程式碼，不需要我的授權，但請先 ListAgents 確認沒有別的 session 也在改同一個 REPO，如果有的話，就不要跨 REPO 修改，改為給我 PROMPT 讓我貼的方式。如果發現沒有別的 session 在一起改的話，一定要先讀取跨 REPO 的 CLAUDE.md 後，再跨 REPO 修改。**」規則本身（三步判定）在 `CLAUDE.md`；⚠️ **原規則的理由沒有被推翻，只是「怎麼確認沒人在寫」從「一律假設有」換成「進去之前實際查一次」**——底下「為什麼會錯亂」那一段照舊成立，它正是判定沒過時要給 PROMPT 的原因。

**改判準的來由**：同一天下午修一個視窗還原的瑕疵時要同時動共用包與兩個下游，實際跑起來的樣子是——先按原規則被使用者打斷（「Stop 你應該給我 prompt」），接著他又兩次當場授權跨 repo 改。**規則與他真正要的東西不一致**，所以他改成「可以直接改，但進去之前自己排除『有人正在寫』」。

⚠️ **三步的順序是有意的，不要調換**：`git status` 最便宜也最硬（有未提交的改動就是有人動過還沒收尾，不必問）；`ListAgents` 次之，它只答得出「有幾個 session 活著」、**答不出它在哪個 repo**，所以那一格是**問使用者一句**而不是自己猜；讀對方的 `CLAUDE.md` 最貴、排最後（前兩步就否決掉的話根本不必讀）。

⚠️ **`ListAgents` 那一格為什麼是「問一句」而不是「一律給 PROMPT」**：定規則當下實際跑一次，18 個 peer 裡有 3 個非 offline，而**三個都跟這批 repo 無關**（兩個是雲端上的 Wiki 專案、一個是背景對話）。照「有活著的就不要動」實作等於永遠不能跨 repo 改，規則會退化回原來那條；而「問一句」的成本遠低於「生一段 PROMPT 讓他自己跑一輪」，答案又只有他知道。

⚠️ **第三步是被踩出來的**：同一天動兩個下游那次，共用包的 `CLAUDE.md` 有讀（`CLAUDE.md` 明令「動它之前先讀」），**姊妹專案那份沒讀**——只 grep 了提交規矩那幾行。而那份裡有一條寫得清清楚楚：「不要自動跨 repo 改東西……正確做法是提醒使用者 ＋ 生一段可以直接貼過去的 PROMPT」，跟使用者當場打斷說的那句是同一句話。**讀了就會知道那件事不該由自己做，而不是等被打斷。** ⚠️ **grep 幾個關鍵字不算讀過**：要找的東西正是「我不知道它存在」的那幾條，關鍵字想不出來。

適用範圍是所有姊妹 repo：`C:\SOURCE5\Python\MP4-2-SRT`、`C:\SOURCE5\Python\meeting-scribe`、`C:\SOURCE5\WIKI`、`C:\SOURCE5\FWIKI`。

**為什麼會錯亂**：那些 repo 各自有自己的 session 與自己的 `CLAUDE.md`。從這裡直接寫檔的話，那邊的對話完全不知道發生過這件事——它的上下文裡沒有這次的量測、沒有這次的理由，下一次它照著自己記得的版本繼續改，就會把剛改的東西改回去，或是在同一個地方做出互相矛盾的第二個決定。而且提交也會落在使用者沒有在看的那個工作目錄裡。

⚠️ **最容易踩到的不是「順手幫個忙」，是本 repo 自己寫著要「三個 repo 一起改」的那幾條**：

- `docs/dev/documentation.md` 的三層分層規範（三個 repo 各存一份、措辭要一致）
- 共用的版面尺規與色票（`SP_*`／`PAGE_PAD`／`CARD_PAD`／`CARD_GAP`、Apple 色票、squircle 皮膚），本專案 2026-08-26 卡片化就是照 MP4-2-SRT 抄的
- 從那邊移植過來的護欄（例如 §10「改壞了重試就把殘骸清掉」）

⚠️ 2026-08-29 之後這幾條**可以由你去改**，但**每一個 repo 都要各自跑一次那三步**——它們各有各的 session，判定要一個一個做，不是「這批 repo 一起過關」。

**PROMPT 要長什麼樣**：對方讀不到這裡的上下文，所以那一段必須自己站得住——

1. **改哪個檔、哪一段**（寫路徑與函式／常數名，不要寫「跟這邊一樣的地方」）
2. **改成什麼**（貼可直接用的片段或前後對照）
3. **為什麼**：門檻數字、實測、反例、量過而否決的路，**整段抄過去**。⚠️ 不要寫「同步本專案的作法」——那句話在對方的 session 裡是一個查不到的指標
4. **驗收怎麼量**：量哪個值、預期多少、跑哪一支測試

寫完在回覆裡明說「這一段是要貼到 `<repo>` 的」，不要混在本專案的說明裡。

⚠️ **講姊妹專案的檔案時，連「路徑的形狀」都不要寫出來**。本 repo 有兩支死指路測試，門檻不一樣：

| `tests/test_docs.py::test_docs_do_not_point_at_files_that_do_not_exist` | 只認**反引號包住**的 Python 檔名與 `docs/`／`tools/` 路徑 |

## 13. 別的 session 也在寫同一批 repo（2026-08-28）

§12 立下「姊妹專案不要直接改」的時候，共用包被寫成例外：「**改 winkit 就直接改、不繞 PROMPT**」，括號裡的理由是「那個 repo 沒有平行 session」。**那個前提當天就被推翻了。**

**當天的實況**：`ListAgents` 列出兩個 interactive session 正在忙——一個在姊妹專案、一個在共用包。而共用包那個 session 依它自己的七步，**也會改本 repo 的檔案**（第 5 步「把用得到這次改動的下游一併改掉」）。所以在本 repo 工作的這個 session，工作目錄底下同時有三方在寫。

**踩到的是什麼**：`/simplify` 收尾時我在本 repo 跑 `git add -A && git commit && git push`，把共用包那個 session **還沒提交**的 `tools/make_launcher.py` 一起掃了進去並推上去。那次改動是它把 `guard_note` 從手抄的字面值改成讀共用包的一個常數——而那個常數在共用包的 HEAD 裡**還不存在**。⚠️ **推出去的那個組合是壞的**：那時候有人 clone 這兩個 repo 的 HEAD，產生器會 `AttributeError`。而本機一路全綠，因為共用包的**工作目錄**已經有那個常數了。

⚠️ **失效方向最糟的地方是它不會叫**：`git add -A` 不會問「這個檔是不是你改的」，測試不會紅（本機看得到別人的工作樹），`git status` 事後也乾乾淨淨。最後對上是**碰巧**——那個 session 幾分鐘後把常數提交了。

**兩條規則**（`CLAUDE.md` 各有一句，共用包那份也更正了它自己的前提）：

1. **動共用包之前先 `ListAgents`。** 沒有別的 session 在跑才照舊直接改；有的話停下來問使用者——只有他知道另一邊做到哪。⚠️ 「這個 repo 沒有自己的開發活動」推不出「沒有人在改它」：**每一個下游 session 都是它的潛在寫入者**，那正是共用包 `CLAUDE.md` 開宗明義寫的事，當初讀漏了。
2. **有別的 session 在動同一批 repo 時，提交一律逐檔指定路徑**（`git add <路徑>`），**不准 `git add -A` / `git commit -a`**——包含**本 repo**，因為別人也會來改這裡。⚠️ 逐檔提交還有第二個好處：訊息裡講得出「**為什麼只提交這幾個**」，下一個讀 log 的人才不會以為那次改動就只有這些。

⚠️ **這條與 §12 不衝突、補的是另一半**：§12 管的是「不要去寫別人的 repo」，這一條管的是「**別人正在寫我的 repo**」。第二種偵測不到——對方不會來打招呼，而 `git status` 上那些檔案看起來就像自己剛才改的。

⚠️ **`ListAgents` 只看得到本機的 session**，雲端與 Remote Control 那些列得出來但狀態不一定即時。所以它是一道**便宜的前置檢查**，不是保證；真正的保護是第 2 條（逐檔提交），那一條不依賴任何偵測。
