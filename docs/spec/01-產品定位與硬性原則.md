# 1. 產品定位與硬性原則

## 1.1 產品的一句話定義

**把純影像的 NotebookLM 簡報 PDF，變成可以在 PowerPoint 裡直接編輯的 .pptx。**

每一頁以全解析度的頁面渲染圖當背景，疊上實心填色矩形蓋住點陣文字，再放上可編輯、樣式比對過的文字——字級、粗體、文字色、蓋板色**全部從影像估計**，沒有任何一項來自 PDF 的文字層（來源 PDF 根本沒有文字層，那正是這個專案存在的理由）。

取代的是 deckedit.com 這個線上服務。專案目標自 2026-06-11 起確定：**本地離線**（RapidOCR，不上傳任何內容）、**完整 DeckEdit 式輸出**（背景圖 + 色塊 + 樣式比對過的可編輯文字）、CLI 介面（後來另加桌面圖形介面）。

## 1.2 最高原則：所有調整必須具通用性

> 使用者指示 2026-06-13。這是本專案唯一凌駕於其他所有規則之上的一條。

**每一條規則／修改都必須對「未來任意新的 NotebookLM 簡報 PDF」有意義，不能只為了通過手上這一份。**

修正一個視覺問題時，要找出該問題背後**可一般化的成因與判別準則**——例如「線稿圖示被誤讀成單字」「背景有銳利明度階躍」「同段折行被 snap 雜訊拆階」——用通用條件去偵測與處置，並記錄其原理與反例。

**嚴禁針對單一頁面／單一字串硬編碼**（如「若文字==某某 則…」「第 N 頁特別處理」）——那對新檔毫無價值。

唯一例外是**已知無誤殺空間的辭典型修正**（如 `_CONFUSION_BIGRAMS` 只收非真實詞彙的穩定誤讀字對），且必須註明已目檢確認。**若某修正本質上只能針對某一份 PDF、無法一般化，必須先向使用者說明並取得確認，再決定是否寫入。**

## 1.3 這條原則長什麼樣子：三個對照

| 情況 | ❌ 不可接受 | ✅ 可接受 |
| --- | --- | --- |
| 某頁的圖示被讀成字母 X | 「文字 == 'X' 且在第 4 頁 → 丟掉」 | 「單一拉丁字母 + ≥28pt + 該列沒有其他真文字 → 判線稿圖示」（真的單字母內容一定有同列鄰字，不會在標題級孤立） |
| 某行的字級量得太大 | 「這一行改成 20pt」 | 「字墨帶被行首高圖示灌高 → 用 char box 框出真字範圍再量」 |
| 模型把某個詞讀錯 | 「若文字包含某某 → 換成某某」 | 先試三條原則性路線（局部重讀、模板 XOR、滑動對位 IoU），全部實測失敗後才收進辭典，且只收非真實詞彙的字對 |

## 1.5 名詞定義

| 名詞 | 意思 |
| --- | --- |
| **deck** | 一份 NotebookLM 匯出的簡報 PDF。回歸語料目前有四份，見 `CLAUDE.md` 的「驗證」章 |
| **偵測框 / OCR 框** | RapidOCR 偵測階段回傳的文字行外框。⚠️ **留白不一致**是本專案第二重要的不變量——任何「用框高的倍數去猜」的做法遲早會壞 |
| **字墨帶（ink band）** | 框內真正有字形墨水的列範圍。字級一律由它量，不由框高量 |
| **蓋板（cover）** | 疊在背景圖上、蓋住點陣文字的實心填色矩形 |
| **投影（glow）** | 這類簡報常給文字加的一層柔和暗色陰影，200dpi 下延伸 10–20px。它不是表面、也不是字墨，卻同時污染兩者 |
| **籌片 / 晶片（chip）** | 帶底色的圓角標籤或色塊 |
| **snap** | 把連續的字級估值吸附到 `FONT_SIZES` 的某一階 |
| **夾制（clamp）** | 因為右方有障礙或投影片邊緣，把字級壓到比自然估值小 |
| **折行組（wrap group）** | 同一段落被偵測器拆成的相鄰數行，必須共用字級 |

## 1.6 系統需求

- **Windows**（PowerShell COM 匯出驗證圖、cp950 的 `.bat`、`C:\Windows\Fonts\msyh.ttc` 量字寬——三者都綁 Windows）
- **uv**，Python 由 uv 準備，目前鎖在 3.14
- 建議有支援 DirectX 12 的 GPU（Intel Arc/Iris、AMD、NVIDIA 皆可），實測快約 4×

詳細的環境與相依鎖定理由見 `09-執行環境與效能.md`。
