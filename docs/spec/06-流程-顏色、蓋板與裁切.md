# 6. 流程-顏色、蓋板與裁切

這一章是「蓋板要鋪什麼顏色、鋪到哪裡」。兩個反直覺的事實貫穿全章：**環帶未必是表面**（文字自己的投影會把它染暗），而 **字墨邊界未必是蓋板邊界**（投影會從蓋板外露出來）。

⚙️ **動到顏色估計，或蓋板與裁切之前請先讀完這一章。** 實作上的落點（模組、函式名）見 §12。

> 這些條目原本住在 `CLAUDE.md` 的「架構」章，2026-08-23 搬進規格書；2026-08-24 改寫成技術中立，門檻、實測數據與反例一字未動。

## 6.1 底色從哪裡量

- **緞帶／色塊偵測**（環帶不是平面色時的退路）：當 OCR 框外圍環帶不是單一平面色時，取框內中段水平帶做雙色聚類並對各遮罩做**侵蝕** — 細筆畫會消失、實心緞帶會存活；存活者為蓋板色，另一個為文字色。單純的主色佔比判斷在這裡會失敗（量化會把緞帶色拆散到多個 bin）。

- **蓋板／文字色的分層情境**：只靠環帶取樣會以兩種方式失敗。
  - **(a) 文字位於灰帶之間的近白色橫條** → 環帶取到錯的帶；以「光暈修正」解決（蓋板色改取距筆畫 4–6px 的帶 — ⚠️ **緊貼筆畫的 3px 是被字色染色的反鋸齒區**，曾經悄悄偏移過整份文件的蓋板色），且光暈色只在與環帶色相差 ≥20 時才覆蓋（同一表面上環帶色更純）。
  - **(b) OCR 框溢出實心膠囊、壓到頁面背景** → 環帶看到外圍色、整顆膠囊被當成墨水；以「墨水佔比 ≥0.45 且侵蝕存活率 ≥0.45」偵測，再用 k=3 色彩聚類重推底／字色（最實心 = 膠囊、最細碎 = 筆畫）。⚠️ **重推底色必須與環帶色差 ≥40 才採用** — 密集粗體大字（p15「把精力保留…」墨水佔比 0.46）會誤闖此分支，把反鋸齒灰殼當文字色、整行刷成灰。

  文字色一律只平均「筆畫核心」（離底色最遠的前 30% 墨水像素），因為反鋸齒會把筆畫邊緣拖向背景色。

- **光暈取樣要「往外走到顏色穩定」，不能只取一圈**（使用者回報 2026-08-23）：上一條的 (a) 直接把「距筆畫 3–6px 的環」當成表面色，**卻從來沒有驗證過那一圈是不是表面**。`AI_Quality_Guardrails` 這份 deck 的白字全都帶一層**柔和暗色投影**（200dpi 下實測延伸 10–20px），3–6px 的環整圈落在投影裡 → 藍籌片 [81,144,201] 的蓋板畫成 [83,129,169]、橘色橫幅 [196,106,73] 畫成 [162,97,70]，p11–p15 共四十幾行出現「比籌片深一階」的色塊（p6/p7/p10 也中）。

  **修法**：從字墨往外一次走一段 3px 的帶（3–6、6–9 … 15–18），**只有當下一段與這一段一致（Chebyshev ≤5，稱為「穩定」）才承認那是表面**；平坦表面在第一段就成立（與舊行為等價），投影則會一路漂移、直到融進填色為止；五段走完仍不穩定就回報「找不到表面」、環帶色照舊生效（≥20 才覆蓋的閘門不動）。

  判別依據是實測分離出來的：**真的「環帶取錯帶」case 逐段完全平坦**（`Transformer_演進地圖` p1 [192,235,236]→[191,235,236]、p11 Query 一路 203–206、`The_GPT_Blueprint` p7 242–244），**投影 case 逐段單調逼近環帶色**（p13 Hook 164→178→185→190→193，環帶 197）。四份 deck 1158 行掃描：舊規則觸發 49 次，新規則保留 4 次真表面覆蓋、其餘 45 次改回環帶色。

  兩個附帶要點：**(i)** 環帶膨脹**不可繞回影像對邊**，否則走到 18px 會把字墨環抹到裁切的另一側（現行實作踩過的那顆地雷見 §12.6）；**(ii) 底色正確之後，右側餘裕掃描才會準** —— 它拿 `bg_rgb` 當「自由欄」判準，投影會讓掃描提早撞牆、把字級夾小；修好之後 p14 規則檔骨架／決策日誌、／內建 Review／故障注入／Log 讀取分析 由 20 回到 24，目視與原稿一致。

  **已知未涵蓋**：p13 五張並排卡片中，第四張（讀紀錄檔／（抓未知／失敗模式，全是 4 字短行）因此完全不受夾制、snap 到 28，另外四張卡的最長行仍被卡框夾在 20，原稿五張同字級卻輸出 20/20/20/28/20。成因是 YaHei 比來源字型寬、長行必被夾（舊版是靠錯的底色「意外」把第四張也夾下去），屬既有限制。**已於 2026-08-23 由使用者裁示並修掉**——見 §4 的同列字級傳遞（多數決），現在輸出 20/20/20/20/20。

- **底色要在投影之外重新取樣，取離投影最遠的那一段邊**（使用者回報 2026-08-23）：環帶半徑 **4px** 貼在「本來就緊貼字形」的框外，所以**環帶自己也在投影裡**，蓋板比籌片暗個幾階；小色塊看不出來，大片平整填色就變成一塊淡淡的方形（p14 橘色警告橫幅：蓋板 [194,104,72]、旁邊橫幅 [200,106,73]）。

  修法：量到投影（`glow_px > 0`）時把環帶整個外推再讀一次**四個邊**，取**離投影色（表面探測回傳的第一段帶色）最遠**的那一段 —— 投影只會把樣本往自己的方向拉，所以同表面上離投影最遠的那段汙染最少。兩道閘門擋掉「已經不是同一個表面」：該段主色與原環帶差 **≤20**、主色佔比 **≥0.55**（p14 第一行的下緣段已離開橫幅落到頁面上，[254,242,227] 佔比 0.38，兩關都不過）。實測 p14 橫幅 → [201,106,74]（真值 200–201）、p13 藍卡 → [82,143,199]（真值 [84,143,199]）、p11/p12/p15 皆 ±2 內；四份 deck 掃描只動底色、不動任何字級。

- **重新取樣的半徑要比蓋板的伸展量少一段**（2026-08-23 code review）：`glow_px` 是**蓋板**要吃掉的距離（確認帶的外緣），把重新取樣的環也推到那麼遠會走出填色——四份 deck 實測 16 行底色漂移 7–14 個單位，其中數行整個落到鄰近表面（`Transformer_演進地圖` p2 `Pre-RMSNorm` 248→234、p4 的 K 籌片）。而且「取離投影最遠的一段」這條選擇規則天生偏好漂到亮鄰居的那一段。取樣改用 `glow_px` 減一個帶寬（3px），蓋板維持外緣。

- **筆畫核心跨底色兩側要選單側**（使用者回報 2026-06-14）：當「離底色最遠的前 30% 像素」**同時含比底色暗與比底色亮的兩群**（彩色／3D 框上有暗邊框／陰影＋白字：p12「開發」灰色 3D 按鈕暗邊框＋白字、p14「根本沒提早完工」暗卡片＋白字），把兩端平均會得到無意義的中灰 [172,176,177]、白字被刷成灰幾乎隱形。

  **解法**：核心像素跨底色兩側時收斂到單側——有**夠多亮像素（≥0.2）即判淺色文字取亮側**（這類簡報每個填色框都是白／淺字），否則亮像素只是反鋸齒雜點、取暗側。對「全部同側」（一般深字白底、白字純色底）是 no-op、不動既有校準。全文修好 p12 開發、p14 根本沒提早/重啟計量、p13 灰塊 確診/繪製 等白字，深字行（p2/p3/p5/p9/p11 內文）零回歸。**未涵蓋**：純暗照片上的黑字＋白光暈（p5「高耦合金流邏輯」橘色電路球上）——底色取到照片色、非框，仍 faint。

- **淺色／描邊文字落在彩色表面 → 取飽和表面為底**（統一判別，放在混合環帶分支最前、優先攔截；使用者回報 2026-06-14）：白字、或**黑字加厚白色描邊**落在彩色／紋理表面上時，混合環帶分支的存活率／膠囊啟發法會把厚白邊誤當底色、蓋板畫成白底黑字（p8「日曆與/依賴卡死」白邊黑字在紅磚牆、p14「資料授權請求清單」黑字白邊在深藍面板）。

  **判別**：全框 k=3 叢集若**同時有近白群**（min ≥200、佔比 ≥0.15＝白字或白描邊）**與飽和表面群**（min <200、max−min ≥45、佔比 ≥0.18＝磚／晶片／面板）→ 取最常見的飽和表面為底、近白為文字色。白字落在飽和晶片（無描邊）走同一條、結果一致。環帶太雜（紅磚佔比僅 0.24）也無妨，靠全框叢集而非環帶主色。閘門天生排除：黑字白底（無飽和表面）、灰機器面板上的白字（max−min <45、不飽和→不觸發、走原存活率路徑給白字）。p8 Guardrail 黑字（無近白群）不觸發。

- **黑字＋白暈在「淺色表面」→ 取近白為底、暗字為文字**（放在存活率分支之前；使用者回報 2026-06-14）：上一條的飽和表面判別需要有飽和叢集；但 p5「高耦合金流邏輯」是**黑字＋白色光暈在一條白色帶上**（環帶 [233,237,240] 近白、全框只有白＋黑兩群、無飽和表面）。存活率啟發法假設文字是細筆畫、會被侵蝕——但**粗黑字的筆畫比薄白暈更厚、反被當底**（→ 白字黑底，與使用者要的「深一點」相反）。判別：兩叢集為 {近白(min≥200), 暗} **且環帶近白(min≥180)** → 文字坐在淺色表面上、取近白為底、暗叢集核心為文字 → 黑字白底。白字深底的環帶是暗的、此分支跳過、存活率照常給白字。

  **仍未涵蓋的尺寸**：高耦合字級量成 28（應 ~24），因底部一條中性暗邊與字僅隔 5 列（<8 切組門檻）、又是覆蓋率 0.01 的微弱列卻仍過「最小字墨列高 3px」、把帶撐高一階；「稀疏邊緣列裁切」已記載試過並撤回（曾把 44pt 標題裁成 40，見 §11.2），故字級暫留。

- **描邊文字在彩色晶片上：膠囊分支會把白邊當溢出膠囊底**（使用者回報 2026-06-14）：晶片色環帶佔比 ≥0.55、底色直接設對（金／綠），但**白色描邊夠厚使墨水佔比 ≥0.45 觸發膠囊重推分支**，分支把「最實心叢集」＝白描邊當成溢出膠囊的底色 override 成白（p13「提速效果」在金晶片、「擴展與制度重構」在綠晶片 → 白底黑字）。守衛：重推底色**近白（min ≥200）而環帶色明顯較暗（min <170）** → 那是描邊文字的白邊、非膠囊 → 保留晶片色為底、把白邊設為文字色（不 override 成白盒）。真正的溢出膠囊底色是飽和晶片色（非近白），不受影響。全文 提速效果／擴展與制度重構 觸發、白字白底案例（白字深底晶片）零回歸。

  ⚠️ **這道守衛自己也要有守衛：環帶色必須真的填滿框內 ≥`RING_INSIDE_MIN`(0.25)**（使用者回報 2026-08-25「PAGE 12 陳 X 豪 X 豪 的底色跟原稿不同，原稿是白底」）。**失效形狀**：文字其實是**淺色牌子上的深色字**，而牌子躺在一張彩色卡片裡；OCR 框比牌子高一點（實測上下各溢出 10–16px），環帶因此整圈落在卡片上、佔比 0.686 ≥0.55 → 底色先被判成卡片色；整片白牌子接著都算墨水（`ink.mean` 0.898、存活率 0.922）而闖進膠囊分支，重推出來的「最實心叢集」正是白牌子（近白）、環帶又明顯較暗 → 上面那道守衛把**牌子當成描邊、卡片當成底**，輸出藍底白字（原稿是白底黑字）。

  **判別**：描邊文字是**坐在**晶片上的，字與字之間看得到晶片色；只是溢出牌子的框則只從溢出的那幾列看得到外圍色。量「環帶色在框內的佔比」（Chebyshev <40）即可分開——五份 deck 全部 156 行「彩色底＋近白字」的真陽性最低 **0.295**、中位 **0.61**，而兩個誤判是 guardV2 p12「陳 X 豪 X 豪」**0.069**（白牌子在藍色藍圖卡片裡）與 guard p1「Data Ingestion」**0.151**（線稿圖裡的白底標籤），門檻取 **0.25** 落在兩者中間。守衛不成立時就落回膠囊分支原本那一支（存活率差 >0.15、與環帶色差 ≥40），實測分別得到底色 (239,242,240)／(234,240,244)，與原稿一致。

  ⚠️ **量「框中央帶」的佔比行不通**（試過並否決）：真陽性的大字會把中央填滿字形、晶片色反而只剩 0.02–0.10，比誤判的 Data Ingestion（0.280）還低，兩群完全重疊。要量就量**整個框**。

  **仍未涵蓋**：白暈在**照片**上（p5「高耦合金流邏輯」黑字白暈在橘色電路球）——白暈太寬使環帶佔比 ≥0.55 直接當底、且墨水佔比 0.46 誤闖膠囊分支把橘照片當底，文字估成灰、字級被白暈灌高；密集粗體＋白暈＋照片三者互相干擾，動之風險高（會碰 p8 Guardrail／p15 校準），暫留原樣。

- **混合環帶的文字叢集可能是反鋸齒殼**：環帶混雜分支選出的「文字叢集」對 p8 Guardrail 1 整個是反鋸齒殼＋晶片外框（灰 ~190），真正的黑筆畫太稀疏沒成叢 — 文字被刷成淺灰。以選定底色重算的墨水遮罩，其核心色若比叢集 override 離底色遠 ≥60 → 信任墨水核心。此修連帶把 p8 時間軸五個月份標籤從反鋸齒灰救回黑色。

- **無蓋板救援**：斜置籌片（p8 等距視角的綠色平行四邊形）的軸對齊框同時罩到籌片＋頁底＋鄰籌片，環帶混色、雙色聚類也失效（兩個叢集都是實心面、無侵蝕存活差）→ 底色判「沒有值」→ 透明文字疊在點陣數字上出現重影。救援：取字墨帶光暈（膨脹 3→6 的環）主色，佔比 ≥0.65 即當蓋板色；漸層／插畫區主色不純、維持無蓋板。

- **同晶片堆疊文字共用底色**（使用者回報 2026-06-13）：一塊純色晶片上垂直堆疊的多行，逐行底色估值偶爾漂移、害蓋板畫出色差接縫（p7 藍色 Synthesize 晶片：步驟名「Synthesize」量成 [59,95,162]、晶片其餘行 [55,99,184]，蓋板出現一塊深色框）。把**垂直緊鄰、x 重疊、同文字色、底色相近（Chebyshev ≤40）**的行歸組、各行底色取組內逐通道中位數。閘門排除 `bg_segments`（雙色橫幅）與不同填色（>40）。全文除 Synthesize 的接縫修正外，其餘變動皆 ≤2/通道（同組噪聲正規化、肉眼不可見）。

  ⚠️ **合併之前要再檢查一次整組**（2026-08-29，使用者回報「好幾個 label 底色有問題」）。上面那三道是**配對**述詞，而分組用的是**遞移閉包**：A 與 B 相鄰、B 與 C 相鄰，A 與 C 就被併在同一組——**即使它們坐在完全不同的底色上，而且從來沒有被比對過**。一張表格正好把這個破口撐到最大：儲存格垂直排列（垂直緊鄰）、同一欄上下對齊（x 重疊）、文字都是黑的（同文字色），於是整張卡片被串成一組。實例（原則八 p1）：9 行、橫跨 x 134..1797，成員原本**各自都估對了**四種不同的底色——表頭灰 [224,223,219]、儲存格白 [249,245,235]、橘色警告框 [254,229,197]、卡片標題 [234,234,230]——取中位數之後全部被塗成 **[248,234,230]，一個那張投影片上根本不存在的粉色**。

  判別：**組內極差**（逐通道 max−min）> `CHIP_BG_SPREAD`(25) 就整組放棄，不改配對條件。理由是這條規則的本意就是「同一塊底的多行只差取樣雜訊」。⚠️ **門檻不能用配對那個 40**：假組的極差 39 剛好在 40 以下（單獨配對時也過得了），因為鏈上每一步都合法。

- **文字坐在對稱漸層表面上：底色取「這一行起點」的顏色，不是主色**（使用者回報 2026-08-29，`Principle_8_Engineering_Blueprint`）：金屬牌、浮雕橫幅這類表面會在**中央打一道高光**，所以一行字底下的表面是「暗 → 亮 → 暗」。本章前面每一條估色規則最後都收斂到「一個主色」，而在這種剖面上，主色就是那道高光 —— 蓋板因此畫成一塊**兩端比牌子亮 ~70 個單位**的淺色板，讀起來像在牌子上貼了一張白紙（實測那一頁三塊牌子：蓋板 [209,218,224]，牌子兩端 [148,162,170]）。

  **判別剖面**：沿用背景分段那一套逐欄背景色（框上下緣列的中位數，再做 5 欄平滑），對它做**二次擬合**。三道閘門，門檻與餘裕都是在六份 deck、1284 個有底色的行上量出來的，三道合起來**恰好命中那一頁三塊牌子上的六行、其餘全不動**：

  | 閘門 | 門檻 | 命中的六行 | 最接近的落選 |

  | 擺幅（端點與中段的 Chebyshev） | ≥30 | 32.8 – 73.2 | 20.7 |
  | 二次擬合殘差（逐欄 RMS 的最大通道） | ≤8 | 2.50 – 6.77 | 23.5 |

  - **擺幅**分開「真的有漸層」與「平坦表面」；平坦表面的環帶色本來就是對的，不該動。
  - **擬合殘差**分開「平滑的斜坡」與「有立體感的東西」。⚠️ 這一道是**擋住圓柱與插畫的唯一判別**：同一頁閥門上的 `Valve` 擺幅高達 70（管身右側是深陰影），只有殘差 13.8 攔得下它。
  - ⚠️ **兩端一致這道不可省，它排除的是「單調漸層」**：`Transformer_演進地圖` p8 的 `Mixtral 8x7B` 坐在一塊**青綠 → 琥珀**的漸層晶片上（兩端相距 198）。對稱漸層取端點＝取表面本體色，兩端都接得上；單調漸層則**取哪一端都輸** —— 選了起點，蓋板另一端就整整差一個色距。這種行維持原本的主色。

  ⚠️ **這道判別必須排在背景分段偵測之前**：分段偵測的說明寫著「漸層會合併成一個 run」，但那只對**緩**的漸層成立 —— 陡到跨過合併門檻的漸層會被切成**階梯狀的假色塊**，而每一塊自己都夠平、相鄰塊色差也夠大，三道平坦度檢查全部通過（那頁中央的牌子被切成 暗｜亮｜暗 三塊，接著行內 highlight 那一支就挑走了中間那塊高光）。二次擬合直接分開這兩件事：**畫上去的填色是階梯，牌子的光澤是斜坡**。全語料 1284 行裡，分段偵測命中 11 行、漸層判別命中 6 行，**兩者同時命中的只有那三行被切成階梯的牌子**，所以這個順序不動任何一個真正的分段案例。

  **連帶效果（不是回歸，但要知道）**：底色改對之後，那一頁 `，搬家當天直接死。` 的字級從 12 變成 14。成因是**底色錯誤會經由「同款孿生」傳染到不相干的行** —— 舊的高光底色 [209,218,224] 與右下角表格那一行的 [217,225,230] 只差 8，落在孿生判別的「同底色 ≤25」之內，於是左上金屬牌的標題**跨過半個版面**把它拖低一階，碰巧拖近了真值。底色修對後兩者差 38、拖動消失，那一行退回自己的量測值 13.78 → 14。⚠️ **真正的缺陷在別處**：它的框頂與上一行的框重疊 8px、字墨帶被上一行的字底灌高，本該由堆疊重疊字級調和（形狀 A）接住，卻因為兩行**粗細判定不同**而被那一支的「同卡＝同字重」閘門擋掉。修它要放寬那道閘門，屬另一件事。

## 6.2 一行之內有多種顏色

- **多色行**：用逐字 word box 取每個字的顏色並分組成 run（合併門檻 ≤45、**只有色差 ≥60 才真正分段** — 不對稱門檻防止模糊雜訊拆散單色行）。run 的字數涵蓋「去空格」後的文字；`Line.char_boxes` 攜帶字框，凡是破壞字元 1:1 對應的轉換（救援）都要把它設為「沒有值」。**夾在兩段同色 run 之間的單字 run 是 CTC 字框抖動**（p4 Idempotent 的尾 t 字框壓到「(」字縫、取到反鋸齒灰 150）— 併回鄰段，不要讓單字雜訊拆 run。

- **行內多重背景填色（雙色橫幅＋行內 highlight）**（使用者指示 2026-06-13）：一行可能橫跨多塊不同背景填色——整行的雙色橫幅（p2「採用 BSD 授權…」前半深底白字、後半白底黑字），或行內被 highlight 的程式碼／關鍵字色塊（p2 `Perl`／`Email`／`Markdown`／`Markdown.pl` 淡紫／淡藍碼片、p6 `==螢光筆==` 紫色塊）。

  用**框上下緣列**（字帶外的純背景，不受字墨密度影響——全欄中位會被密筆畫拉黑、單一參考底色的墨水遮罩在橫幅遠側會反相）逐欄取背景色，再以游程編碼（running mean，相鄰欄差 ≤26 併為同一塊）切成數塊平整填色。

  **通用閘門排除漸層／照片**：漸變欄會逐步併成一塊；任何塊自身欄色 std > **16** 即整行作廢（漸層／照片永遠收斂不成平整塊）；相鄰塊色差需 **≥32** 才算刻意。內部邊界精修到**逐通道中位交界中心**（視覺幾何交界、天生落在字間空隙）——⚠️ **不可貼齊 char box 空隙**：char box 有 padding（p2「個」墨水到 ~1911、框卻灌到 1931），貼齊會把色塊往右推 27px、突出到鄰塊（使用者回報）。

  **分界兩側文字色是否不同，決定保留或移除色塊**：
  - **(a) 文字跨塊變色（橫幅白↔黑、p6 螢光筆紫↔白）→ 保留色塊**，並逐字按所屬區段背景量色（否則白底會被當墨水量成白字）。`bg_segments` 存各區段 `(x0,x1,bg)`；輸出時**先鋪一整條最右側填色的全寬底板**（接縫永不露出底圖、即使色塊被手動微移）、再把較左區段疊到各自邊界、最後疊透明文字框承載分色 run。
  - **(b) 文字同色的純行內 highlight（Perl／Email／Markdown／Markdown.pl）→ 移除色塊**（使用者指示 2026-06-13）：色塊畫在原稿欄位，但**輸出字型步進寬與原稿不同**、中段字前面累積位移、色塊對不上文字（使用者否決）；純深字落在底色上仍清楚，故設 `highlight_removed`、改用**符合環帶背景的底色**（⚠️ **不是最寬區段**——Markdown.pl 的紫塊比周圍文字寬、取最寬會把整行刷紫）整片蓋掉原稿色塊，蓋板涵蓋整框高 ±max(8, 0.12h)（色塊常溢出 OCR 框幾 px、不夠寬會露一條）。

  全文 5 處 highlight ＋ 1 橫幅全數偵測命中、零誤判（已逐一比對原稿）；其餘行維持單一蓋板。

## 6.3 蓋板鋪到哪裡

- **蓋板要吃掉文字自己的投影，堆疊的同色蓋板之間不可留縫**（使用者回報 2026-08-23）：底色修對之後**殘留的投影反而現形**——舊版蓋板本來就是投影色，與框外的投影融成一片看不出來；蓋板改成正確的籌片色，框外那一圈投影就變成沿著蓋板邊緣的暗框。三個方向都要處理：
  - **垂直**：蓋板高原本是「字墨 ± max(4px, 0.08×字墨高)」，p13 卡片內文只有 9px，而投影量到 10–20px。表面探測走了幾段才穩定就是投影半徑（settle index i → `3 + 3(i+2)` px，取**確認帶的外緣**；**第一段就穩定＝沒有投影＝0**。內緣曾用過，但「穩定」容許 5 個單位殘差，邊界上還留著約 9 個單位的投影——p14 橫幅最後一行下緣露出一條，2026-08-23 改成外緣，**實測該行 dy=12 的殘差 8.7 移到 dy=15 的 4.x，目視消失**），存進 `Style.glow_px`，垂直 pad 取 `max(4, 0.08h, glow_px)`。
  - **水平**：OCR 框左右留白不一致（p13 Hook 左邊有 22px、`(無腦零等待)` 的左括號只剩 4px），後者整條左緣露出暗痕。蓋板水平外擴從蓋板邊往外走 `glow_px` 欄、**碰到任何真墨水就停**（卡框、牽引線、鄰字都是墨水），所以吃不到卡片邊框。
  - **行與行之間的縫**（最明顯的那條）：p13 同卡兩行字墨相距 35px、上下各 pad 9px → 中間 17px 沒被蓋到，而那 17px 正是上一行投影的尾巴。堆疊裁切原本只處理「兩塊蓋板重疊」，上塊底 ≤ 下塊頂就直接跳過；改成**縫也要處理**、兩塊在接縫中點會合。四道閘門避免灌滿真的間隔：(a) 至少一方 `glow_px > 0`（**黑字白底 glow=0，這條規則對它完全不作用**，格線紙背景不會被塗掉）、(b) 兩塊底色差 ≤20、(c) 縫寬 ≤ max(8px, 0.5×較小字墨高)、(d) 縫內整段無墨水（同一個 >60 門檻）。三行以上的卡片天生安全：跨行配對的縫裡有中間那行的墨水，(d) 就擋掉了。
  - **仍未涵蓋**：p14 橘色警告橫幅蓋板量到 [194,104,72]、橫幅本體 [200,106,73]，差 6，放大仍看得出一塊淡方形。成因是**環帶自己也在投影裡**（環帶半徑 4px 貼著框、框又貼著字），而往外走到 18px 也只回到 [197,105,72]；橫幅本身還有紙紋與暗角，平整填色無論如何都會現形。**後續（2026-08-23 使用者再報，已修）**：外推整個環帶取「主色」確實沒用，但**取「離投影色最遠的那一段邊」有用** —— 見 §6.1 的重新取樣那條。

- **蓋板裁掉框緣外溢的彩色圖示**（使用者指示 2026-06-13）：偵測框左／右緣常外溢吃進鄰近的彩色狀態圖示（p13「Not That」左邊的紅 ✗、p11 Tip/Warning 的 ℹ/⚠），單一蓋板就把晶片色塗在圖示上、且粗體文字擠到圖示旁。判別用**色彩飽和度**（max−min 通道 >60）：紅 ✗／綠 ✓ 圖示飽和度極高，而帶色文字（藍／紫連結）只是輕微染色（<60），可分。收窄量存進 `cover_x0_px`／`cover_x1_px`。

  三道閘門防誤裁正常文字：(a) 行首／尾字必須是真字母／CJK（行內 `×` 是內容、不裁，否則會重出一個 × 字）；(b) 圖示與文字間須有**空白欄縫**隔開（`結論：` 開頭染色但無縫 → 不裁）；(c) 裁掉後文字區仍須夠寬（>20px，整行就是圖示的「X」不裁）。

  ⚠️ **第四道閘門：文字本身飽和時整條停用**（使用者回報 2026-06-13）：飽和度判別只在「文字是深色、圖示才是飽和色」時成立。鮮豔色的標題／標籤（p2 橘色「現狀痛點」飽和 110、棕色圖表註解「傳統 RAG」飽和 78）整行每欄都飽和，邊緣掃描會停在文字內某根稀疏筆畫欄、把真的邊緣字裁掉 — 現狀痛點尾端的「點」被露出、傳統 RAG 行首「傳」被重出成「傳傳」。全文每一次觸發裁切的行都是這種鮮豔文字行（p13「内容矛盾」等真圖示案例文字與圖示同棕色、掃描根本停不下來、本就不會裁），故 `text_rgb` 飽和度（max−min）>60 時直接不裁 — 同色圖示無法用飽和度與同色文字分離。

  ⚠️ **第五道閘門：裁切點不得切進逐字框的範圍**（使用者回報 2026-08-25）：**圖示按定義就不在 OCR 文字裡**，所以逐字框宣稱是文字的地方一律不准裁。第四道閘門看的是**整行的主文字色**，而一行**兩種顏色**時主色是佔多數的那一種——`guard V2` p7 的「規格層：44.4」前綴是黑字（飽和度 1）、數字是鮮橘色，閘門完全看不見，於是掃描從行尾一路吃掉整個 44.4（580px 的框裁掉 275px）：蓋板停在「規格層：」，點陣的 44.4 從蓋板外露出來，疊上可編輯的那一份之後畫面顯示「規格層：444.4」。

  五份 deck 實測，加上這道閘門後**16 條裁切剩 9 條**，消失的 7 條全都是在裁自己的文字：`guard V2` p7「規格層：44.4」（−275px）、p8「70% 的測試住在…」（−146px，行首橘色的 70% 被吃掉、重出成「70% 70%」）、`rlbp` p5「在每個時間步 t，智能」（−169px，藍色的「智能」重出）、`rlbp` p10「10.519.B 15.615.0」（−117px）、`trans` p11「MoE(Mixtral/DeepSeek 架構)」（−76px）、`gptbp` p8「Input」（−27px）、`trans` p3「matmul」（−17px）。**保留的 9 條一條都沒變**（`trans` p11 那頁匯出的 PNG 與改動前逐像素相同），因為真的圖示不在逐字框裡。⚠️ 逐字框被清成「沒有值」的行（任何破壞字元 1:1 對應的修正都會清）退回原本的四道閘門。

- **同列重疊框要裁切**：偵測器會把框外擴壓進同列鄰行的字形（例：「…書）」框尾蓋進「再批次…」框頭 43px），後畫的蓋板就會塗掉先畫的鄰行文字。在渲染圖上找兩段字墨間最寬的空白欄縫、把兩框各裁到縫中線兩側（各退 3px 邊距）；縫被實心墨水填滿時退而取重疊區中點。

  ⚠️ **嵌套框必須整對跳過、且邊界要鉗回兩框之內**（2026-08-16 審查）：閘門只擋住「b 從 a 的右緣之外開始」，擋不住「b 整個窄框落在 a 的寬框裡」（`bx1 ≤ ax1`）——那不是接縫重疊，取中點會把寬框腰斬、又把窄框裁成 `x0 > x1`，算出**負寬度**，PowerPoint 直接判檔案損毀要求修復、該塊文字消失。空白欄縫的掃描視窗還會伸出兩框之外（`x_lo = bx0−8`、`x_hi = ax1+16`），勝出的 run 可能整段落在框外，所以邊界另需鉗進 `[ax0+2·pad, bx1−2·pad]`，裁完再檢查兩框都沒退化。

- **垂直堆疊框要裁切**（緊接同列裁切之後跑；使用者回報 2026-06-14）：上下堆疊的兩個單行框其字墨帶若重疊，上框蓋板底會塗掉下行字頂（p8「單一」蓋住「主專案」上半成亂碼、p10「Legacy」蓋住「Codebase」——偵測框在 y 軸重疊但字形不重疊）。在 x 重疊區用各塊自己的底色算墨水遮罩，找兩字墨帶間的空白列縫。閘門：x 重疊 ≥0.5×min 寬、兩蓋板 y 確實重疊。

  ⚠️ **要裁的是「實際塗出來的色帶」而不是字墨界**（2026-08-16 審查）：裁 `ink_top_px`／`ink_bottom_px` 根本分不開兩塊蓋板——輸出階段之後會把色帶重新推導成「字墨 ± max(4px, 0.08×字墨高)」，等於把這一遍剛買到的 6px 間隙又還回去。實測重疊量：20pt −0.2px（剛好不碰）、24pt +0.96px、28pt +2.11px（就是 p8 單一／主專案）、40pt +5.6px、60pt +11.4px ⇒ **p8/p10 的修正在 ≥24pt 只是部分生效、字級越大越糟**。

  改成把最終色帶寫進 `cover_band_px`（單一 tuple，半設狀態無法表示）、輸出階段有覆寫就直接用；**覆寫之後仍要再套一次「自帶底色的 leading 延伸」**，覆寫才可以直接用原始幾何寫入而不會靜靜丟掉那 0.20em（也因此 `--no-cover` 下方色塊被推下去的值會自動被夾回字形位置，裁切端不必自己分模式），連帶讓 `highlight_removed` 那條（色帶取自原始框 ±max(8, 0.12h)、完全不看字墨界）第一次真的能被裁到。對照組：水平方向的同列裁切本來就是精確的（退 3px 邊距、輸出端再加回同一個 3px），兩邊做法要一致。空白列掃描視窗也要涵蓋「只有 pad 重疊、字墨其實已分開」的配對（視窗取 `min(itop_lo, ibot_up)−6 … max(…)+6`）。

- **文字垂直定位**：形狀同時身兼蓋板（必須涵蓋整個 OCR 框）與文字容器（字形必須落在點陣字墨上）。小字時偵測框上緣留白會大於行高補償、兩者衝突 — 解法是用**上內距**解耦，⚠️ **絕不要移動形狀頂端**。

## 6.4 色塊畫在哪：`--cover` 與 `--no-cover`

- **`--cover` / `--no-cover` 只決定「色塊畫在哪」，不是精緻度開關**（2026-08-16 審查）：`--no-cover` 的用途是讓底色長在文字方塊自己身上，**在 PowerPoint 裡移動文字時底色跟著走**；它**不是**「關掉蓋板機制」。三件事因此**不可**掛在色塊模式旗標上：
  - **(a) 同列／堆疊裁切**本來就沒掛（它們是幾何修正），但 help 與 README 曾宣稱有，說明必須改掉。
  - **(b) 雙色橫幅的分段蓋板**：`bg_rgb` 只記**最右段**的顏色而 `runs` 仍逐段上色，跳過分段蓋板會把整行刷成右段色、左半白字變成白底白字整段消失、連底下的深色點陣也一起蓋掉（p2「採用 BSD 授權…」）—— **一個形狀承載不了兩種填色**，所以兩種模式都要畫。
  - **(c) 弧形切線段**：弧形蓋板在 `--no-cover` 直接返回，若弧形切線段還硬設成透明填色，弧形就成了全份唯一「可編輯文字透明疊在點陣原字上」的重影（p3 緞帶）—— `--no-cover` 時改讓切線段自帶 `bg_rgb`。另外**弧形幾何量測**（在全解析度圖上做三點字墨掃描）**必須在色塊模式閘門之後才呼叫**，否則整段算完就丟。

- **預設是 `--no-cover`，而且理由是可維護性、不是外觀**（使用者指示 2026-08-24）：兩種模式在 `guard` 的十五頁上做過完整 A/B——PowerPoint COM 匯出 1376×768，逐像素比對。

  **視覺：兩者是平手。** 差異最大的一頁（p15）只有 **0.22%** 的像素差異超過 8 個灰階，p2/p4/p6/p7 完全相同，其餘落在 0.01–0.13%。而且差異的**形狀**是固定的：全部集中在色塊上緣的背景格線上，因為 no-cover 的色帶頂端是 `ink_top − 0.20em`（見下一條）、cover 的是 `ink_top − pad_v`（≈0.09em），兩者差約 4pt，剛好切過那些髮絲線。**沒有一頁有可辨識的視覺劣化**——所以這題不是取捨。

  **決定權因此落在編輯性，而 `--no-cover` 贏在兩點：** **①** 形狀數 **255 vs 463**（文字形狀兩邊都是 227，差的 208 個全是純色塊；檔案大小只差 5 KB，頁面圖佔絕大多數）。**②** 更重要的是**一致性**：`--cover` 並不是「一律分離」，仍有 **19 行**自帶填色（雙色橫幅、行內 highlight、弧形切線段——一個形狀承載不了兩種填色，見上一條），而使用者**沒有任何視覺線索**能分辨哪一行改底色要點一層、哪一行要點兩層。`--no-cover` 則是 227 行全部同一種操作方式。

  ⚠️ **`--cover` 唯一實質勝出的情境是「刪掉一行」**：色塊留在原地繼續蓋住點陣原字，真的變空白；`--no-cover` 刪掉文字方塊等於連底色一起刪，**背景圖裡的點陣原字就露出來了**，而那是圖片的一部分、再也刪不掉。這一點有簡單解法且已寫進 README 的「編輯輸出的 PPTX」給使用者：**清空文字內容、保留形狀**（填色掛在形狀屬性上、與文字內容無關，所以形狀與底色都留著）——實測輸出與 `--cover` 的刪除結果一致。

  另一個要知道的差異是**搬動一行**：`--no-cover` 底色跟著走（不會變成透明字落在別的背景上）但原地露出點陣原字，`--cover` 反過來（原地乾淨、搬過去的文字沒帶底色）——**兩種模式都要善後**，只是善後的內容不同，這一項不構成取捨。

- **`--no-cover` 的色帶比字墨高 0.20em，裁切必須知道**（2026-08-16 審查）：文字方塊頂端是 `ink_top − LEADING_COMP(0.20)×字級`（PowerPoint 的行首 leading 補償），所以底色長在文字方塊上時，**實際塗到的最上緣就是那裡**，不是 `ink_top − pad_v`。

  這個位移恆大於 `pad_v`（≈0.09em），因此「文字頂端高於色帶頂端」這個判斷式對 **6pt–60pt 每一行都成立** —— 它不是「緊密行特例」，**cover 模式下每一行都會拆成獨立色塊＋透明文字框**（形狀數約兩倍，這是設計、不是 bug，但註解不可寫成特例）。蓋板色帶在 `--no-cover` 時把這 0.20em（200dpi 下約 0.8×字級 px，24pt ≈ 19px）折進回傳的色帶，堆疊裁切才不會裁到一個色塊照樣跨過去的邊界。

  反過來，⚠️ **`--no-cover` 時下方色塊的頂端不可被推下去**：它被字形位置釘死，推它只會讓記錄的色帶與實際塗的不符、害到第三塊。

  ⚠️ **邊界必須鉗制到 ≤ 下行字頂 − 3px 邊距**（使用者回報 2026-06-14）：暗色／紋理背景（p8 單一／主專案 在裂痕機器上）讓空白列掃描失敗、退回「框重疊中點」，但這個中點**低於下行字頂** → 上框蓋板仍蓋住下行字頂、且下框蓋板頂被 `max(itop, 中點+pad)` 推到字頂之下、露出自己上緣的點陣。鉗制後只縮上框、下框維持蓋住自己字頂（**下行字頂是可靠分界、上行字墨帶才是被鄰字灌爆的那個**）。
