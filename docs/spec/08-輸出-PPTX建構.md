# 8. 輸出-PPTX建構

前面所有估計的結果到這裡變成投影片上的形狀與 XML。這一層的坑大多來自 PowerPoint 自己的行為。

⚙️ **動到輸出階段之前請先讀完這一章。** 實作上的落點（模組、函式名）見 §12。

> 這些條目原本住在 `CLAUDE.md` 的「架構」章，2026-08-23 搬進規格書；2026-08-24 改寫成技術中立，門檻、實測數據與反例一字未動。

- **單行形狀關閉自動換行**：字級估計只要略大一點就會把整行折行、毀掉版面。

- **CJK 字型需要直接寫 XML**：函式庫的字型設定只會寫進 `<a:latin>`；⚠️ **必須自己注入 `<a:ea>`**，否則中文會悄悄回落到佈景主題字型（見 §12.7）。

- **上標註腳標記**（使用者指示 2026-06-13）：行尾的註腳標記 `[1]`（p10「需要出處佐證[1]」）是縮小上移的上標、被辨識模型當成正常字。判別：文字結尾符合 `\[\^?\d+\]$`、且**該標記字墨明顯上移**（底部離本文底 ≥0.2 本文高）**又較矮**（≤0.92 本文高）。

  ⚠️ **程式碼框內字面 markdown `[^1]` 不上移（上移量 0）→ 排除**；行首的註腳定義標記 `[1]`（不在行尾）也不符。輸出時把行尾 N 字切成獨立 run、設上標基線（`baseline="30000"`）與 0.65 倍字級。全文僅 Render 面板那個 `[1]` 觸發。

- **刪除線**（使用者指示 2026-06-13，2026-06-14 重寫判別）：字墨中線有一條橫貫的細線（p9 `~~作廢內容~~`）。

  ⚠️ **純覆蓋率無法分辨「畫出來的線」與「碰巧對齊的 CJK 橫筆」**——使用者校驗的那份文件完全沒有刪除線，舊的「中段某列覆蓋 ≥0.75 且 ≥1.5×中位」卻在三行誤判：牽一髮動全身（「一」本身就是滿寬橫條＋鄰字中段橫筆對齊，峰 0.84）、單一（「單」堆疊多條 ~0.75 橫筆帶、峰僅 0.77）、(Context Engineering)（拉丁 x-height 密集、峰僅 0.65）。

  真刪除線是**單一、細、近滿寬、且疊在稀疏字身上**的線，三個誤判各破壞其中一條。新判別（字墨帶內覆蓋率 ≥0.70 的連續列為「帶」）：**恰好一個帶**（排除單一的 4 條堆疊帶、與 Context 的零帶）、帶**厚 ≤0.10×字高**（排除 ~0.13×字高 的「一」字橫條）、峰覆蓋率 **≥0.80**（排除單一/Context 的 <0.80）、帶中心落 0.30–0.70h、峰 ≥1.5×全列中位、且**帶外字身中位 ≤0.6×峰**（排除牽一髮動全身的密集字身 0.48）。閘門仍限水平、非弧／斜、≥2 字。

  **取捨**（使用者裁定 2026-06-14）：緊排 2 字若真有刪除線可能漏判，但遠勝誤判——這類簡報極少出現刪除線。

  **厚度閾值 0.07→0.10**（使用者回報 2026-06-15，p9 更新後加上真刪除線）：真刪除線帶厚 5px／行高 67＝比值 0.0746，舊的 0.07 差 1px 漏判。放寬到 0.10：全文掃描確認「作廢內容」是**唯一**通過其餘所有閘門的近候選。

  ⚠️ **但「三個舊誤判在前置閘門就被排除」這句話只對其中兩個成立**（2026-08-16 審查更正）：單一 靠帶數（4 條堆疊帶）、(Context Engineering) 靠零帶，都與厚度無關；**牽一髮動全身 四個前置閘門全過**——峰 0.84 ≥ 0.80、中心 ~0.5 在 0.30–0.70 內、字身 0.48 ≤ 0.6×0.84 = 0.504 —— **厚度是它唯一的判別器**，而餘裕已從 0.07-vs-0.13（1.9×）縮到 0.10-vs-0.13（1.3×），字身距離翻轉只剩 5%。⚠️ **不可再放寬。**

  帶厚／行高這個比值本身也帶字重（粗體上的刪除線畫得比較粗），正解是改用同一處早已算好的**筆畫寬**正規化（帶厚 ≤ K×筆畫寬，對字級／字重／DPI 都免疫），但那要有原始 deck 做視覺回歸才能定 K —— ⚠️ **沒有視覺驗證就不要動這個數字**（來源檔已刪除，見 §10）。

  ⚠️ **刪除線在輸出階段必須加「這個 block 只有一行」的閘門**（與同處的 `runs`／`superscript_tail` 一致）：合併後的 block 只保留第一行的樣式，合併行時會把整個合併段落全部畫上刪除線。
