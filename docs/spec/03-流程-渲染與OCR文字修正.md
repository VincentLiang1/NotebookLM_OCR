# 3. 流程-渲染與OCR 文字修正

這一章是 **OCR 讀出來的字串本身**：邊畫模型丟掉的空格與標點、被誤讀的字形、滑進來的簡體字、以及偵測器漏掉的行。這一層的每一條修正都有同一個危險：**補錯了比漏掉更糟**（蓋板會把正確的點陣字蓋掉、換上錯字），所以幾乎每一條都需要物理或詞彙佐證。

⚙️ **動到 OCR 文字修正或渲染之前請先讀完這一章。** 實作上的落點（模組、函式名）見 §12。

> 這些條目原本住在 `CLAUDE.md` 的「架構」章，2026-08-23 搬進規格書；2026-08-24 改寫成技術中立，門檻、實測數據與反例一字未動。

## 3.1 模型丟掉的東西：空格、分隔線、行尾標點

- **空格還原**：辨識模型會丟空格。拉丁字詞間的真實空格從**逐字 word box** 復原（間隙 > 行內字寬中位數的 1/3）— 但 CTC 的字框邊緣不準（KEEP 中間出現過 17px 的假縫隙、句點框寬達 30px），所以候選間隙還必須通過物理檢查：間隙條中段的墨水比例 < 0.15（實測：真空格 0.00–0.10、假縫隙 0.24）**且完全空白欄帶寬 ≥ max(4px, 0.27×字寬中位數)**（實測：Git Commit 真空格 23px、p6 Transformer 的 r→m 假縫隙 0px — r 字形右下天生稀疏、墨水比例擋不住，但模糊讓字墨連續、空白帶寬抓得住）。

  ⚠️ **空白帶寬門檻要按字寬比例縮放、不可用固定下限**（使用者回報 2026-06-13）：CTC 字框對寬的斜筆字會少框（W 的右臂落在框外），在字內製造假的「字母間」縫隙 — p4「Wiki」被拆成「W iki」（W→i 假縫只跨 6px 空白），而真正的詞間空格（LLM␣Wiki 跨 11px、b␣C 跨 18px，字寬中位 28–34）。0.27×字寬中位讓窄的字母抖動縫不再被當空格，真詞間空格仍以 ~1.7px 餘裕通過（舊的 0.2 固定係數在字寬 28 時放行了 6px 縫）。

  中文字 ↔ 英數字交界一律補空格（盤古之白），因為該處的量測間隙不可靠。⚠️ **重組時必須走訪原始文字**以保留模型自己輸出的空格 — 間隙分析只能「增加」空格、不能弄丟。

- **表格分隔線 `|` 復原**（使用者指示 2026-06-13）：辨識模型常把細的 `|` 直線吞掉（p9 markdown 表格示範「內容 | 內容」、提示行「段落，| 需」）。難點是字間隙裡的 `|` 與 CJK 字本身的直筆畫一模一樣，純偵測「間隙裡的細高直條」會在全頁誤判數十處（編／業／格／繁 等字的直筆）。

  **關鍵判別（使用者點出「全型｜」的啟發）：pipe 跨越整行高、比 CJK 字還高**（帶高／CJK 高 ∈ [0.9, 1.3]，CJK 邊緣筆畫只到 ~0.65）、**且是有空格的獨立 token**（間隙 ≥0.85 字寬）。再加上細（≤0.22 字寬）、寬度均勻（std/mean ≤0.3，排除 `[` 括號的上下勾）、兩側各留 ≥4px 空白（排除貼著字的邊緣筆畫）。六條閘門合一後全文僅命中 4 個真 pipe（提示行 1 ＋ 表格 3）、零誤判（checkbox 的 `[ ]`、CJK 直筆全部排除）。插入 ` | ` 並把 `char_boxes` 清成「沒有值」（1:1 映射已破壞）。輸出用半形 `|`（markdown 語意正確、與已辨識的表格 pipe 一致）。

- **行尾標點復原**：偵測器常把行尾的 。／） 裁掉。當框右側有墨水時，將行條右延 1.2×行高後以 **rec-only** 重新辨識（小裁切跑偵測會把行打碎），只接受「補回 1–2 個行尾標點」的結果。

  **兩道防幻覺守衛**（p12 卡片的紅棕虛線邊框被讀成 ：、整頁長出「單次寫：」「免疫防護。：」）：**(a)** 行尾已是 。！？ 的行不得再補 ：；，、．；**(b)** 補回標點的墨水欄位若在行帶上下的行距區（±0.08h~0.5h）都有墨、而**右移一個標點寬的對照窗乾淨** → 是垂直邊框、拒收 — 對照窗是關鍵：p2 橫幅色帶的上下緣會讓行距區全寬有墨，沒有對照窗時合法的 …的書。 也被誤殺。

  ⚠️ **行尾出現開引號（「『（等）視為幻覺**（框外被切半的 。 左弧會被認成 「，p6 案例）：改重讀「行尾 5 字高寬度」的小段、以 4 字後綴比對 — 整行重讀在 3400px 長行上會丟字（翻 N 本 → 翻本）害前綴比對失敗；真正的折行開引號重讀仍是 「、不在行尾標點集合內、自動保留原文。

  ⚠️ **辨識引擎的偵測／方向／辨識三個旗標會跨呼叫殘留** — 每次引擎呼叫都必須三個旗標全部顯式傳入，否則 rec-only 呼叫會污染下一次完整呼叫（見 §12.7）。

  **行尾 CJK 詞被併讀的復原**（同一條路徑；使用者回報 2026-06-13）：太短的框會把行尾的兩字 CJK 詞併成一個字（p13 膠囊標籤「執行 --lint 掃描」讀成「…描」，掃描→描）。重讀延長框後，若結果剛好多一字、前綴與原文（去掉原最後一字）完全相同、且復原的 2 字尾是**頁面詞彙**裡的詞（同頁「全域掃描」佐證），就採用。這些字其實在框內（框右側沒有新墨——只是更寬的裁切讓辨識模型有足夠脈絡拆字），故保留原框、只改文字、跳過行尾標點的延框與邊框檢查。**頁面詞彙佐證是防幻覺關鍵。**

## 3.2 簡繁與詞彙校正

- **簡繁轉換只准改「不可能是繁體」的字**（使用者回報 2026-08-23）：OpenCC 會把**兩種寫法都是合法繁體**的字對合併掉（划/劃、升/昇、台/臺、注/註），在一份模型讀對了的頁面上那是純粹的破壞——實測四份 deck 23 次轉換裡有 7 次是這種傷害（`AI_Quality_Guardrails` p2/p15「划得來」變「劃得來」、p1「拉升」變「拉昇」、p5「注定」變「註定」、p7「他那台壞」變「他那臺壞」，每一個都與渲染圖逐字核對過），真正的簡體殘留只有 14 次。

  **判準是 Big5**：cp950 編得出來的字本來就可以是繁體（划／升／台／注／征），編不出來的（恶／实／内／两／决／纪／装／试）才是模型滑進簡體的鐵證。沒有鐵證時只改編不出來的那些，其餘保留原樣。

  **鐵證以「頁」為單位**：同一頁只要出現一個 Big5 編不出的字，就代表模型在這頁確實在滑，該頁的模糊字對照舊信任轉換字典（`Transformer_演進地圖` p12 靠同頁的「训」把「新表征空間」修回「新表徵空間」）。

  **已知未涵蓋**：`The_GPT_Blueprint` p6 整頁沒有任何 Big5 編不出的字，「特征」因此留著沒修成「特徵」（原圖確實是「特徵」，屬模型滑動）——但那是一份簡體來源的 deck，代價可接受。

- **「這頁的模型在滑」這個判斷要收得很緊**（2026-08-23 code review）：上一條用「同頁出現 Big5 寫不出的字」當作放行轉換的鐵證，但**三種無辜的字也會踩到**，任何一個都會把整頁的保護關掉：
  - **(a) 刻意呈現的純簡體內容**（`CLAUDE.md` 自己的 `掌控习惯`）——那是受保護的內容而不是誤讀，所以**純簡體行沒有投票權**；
  - **(b) 不是簡體形的異體字／外文漢字**（喆 堃 犇、辻 働 図）——所以還要求該字**確實會被轉換字典改寫**；
  - **(c) 插圖裡的亂碼行**——所以套上與頁面詞彙相同的信心下限（分數 ≥0.8）。

  三道一起加之後，`['划得來的成本','他那台壞了','干擾訊號','後台管理','掌控习惯']` 這種頁面不再被一行簡體示範字整頁解除保護。

- **事後的整行確認也要吃同一道閘門**（同上）：純簡體行的確認在逐行修正**之後**才跑、直接呼叫轉換字典，只靠「改動的 2–4 字詞出現在頁面詞彙裡」把關——而**一份 deck 只要同時寫過 台北 與 臺北，它就自己提供了那份佐證**，於是把剛保住的 台 又改成 臺，在 台 的點陣上蓋一塊 臺。沒有頁面級鐵證時，這裡也只改 Big5 寫不出的字。

- **簡體混入修正**：辨識模型偶爾吐出簡體字形（惡→恶）。轉換**只套用在繁簡混雜的行** — 純簡體的行是刻意呈現的內容（例如第 4 頁畫面中的搜尋詞「掌控习惯」），必須保留。行級平手（規则）純文字無法判斷，預設轉繁體。

  ⚠️ **字典必須用 s2tw 而非 s2t**（使用者回報 2026-06-12）：s2t 是正體舊形字典，會把台灣慣用的合法繁體字也改寫 — 「越吃重」被轉成「越喫重」；s2tw 保住 吃、照樣修 恶→惡。

  **整行 CJK 全滑成簡體時混雜測試不會觸發**（p3「AI 执行：」、p9「LLM 合规」— 拉丁字母不影響往返比對、行被當成純簡體保護）：靠頁面詞彙佐證解套 — 轉繁後「有變動的 CJK 字串」（2–4 字）逐一在同頁高分行詞彙中找到才採用（執行 由同頁「…AI 執行的自動化編譯…」佐證）；找不到佐證就維持原樣，刻意呈現的純簡體內容（掌控习惯）因此仍受保護。

- **頁面詞彙校正**：最小的籌片字退化到模型極限（p9 資訊 讀成 黃訊 0.66、驅動 讀成 驅勤），但同頁通常有大字高分行寫著同樣的詞（商業驅動>資訊架構>系統建設 0.85）。低分（<0.8）2–4 字純 CJK 行若與頁面詞彙（高分行的 2–4 字子串）恰差一字就校正。⚠️ **候選以頻次裁決、嚴格最高頻才採用** — 跨詞邊界子串會污染候選（架的 來自 框架的…），但真詞會在頁面重複出現（架構 在 資訊架構＋RAG架構）。

- **同籌片漏行救援**：偵測器整行漏掉小籌片的第二行（p9 資訊 下面的 架構，偵測器任何解析度／模型都看不見）。⚠️ **偵測器換更大的邊長上限（4096）或 server 偵測模型都試過，更糟。** 改對 2–4 字小 CJK 行上下探帶、rec-only 重讀，**只在頁面詞彙能驗證（精確或差一字）時採用** — 未驗證就插入會蓋掉正確點陣字卻顯示錯字，比漏掉更糟（架構 那一帶讀出來是 架樽／架模）。

- **混淆雙字組修正表**：辨識模型穩定誤讀、且以 5× 放大目檢確認過原圖真值的字對（反椎→反推、雨份→兩份、幹擾→干擾）。⚠️ **只收非真實詞彙的雙字組**（無誤殺空間）。三條原則性路線都實測失敗才收表：局部窗口 rec-only 重讀照樣讀錯；YaHei 模板 XOR 區比對與滑動對位 IoU 都分不開「只差部首」的字（椎/推 邊際 −0.02，來源字型又非 YaHei）。

## 3.3 圖示與圓點

- **警告圖示修正**：行首的 ⚠ 三角形會被辨識成 'A'。判別器：圖示底部是一條連續墨水帶（佔框寬 0.93）、真正的 A 是兩隻分開的腳（0.24）；門檻 0.6，只套用在「行首 A、後接空格或中文」。

  兩個陷阱：⚠️ **背景色不能用環帶**（緊貼圖示的環帶會落在圖示上、把背景估成圖示色），要用框內主色；⚠️ **反鋸齒也會形成第二叢集**，但 AA 色落在「背景↔字色」連線上（殘差 < 45），圖示填充色偏離該線 — **必須做共線檢查**（TSV 曾被誤判）。只套用在「單一拉丁字母」的偵測行。

  **框外搜尋與蓋板左延**（使用者回報 2026-06-14）：偵測框常切掉或排除行首圓點 → 蓋板從框左起算遮不到點陣圓點、露出一截（p2 改變計量／投资工程，模型已把圓點轉成原始的「·」但框左切過圓點中心），或圓點整顆在框外（p2 制度面，框左 1497、圓點 ~1450）。改用**固定視窗** `[x0−0.9lh, x0+1.0lh]`（不再以第一字左緣為界——已轉寫時第一字框就是圓點本身、反而排除它）搜最左合格圓盤，回傳一個新的左界把 `bbox` 左緣延伸到圓點左邊（等同修正偵測誤裁、下游蓋板與「• 」文字自然對齊）；原始「·」開頭也照搜（只延蓋板、不重複加）。

  ⚠️ **「實心」不夠，必須是「圓盤」**（2026-08-17 以 CB 詢圈策略／Markdown Blueprint 兩份新 deck 驗證）：原本「填充率 ≥0.55 ＋ w/h ∈[0.55,1.7]」太鬆，會把**楔形標記**當成漏掉的圓點，於是把點陣三角形蓋掉、改畫一顆圓點（換掉了原稿真正顯示的字形），或在已轉寫的箭頭後面再補一顆。三道量測到的判別（真圓點 vs 誤判，樣本 8 vs 7）：
