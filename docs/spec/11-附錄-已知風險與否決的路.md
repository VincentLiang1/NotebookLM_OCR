# 11. 附錄-已知風險與量過而否決的路

這一章收兩種「不要再走一次」的東西：**查證過但決定不動的結構性風險**，以及**做出來或量過、結論是不做的路**。兩者的共同點是——不寫下來的話，每個接手的人都會再做一次。

## 11.1 已知的結構性風險（查證過、決定不動）

- **2026-08-23 code review 留下、尚未處理的三個結構性風險**（有紀錄才不會被下一輪「順手修好」或悄悄踩到）：
  - **`_surface_around_ink` 對投影深度的反應不是單調的**：投影若深到把最前面兩段都灌滿（合成測試：投影核心 ≥18px 平坦），兩段會「一致」，函式就回報**投影色本身**當表面、且 `glow_px=0`（因為半徑寫死 `0.0 if i == 0`），等於把 73dd4b3／fcf74ee／43bbdc7 三次修正整組關掉。CLAUDE.md 量到的真實投影是 10–20px，失效帶就在這個範圍的上緣。真實 deck 沒有重現（四份掃描全數正常），但**「走完五段仍不穩定」的哨兵值與「最後一段才穩定」的半徑同為 18，兩者無法區分**——要改的話得改成拿收斂後的顏色（而不是帶的索引）當判準，並給 `HALO_BANDS` 留出 18px 以外的餘裕。
  - **`harmonize_bold` 會用 `bold_r` 推翻 `CHROMA_TRUST_R` 剛做的判斷**：隊列鍵只看字級（刻意不含文字色，也沒有 chroma 閘門），`_bold_promote_ok` 只要 `r ≥ −0.05` 就補粗、`_bold_demote_ok` 只在 `r < 0.22` 才撤粗——於是同一個 `bold_r` 在檔案裡有三個互相矛盾的信任門檻（有彩時 <0.35 不可信、補粗時 ≥−0.05 可信、撤粗時 <0.22 可信）。`Reinforcement_Learning_Blueprint` p3「延遲回饋」(r=0.29) 實際走過這條路，但最終輸出**是對的**（原稿三行同粗），所以目前是一致性缺陷而非可見回歸。
  - **`_cover_band` 的垂直 `pad_v` 沒有墨水測試**，而同一個半徑的水平版本 `_glow_reach_x` 有（它的 docstring 就寫著「不可吞掉卡框、牽引線、鄰字」）。`_trim_stacked_overlaps` 只保護「兩個文字塊」的配對，卡框／格線／牽引點不在其中。另外接縫灌填的閘門量的是**加了 pad 之後**的間隙，所以 `glow_px` 每加 3px，可被灌填的真實設計間隙就多 6px。

- **把上下標公式的判別放寬到純字母行**（2026-08-25）——見「無法忠實還原的行保留原圖」的 (c)。判別是「切欄量各字墨重心，散佈 >0.25 行高」，而「行內要有數字」那道閘門**不是遺漏、是它成立的前提**：數字與大寫字母等高，重心散佈才等於基線位移；一旦放小寫字母進來，x-height 與 ascender 的高度差自己就把散佈撐開了。五份 deck 量過，散佈 >0.25 的純字母行有 8 個，其中 **6 個是真內容**（`matmul` 0.453、`NETWORK` 0.467、`Sparse` 0.404、`(ReLU)` 0.375、`Post-LN` 0.255、`XSNorm =` 0.253），該丟的只有 `QKT` 0.347。
- **改用「全大寫 + 末欄又矮又抬高」抓轉置上標**（QK^T，2026-08-25）——同上一條。414 個拉丁行、45 個全大寫行量過：`QKT` 的末欄高度比 **1.000**、抬高 **0.000**，判別式**完全抓不到它**（欄投影根本沒把上標 T 切出來）；反而是 `NETWORK`（末欄是框緣的 1px 雜點，0.044／0.935）與 `EXPERT GATE`（0.706／0.217）會誤觸發。
- **單行斜排裝飾字比照成對規則丟棄**（2026-08-25）——見「書封／告示牌式斜排裝飾字成對丟棄」。五份 deck 只有 10 行 |角度| ≥15°：3 行含 CJK（本來就豁免）、2 行是 `000` 雜訊、**4 行是真內容**（`Day1` 26.1°、`Week1` 25.7°、`User Profile` −28.7°、`EVOLUTION&OPTIMIZATION(8YEARS)` −23.3°），該丟的只有斜置紙片上的 `System Pramp!`（−23.3°，真值 System Prompt）。`Day1`／`Week1` 與同頁 25° 的三行 CJK 斜字是同一組，可見「無 CJK」不等於裝飾；分數也分不開——該丟的那行 0.95 反而是全場最高。
- **整個關掉辨識管線的 180 度方向分類器**——見「整行被辨識管線吃掉：方向分類器把橫排行判成上下顛倒」。五份 deck 量過：救回 6 行、卻弄丟 3 行真的被轉成顛倒的直排標籤（rlbp p12 決策依據（Decision Basis)、trans p1 DECODER／2028）。改成「只有被轉過 90 度的裁切才准套用」之後兩邊都成立。
- **偵測器換更大的 `max_side_len` / det server 模型救漏行**——見「同籌片漏行救援」。4096 與 server 模型都更糟。
- **靠局部窗 rec-only 重讀、YaHei 模板 XOR、滑動對位 IoU 分辨「只差部首」的誤讀字**——見「混淆雙字組修正表」。三條原則性路線都實測失敗，才收下辭典型修正。
- **把粗體模板比對的取墨門檻抬到反鋸齒緩坡更高處**（2026-08-25，實作後退回）——見「粗體判定：≥24pt 一律粗體；≥16pt 用「模板比對」；更小用筆畫門檻」。起因是 guardV2 p13 兩個並排標題同樣粗、卻一個判粗一個沒判：`Phase 1: 粗篩 (機械化)`（黑字）r=0.1202、`Phase 2:判斷 (AI 精讀)`（藍字）r=0.8165，而門檻是 `BOLD_R_THRESH`(0.13)，差 0.0098。**成因查清楚了而且是真的**：藍字帶 12px 光暈（`glow_px`=12，黑字是 0），`INK_DIST`(60) 的遮罩把整圈光暈算成墨水，實測筆畫被吹成 11.027；黑字量到 9.109。把取墨門檻掃過 30→140 可以看到兩行**核心筆畫完全相同**（門檻 100 時 8.128 vs 8.169），差異全在緩坡。同時模板那邊的補償方向相反（`rel` = 60/contrast，黑字 0.250、藍字 0.291，於是黑字的模板被留得更粗），兩個效應同向疊加。

  **做法**：取墨距離改成 `max(INK_DIST, α×contrast)`，觀測遮罩與模板 `rel` 同步用它（α ≤ 0.42 時對 contrast ≤143 的行完全等價於原行為，低對比的行一行都不動）。**結論是退回**，兩個理由：

  1. **五份 deck 全跑的逐行比對（1292 行）**：輸出變動 59 行——bold 翻掉 56 行（54 補粗、2 撤粗）、`font_pt` 動了 6 個（bold 是 `harmonize_font_sizes` 的分組述詞之一，翻了就會改分組）。目視 guard p8 與 guardV2 p9 的整頁渲染圖確認**補粗是錯的**：那些是一般字重的內文。判別很硬——**翻掉的行與同一段的其他行不一致**（guard p8 的『主觀判斷。』翻了、同段的『檔名就是正確答案，不需要人為』沒翻；guardV2 p9 右欄的四行項目翻了、左欄一模一樣的四行沒翻）。
  2. **重新校準門檻救不了**。α 掃過 0.25／0.30／0.35／0.42／0.50／0.58／0.65，對照 28 行目視標註（2 行該粗、26 行不該粗）：**每一個 α 的餘裕都是負的**——該粗的最低分（Phase 1）永遠低於不該粗的最高分。最好的是 α=0.50 的 −0.075（Phase 1 0.2315 vs `• 實測：抓出 7 個靜默漏報` 0.3061）；現行的 α=0.25 是 −0.165。**沒有任何門檻切得開。**

  換句話說：這份語料在 18–20pt 的 SemiBold 標題與 Regular 內文，在模板指標上**本來就重疊**，切在緩坡哪個高度都一樣。要修 Phase 1 得換一條路——**同段折行的字重一致化**，或**同列並排標籤的孿生一致化**——而不是動這個指標。⚠️ 附帶量到的：多色行（`抽取警告，把數字轉為`，其中『警告』是橘色）在 α ≤0.42 時是最穩定的偽陽性，baseline 就已經誤判成粗體了。
